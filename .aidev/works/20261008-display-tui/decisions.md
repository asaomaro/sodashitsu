# 決定の記録: 表示の面の端末版

`mode: autonomous`。TD1 は経緯。**TD2〜TD7 は、勧める案で骨子を書いたもので、利用者に決めてもらう点**。

## TD1: 別の work にした・PR は 2 つ

- 経緯と理由は `20261008-display-layout/decisions.md` D2。端末版は、面を描くことから作る。
- **TUI-1**（帯とパネルを描く・操作を返す）は、ブラウザ版の PR-A の後なら始められる。**TUI-2**（配置・たたみ・浮いた窓・D&D）は、ブラウザ版の PR-C の後（決まりを揃えるため）。
- この work は、要件と、設計の骨子まで書いた。`tasks.md` は、TD2〜TD7 の答えの後に書く（答えで、作るものの量が大きく変わる。特に TD3・TD6）。

## TD2: 端末版は、ブラウザ版と別の種類を名乗る（`term-panel`・`term-band`・`term-actions`）

- **勧める案**: `DISPLAY_RENDER_FEATURES` に 3 つを足し、`DisplayRenderers` に `termPanel`・`termBand`・`termActions`（数）。端末版は `panel`・`band`・`actions`・`script-html` を名乗らない。TUI-2 で、`collapse`・`dock`・`float` も名乗る（計 6。`subscribe` の配列の上限 8 の内。ブラウザは 7 で、残りは 1 つ。上限を上げると、古いサーバが `subscribe` ごと断るので、上げない）。
  サーバの機能の名前 `term` を `DISPLAY_FEATURES` に足し、端末版は `display.features` で確かめてから描く（`subscribe` は、知らない種類を黙って捨てて成功するので、`subscribe` だけでは、古いサーバを見分けられない）。
- **理由**: `panel` の数は、いま「HTML と CSS を描ける画面の数」を意味している。端末版が同じ名前を名乗ると、HTML だけで出すプログラムが「見えている」と誤解する（`research.md` T3）。
- **代替案**: (a) 同じ `panel`・`band` を名乗り、別に「文字だけ」の印を足す＝数え方が 2 軸になり、読み手が間違えやすい。(b) 何も足さず、`panel` に数える＝いちばん単純だが、上の誤解が残る。
- **得失**: プログラムは、`renderers.panel === 0 && renderers.termPanel > 0` なら「文字か Markdown で出す」と判断できる。古い sodactl・古いプログラムは、知らない項目を無視する（今の決まり）。
  **失うもの**: いまの文書は「端末版だけ → `renderers` はすべて 0」と案内している（`docs/display.md:302`）。`panel` の数を見て、出すかどうかを決めている既存のプログラムは、直すまで、端末版しか無いときに何も出さない（代替案 (b) なら、文字と Markdown のプログラムは、直さずに端末版に出る）。
  `collapse`・`dock`・`float` の数は、ブラウザと端末版を合わせた数になる（分けない。「その機能を持つ画面が 1 つでもあるか」の意味）。

## TD3: `html` は、文字を取り出して描き、ボタンだけを押せる行にする

- **勧める案**: タグを落として文字にする（ブロックの要素は改行・`<script>`・`<style>` の中身は捨てる・実体参照は戻す）。`<button data-soda-action="…">` だけを、押せる行（`[ ▸ 文字 ]`）にする。`markdown` の中の同じボタンも。フォーム（入力欄）は出さず、固定の文言を 1 行。
- **押せるものの決まり**: ブラウザ版で押せないもの（コードの囲み・`<textarea>`・`<template>`・コメントの中の `<button>` の文字、`disabled`・`hidden`）は、押せる行にしない。タグを落とすだけの取り出しでは守れないので、**HTML の字句を、状態を持って読む小さな読み手**（タグ・属性値の引用符・コメント・生の文字の要素を区別する）を書く。
- **代替案**: (c) HTML の字句解析のライブラリを足す＝正確。依存が増える（`research.md` V2）。(a) `html` は全部、固定の文言「ブラウザ版で見られます」＝作るものが最小で、誤った見え方をしない。ただし、操作（ボタン）は `html` か `markdown` の中の HTML でしか宣言できないので、端末版では操作を 1 つも返せなくなる。
  (b) フォームも、端末の入力欄に読み替える＝端末版でも入力を返せるが、入力欄の部品・検査・フォーカスの扱いが増える（差分が大きい）。後の作業の候補。
- **得失**: 勧める案は、レイアウトに頼った HTML（表・横並び）は崩れて見える。作者は、機能の問い合わせ（TD2）を見て、端末版には Markdown で出せる。

## TD4: Markdown は、行ごとの小さな解釈を自前で書く（未確認の前提あり）

- **勧める案**: 見出し・箇条書き・番号つき・チェックリスト・コードの囲み・引用・表・区切り線・強調の記号を外す・リンクは「文字（URL）」、だけを扱う、行ごとの解釈を `packages/tui` に書く。分からない書き方は、文字のまま出す。
- **代替案**: `marked` の字句解析を使う＝正確だが、端末版の依存とバンドルが増える。使えるか・どれだけ増えるかは **未確認**（`research.md` V2）。design の最初に確かめて、決め直してよい。
- **どちらでも**: 解釈の結果は「行（文字と飾り）と、押せる場所」の並びで、無害化の後の文字だけを含む。

## TD5: 帯は 1 行。端末の最小は、端末版では 30 列・8 行。収まらない面は、重ねて開ける

- **勧める案**: 帯は、高さの指定（px）に依らず 1 行（中身の最初の 1 行）。パネルの最小は 20 列・4 行。**端末（pane の中身）の最小は、端末版では 30 列・8 行**。下回るなら、パネルは自動でたたむ（ブラウザ版と同じ順）。
  自動でたたまれた面・たたんだ面は、帯の行の印になり、**押す（か `prefix+i`）と、pane の上に重ねて開ける**（TUI-1 から。今の重ねる部品＝開いている間は、キーはそのパネルへ）。
- **理由（数字）**: サイドバーの既定は 26 桁・1 列表示は 64 桁未満。80 桁の端末では、pane の中身は 52 桁（枠を引いて）。ブラウザ版と同じ 40 列だと、パネルの最小 20 桁を足して 60 桁が要り、**80 桁の端末で、パネルが 1 つも開かない**。30 列なら 50 桁で、開く。
  120 桁を左右に分割した pane（47 桁）では、30 列でも開かない。だから、「重ねて開ける」を TUI-1 に入れる（入れないと、`set` は成功し、数にも入るのに、何も読めない）。
- **代替案**: (a) 最小を、ブラウザ版と同じ 40 列・10 行にする（決まりが 1 つで済むが、上のとおり、80 桁で開かない）。(b) もっと小さくする（20 列・5 行）＝開くが、端末が読めないほど狭くなる。使ってみて決め直せる（定数）。

## TD6: 浮いた窓は、モーダルでない新しい層として作る

- **勧める案**: `Renderer` の描く順に「浮いた窓の層」を足す（pane の後・飾りとトーストの前・重ねる部品〔メニュー・ダイアログ〕の下）。窓は、その pane の中身の箱の中だけ。開いていても、キーは pane へ届く（フォーカスを移すのは `prefix+i`）。マウスの当たりの判定に、窓を足す。
- **理由**: 端末版の重ねる部品（`Overlay`）は 1 つずつで、開いている間は入力を全部取る（`research.md` T10）。出しっぱなしの窓には使えない。
- **代替案**: 浮いた窓だけ、モーダルにする（開いている間は pane を打てない）＝既存の `Overlay` に載るので作るものは少ないが、「端末の幅を奪わずに、見ながら打つ」という要望に合わない。
- **得失**: 勧める案は、描く順・当たりの判定・フォーカスの状態の 3 か所に手が入る（TUI-2 の中心の作業）。

## TD7: 端末版の E2E は持たない

- **勧める案**: 確かめは、純粋な関数の単体・格子の単体・アプリごとのテスト（`startedApp`。試験用の外側の端末に流して、見えている文字列と、**出した列そのもの**を調べる）・サーバとの結合（`tui.integration.test.ts`）。エスケープシーケンスの無害化は、「出した列に、禁じた列が現れない」を、アプリごとのテストで見る。
- **理由**: `packages/e2e` に端末版の spec は無く（`research.md` T17）、PTY で動かす仕組みを作るのは、この作業の外。手で流す `scripts/tui-pty-verify.mjs` に、面の 1 巡を足す。

## TD8: 独立点検の結果（1 回目。要件と骨子）

- 25 件（must 3・should 17・nit 5）。直したもの:
  - **must**: 既存の `stripControl` は、終端の無いエスケープの始まりが並ぶ中身で、長さの 2 乗の時間が掛かる（256 KiB で 6〜18 秒。点検の側が、同じ正規表現で測った）→ 無害化は、1 回の走査の状態機械を自前で書く（要件の非機能・AC8・設計の E8）。
  - **must**: 無害化を解釈の前に掛けると、HTML の実体参照（`&#x1b;`・`&#x202e;`）の復元で、制御文字が生まれ直す。`Grid.set` は文字を検査しない → 無害化は、解釈の後の文字に掛ける・面の箱へ書く関数を 1 つにする（機能要件 6・AC6・AC7・E1）。
  - **must**: ブラウザ版と同じ最小（40 列）だと、80 桁の端末で、パネルが 1 つも見えない → 端末版の最小を 30 列・8 行にし、収まらない面を「重ねて開ける」を TUI-1 に入れた（TD5・機能要件 8・AC20）。
  - should: 外側の端末への出口は `Screen.frame` だけではない（題・通知・クリップボード・stderr）→ 不変条件と AC19。サーバの機能の名前 `term`。`tui-state.json` は端末ごとではない → マシンごとの鍵。面のフォーカスとキーの振り分け・当たりの判定の順・画像・押せるものの決まり、ほか。
- 残したもの（design の続きで決める）: 外側の端末と幅の表が食い違う文字の扱い（`research.md` V5。限界として docs に書き、箱の右端に 1 桁の余白を置く案）・前処理の時間の上限の値・浮いた窓と「前の格子から写す最適化」。

## TD9: 独立点検の結果（2 回目）と、design の続きで必ず取り込む点

- **2 回目**（1 回目を直した版。別のコンテキスト）: **must は無い**。1 回目の must 3 件は、要件・骨子・決定の記録で食い違いなく直っている。should 14・nit 9。点検の回数の上限（2 回）なので、要件と骨子は、ここでは直さない（直すと、その版を見る点検がまた要る）。
  **下の点は、`design.md` の細部と `tasks.md` を書くときに、必ず取り込む**（取り込んだ版に、あらためて独立点検を掛ける）。
- 安全・AC5／AC6 に直に関わるもの:
  1. **押せるものの決まりが足りない**。ブラウザ版は `marked`（同梱。`packages/web/public/ask-view/vendor/marked.umd.js`）で解釈し、押せるのは「`data-soda-action` を持つ任意の要素で、`form` でなく、`disabled` も `aria-disabled="true"` も無いもの」（`packages/web/public/display-view/frame.js:222-224`）。
     端末版の決まりは「迷ったら押せない」にし、**「端末版で押せる ⊆ ブラウザ版で押せる」を AC にする**（インラインのコード・字下げのコード・`~~~`・引用や箇条書きの中の囲み・逆斜線・`&lt;button&gt;`〔戻した実体参照を、もう一度タグとして読まない〕・生の文字になる要素・ブラウザ版が取り除く要素の中）。TD3・TD4 の得失に、「`marked` の字句解析を使えば、解釈がブラウザ版と揃う」と「同梱の版がある」を足す（`research.md` V2 の「どの `package.json` にも無い」は、依存としては正しいが、同梱の版がある）。`<button>` だけか、任意の要素か、も選択肢に。
  2. **無害化の状態機械の遷移を、表で決める**（CSI・文字列以外の ESC の列〔`ESC ( B`〕・不正な CSI は、その文字から読み直す・文字列の途中の ESC／CAN／SUB で打ち切る・CRLF は LF・単独の CR は改行）。**安全は、段 2（制御文字を落とす）と、書く関数が担い、段 1 は見た目のため**、と書く。
  3. **1 つのセルに足す幅 0 の文字の上限は、一般カテゴリではなく、`charWidth(cp) === 0` で数える**（U+1160 など、Cf でも Mn・Me でもない幅 0 の文字が、無制限に 1 つのセルへ足される。`Grid.text` は無制限に足す＝`render/Screen.ts:147-150`）。面の箱へ書く関数は、自前でまとめた文字を `Grid.set` へ渡す（`Grid.text` を使わない）。
  4. **AC6 の判定に、「ESC 以外の C0 と DEL が、出力に 0 件」を足す**（裸の SO・BS・CR・BEL）。
  5. **面のフォーカスを外す条件は、「copy・navigate・resize に入った」**（prefix に入っただけでは外さない。外すと、`prefix+i` で次の面へ巡れない）。`prefix+i` の順（開いているパネル → たたんだパネル → 出ている帯 → たたんだ帯。最後にフォーカスした面の次から）。重ねて開いた部品の中での、次の面への移り方。
  6. **面にフォーカスがある間、pane へ書く操作を全部捨てる**（prefix の 2 度押しの `send`・`ctrl+v` の画像の貼り付けも。`pass` だけを回す作りでは、この 2 つが pane へ届く）。
- そのほか: マウスの当たりの順（進行中のドラッグ → 知らせ → サイドバー → tab バー → 面 → スクロールバー → 境界 → 枠 → 中身）と、スクロールバーの桁（`content` のすぐ右の桁。面の無い pane では今と同じ）／Cf を落とすことで崩れる言語（ペルシャ語・インド系の文字の接合、アラビア語の数の印）と、暗黙の双方向を持つ外側の端末での並べ替えを、限界に書く／TUI-1 から `collapse` を名乗る／
  TUI-2 で、自動でたたまれた面を印から開くのは「一時の重ね表示（記憶を書かない）」のまま／帯の 2 行目からと、収まらないボタンを読む道（帯も、重ねて開ける）と、帯・印の行を出す下限／`--size`（px）を列数にどう読むか／AC16 は、行番号でなく「`docs/` と `AGENTS.md` に『ブラウザで使えます』『端末版には出ない』の残りが 0」で書く／
  `tui-state.json` の「読み直して重ねる」は排他ではない（限界）・マシンの鍵が何か／面の文字を写す手段が無いこと（限界）／知らせ（右下）が、下の帯・右のパネルに重なる（ブラウザ版の D14 に当たる決まりを持つか）。

## TD10: 利用者の決定（確定。2026-10-08）と、main との関係

- **TD2〜TD7 は、すべて、勧める案で確定**: TD2（`term-panel`・`term-band`・`term-actions` を名乗る）・TD3（`html` は文字を取り出し、ボタンだけ押せる行に）・TD4（Markdown は自前の小さな解釈）・TD5（帯は 1 行。端末の最小は 30 列・8 行。収まらない面は重ねて開ける）・TD6（浮いた窓は、モーダルでない新しい層）・TD7（端末版の E2E は持たない）。
- **進める順**: ブラウザ版 PR-A → PR-B → PR-C → 端末版 TUI-1 → TUI-2。
- TD9 の「design の続きで必ず取り込む点」は、そのまま有効（TD3・TD4 を勧める案で進めるので、**「端末版で押せる ⊆ ブラウザ版で押せる」を AC にする**・無害化の遷移の表・幅 0 の文字の上限、が特に要る）。
- PR3 がマージされた main（`1ff0418`）で、端末版に効く変更: `script-html` は設定（`displayScriptEnabled`。既定は無効）で有効にしたときだけ出る。端末版は、`script-html` を描かない（固定の文言）ので、設定を読む必要は無い。`design.md`・`tasks.md` を書くときに、行番号を main で取り直す（`research.md` の行番号は、PR3 の途中の版のもの）。
