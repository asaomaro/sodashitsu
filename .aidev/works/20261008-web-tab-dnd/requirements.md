# 要件: ブラウザ版の tab のドラッグでの並べ替えと、pane の移動を同じ worktree の中に制限する

## 背景 / 課題

- 端末版は tab をドラッグで並べ替えられる（`docs/tui.md`「マウス」、`docs/tui-parity.md` の H04m・M12）。ブラウザ版はキー（`move_tab_previous`・`move_tab_next`。既定のキーなし）でしか並べ替えられず、マウスで使う人には手段が無いのと同じになっている（`docs/tui-parity.md` の H04m・M12 の Web の列が「無し」）。
- 前の作業 `20261004-ui-interaction-polish` が、利用者の指摘「タブは、ブラウザ版ではドラッグで並べ替えられない」を `split-dnd.md` の F13・AC8 として切り出したままになっている。この作業は、そのうち **tab の並べ替え**だけを取り上げる（F13 と、それに要る最小の見せ方）。workspace・pane を含む D&D 全体の表現の作り直し（ポインタに付いて動く像・掴める形のカーソル・禁止の印。F7・F8 の像・F10・F11 の印）は、取り上げない。

- **追加（利用者の決定。2026-10-08）: pane を別の workspace へ移すのを、同じ worktree（同じフォルダ）の workspace どうしに制限する。** いまは、pane の名前を tab・サイドバーの workspace の行へ落とすと、どの workspace へも移せる（`pane.move_to_tab`・`pane.move_to_new_tab`）。一方、workspace がどの worktree として一覧に出るかは、最初の tab の先頭の pane のフォルダだけで決まる。別の worktree の workspace へ pane を移すと、一覧の行（ブランチ名など）と中身がずれる（worktree `main` の workspace に `feature-x` の pane が混ざる）。先頭の pane を移すと、移動元の行の表示が切り替わる。1 つの worktree を 1 つのまとまりとして扱うために、混ざる移動そのものを断る。

## 目的 / ゴール

ブラウザ版（デスクトップ）で、マウスだけで tab の順を直せる状態。つかんだ tab がどこに入るかが離す前に分かり、今ある操作（クリックでの切り替え・右クリックのメニュー・ホイール・pane の名前を tab へ落とす移動）はどれも今までどおり働く状態。

pane については、どの入口から来ても、pane が別の worktree の workspace へ移らない状態。落とせない先は、落とす前に落とせないと分かり、断られたときは理由と、どこへなら移せるかが分かる状態。

## ユーザーストーリー

- US1: マウスで使う利用者として、tab をドラッグして並べ替えたい。なぜなら、キーを割り当てなくても順を直せるから。（受け入れ: AC1〜AC9, AC-I1〜AC-I5）
- US2: 複数の worktree・リポジトリを 1 つのサーバで開いている利用者として、pane が別の worktree の workspace へ移らないようにしたい。なぜなら、一覧の行（どの worktree か・ブランチ名）と、その workspace の中で動いているもの（そのフォルダのシェル・エージェント）がずれると、どこで何が動いているかを取り違えるから。（受け入れ: AC11〜AC19）

## スコープ

### 対象
- ブラウザ版のデスクトップの画面の tab バー（`TabBar.vue`）。同じ workspace の tab の間での並べ替え。

- pane を別の tab・別の workspace へ移す操作（`pane.move_to_tab`・`pane.move_to_new_tab`）の制限。サーバで断り、ブラウザ版・端末版の pane の名前のドラッグは、落とせない先として見せる。

### 対象外
- 利用者が作る「グループ」・worktree グループ（同じリポジトリ）を、pane の移動の制限の単位にすること（単位は worktree 1 つ）。
- pane の中で `cd` して別の worktree へ移ることの制限（今の動きのまま）。
- pane を移す新しい入口（`sodactl` のコマンド・メニュー・キー・モバイルの移動先の一覧）を足すこと。いまある入口は pane の名前のドラッグ（ブラウザ版・端末版）と、RPC を直接呼ぶクライアントだけ（design「確かめたこと」）。
- 同じ tab の中の操作（入れ替え・縁への分割・置き換え）。もともと同じ tab の中でしか働かない。
- 別の workspace への tab の移動（後の作業の候補）。
- モバイルの 1 列の画面（tab バーを持たない）と、タッチでのドラッグ（AC9）。
- ポインタに付いて動く像・掴める形のカーソル・「落とせない」印など、D&D 全体の表現の作り直し（`20261004-ui-interaction-polish/split-dnd.md` の残り）。
- tab の並べ替えのための、サーバ・protocol の変更（AC8）。1 回で目的の位置へ動かす RPC（`tab.move_to` のようなもの）は足さない（後の作業の候補）。
- 端末版の変更。

## 完了条件 (受け入れ基準)

- [ ] AC1: tab バーの tab をマウスの左ボタンでつかんで動かし、別の位置で離すと、その tab がその位置へ並べ替わる。隣へ・2 つ以上離れた位置へ・先頭へ・末尾へ、前向きにも後ろ向きにも動かせる。画面の tab の順と、サーバの持つ順（再読み込みした後の順）が一致する。
- [ ] AC2: ドラッグ中、離したときに入る位置（tab と tab の間・先頭の前・末尾の後）に線が 1 本だけ出て、つかんだ tab は元の場所で薄くなる。線の位置と、離した結果は一致する。離しても順が変わらない位置（つかんだ tab の前後の境目）と、tab バーの外では、線は出ない。離す・取り消すと、線と薄さは消える。
- [ ] AC3: tab が多くて tab の列があふれているとき、ドラッグしたままポインタを列の左右の端（24px）へ寄せると、列がその向きへ自動でスクロールし、最初は見えていなかった位置へ落とせる。
- [ ] AC4: tab バーの位置の設定が「下」でも、AC1・AC2 が同じに働く。
- [ ] AC5: 並べ替えは、同じサーバにつながっているほかの画面（別のブラウザ）に、再読み込みなしで反映される。
- [ ] AC6: ドラッグ中に画面の外から状態が変わっても壊れない。つかんだ tab が閉じられた・tab が 1 個になって tab バーが隠れた・表示中の workspace が切り替わった・ダイアログ（グラフ画面・質問のフォームを含む）が開いた、のどれでも、ドラッグは取り消しになり（何も送らない）、線・薄さ・キーの受け口が残らない。tab の数や順だけが変わったときは、離した時点の順で入る位置を決める（その変化でブラウザがポインタの捕捉を外したときは、取り消しになる。どちらでも、線・薄さ・キーの受け口は残らない）。
- [ ] AC7: pane の名前のドラッグと取り違えない。pane の名前を tab へ落とすと今までどおりその tab へ pane が移り（`pane.move_to_tab`）、tab の順は変わらず、入る位置の線も出ない。tab のドラッグ中は、pane の落とし先の強調（tab の破線の枠・pane の縁と中央・サイドバーの行）は出ず、pane の上・サイドバーの上で離しても何も起きない。
- [ ] AC8: tab の並べ替えのためには、サーバ・protocol を変えない。tab のドラッグでブラウザが送るのは既存の `tab.move`（動かす数だけ）と、確定の後の `tab.focus` だけで、取り消し・順が変わらない位置で離したときは `tab.move` を 1 つも送らない。`tab.move` を持つ今までのサーバでそのまま動く。
- [ ] AC9: タッチのポインタでは、tab のドラッグは始まらない（タップでの切り替え・tab の列の横スクロールは今までどおり）。モバイルの 1 列の画面は tab バーを持たないので、何も変わらない。
- [ ] AC10: 文書が合っている。`docs/tui-parity.md` の H04m・M12 の Web の列が「あり」になり、`docs/herdr-parity.md` の H04 に、ブラウザ版の tab のドラッグ（使う RPC・同じ workspace の中だけ）が書かれ、`docs/verification.md` に手で確かめる項目がある。


### pane の移動の制限（追加）

「同じ worktree」は、worktree グループの代表を決めるのと同じ鍵（`Workspace.git.worktreeKey`＝その worktree のフォルダを一意に示すパス）が同じこと。判定は移動元と移動先の **workspace** で行う（pane 自身のフォルダは見ない）。

- [ ] AC11: 移動元と移動先の workspace が同じ worktree（`worktreeKey` が同じ）のとき、pane を別の workspace へ移せる（今までどおり）。同じフォルダを開いた 2 つ目以降の workspace（worktree グループの代表でない、サイドバーでは通常の行）との間が、これに当たる。
- [ ] AC12: 移動元と移動先の workspace が別の worktree（同じリポジトリの別の worktree・別のリポジトリ）のとき、`pane.move_to_tab`・`pane.move_to_new_tab` は何も動かさず、`{ok: false, reason: "different_worktree"}` を返す。イベントは 1 つも配られない。
- [ ] AC13: git の判定が無い workspace どうし（管理外のフォルダ・判定がまだ入っていない）は、**開いた場所（`Workspace.cwd`）が同じ**ときだけ移せる。それ以外（場所が違う・片方だけ判定がある）は断る（`different_worktree`）。
- [ ] AC14: 「同じ worktree」と確かめられないときは断る。判定が入った後は、AC11・AC12 のとおりになる（作った直後に断られた相手でも、同じ worktree と分かれば移せるようになる）。
- [ ] AC15: 同じ workspace の中の移動（別の tab へ・新しい tab へ切り出す・分割・置き換え）は、判定に関わらず今までどおりできる。pane の中で `cd` して別の worktree のフォルダへ移ることは、制限しない（今までどおり）。
- [ ] AC16: 制限はサーバにあり、入口に関わらず働く: ブラウザ版・端末版の pane の名前のドラッグ、RPC を直接呼ぶクライアント（古い画面・スクリプト）、別のマシンへの中継（そのマシンのサーバが断る）。pane が workspace をまたぐ RPC は `pane.move_to_tab`・`pane.move_to_new_tab` の 2 つだけで、ほかに抜け道が無い。
- [ ] AC17: 新旧の組み合わせで壊れない。断るときの応答は、今ある「何も起きなかった」の形（`ok: false`）に `reason` を足しただけで、古い画面・古い端末版は今までどおり「何もしない」。新しい画面・端末版が古いサーバ（`worktreeKey` を配らない・断らない）へ送ると、今までどおり通る（画面は、`worktreeKey` が無い相手を自分では断らない）。
- [ ] AC18: 落とせる相手が少なくなるので、落とす前に分かるようにする。ブラウザ版は、pane の名前のドラッグが始まった時点で、**落とせない workspace の行を全部薄くする**（落とせる行と、自分の workspace の行はそのまま）。落とせない行の上では、落とせる先の強調（破線）を出さず、既存の「落とせない行」の見た目（点線と not-allowed のカーソル）にする。そこで離すと、何も送らず、「別の worktree の workspace へは移せません（同じフォルダを開いた workspace へだけ移せます）」と知らせる。端末版は、落とせない行に強調を出さず、離すと同じ文言で知らせる。サーバが断った（`reason` 付き）ときも、同じ文言で知らせる。
- [ ] AC19: 文書が合っている。`docs/herdr-parity.md` の H41・`docs/tui-parity.md` の H41・W03・`docs/tui.md`「マウス」・`docs/sodactl.md` の pane の移動に触れている箇所・`docs/verification.md` に、別の workspace へ移せるのは同じ worktree の間だけ（管理外・判定前は開いた場所が同じときだけ）・pane の中の `cd` は対象外・断るときの応答、が書かれている。以前の作業（20260924-pane-move-cross-tab）の「サイドバーの workspace の行へ落として移す」は、ほとんどの相手で落とせなくなった、と分かる書き方にする。

## 相互作用の受け入れ基準（UI を伴う work のみ）

- [ ] AC-I1 開始 / 終了: ドラッグは、tab の上で左ボタンを押したまま 6px 以上動かしたときに始まる（pane の名前・workspace の行と同じ閾値）。右ボタン・中ボタン、「＋」のボタン、右端の帯からは始まらない。離す・取り消すと終わる。
- [ ] AC-I2 確定 / 取り消し: 線が出ている位置で離すと確定する。`Esc`・tab バーの外で離す・順が変わらない位置で離す・ポインタの取り消し（`pointercancel`）は取り消しで、順も、選ばれている tab も変わらない。`Esc` で取り消した後にボタンを離しても、tab は切り替わらない。
- [ ] AC-I3 キーボードだけで完結するか: 同じ並べ替えは、既存のキー操作 `move_tab_previous`・`move_tab_next`（既定のキーなし。設定で割り当てる）だけでできる。この作業でキー操作は足さず、変えない。tab のボタンに Tab キーで止まって Enter・Space で切り替える操作も今までどおり。
- [ ] AC-I4 フォーカスの行き先: 確定すると、つかんだ tab が選ばれ（表示が切り替わり）、その tab のフォーカス中の pane の端末にフォーカスが移る。取り消すと、選ばれている tab は変わらず、選ばれている pane の端末へフォーカスが戻る（tab のボタンに残らない。ダイアログが開いたことによる取り消しでは、フォーカスはそのダイアログのもの）。
- [ ] AC-I5 既存の操作を妨げないか: 6px 未満で離したときは今までどおりのクリック（tab の切り替え。`tab.focus` を 1 回）で、ドラッグの後に切り替えが二重に起きない。右クリックのメニュー・tab バー上のホイールでの切り替え・「＋」・tab が 1 個のときの自動非表示は今までどおり。ドラッグ中のキーは端末へ届かない（`Esc` を含む）。

pane の移動の制限（追加）は、既存の pane の名前のドラッグの「落とせる先」を狭めるだけで、開始・取り消し・キーボード・フォーカスの決まりは変えない（AC18 が落とせない先の見せ方と知らせ方を定める。断られたとき、表示もフォーカスも動かない。行を薄くするのはドラッグ中だけで、離す・取り消すと戻る）。
