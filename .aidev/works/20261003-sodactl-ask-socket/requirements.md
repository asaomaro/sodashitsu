# 要件: pane の中のプログラム向けのログイン不要の受け口を作り、sodactl ask をログインなしで使えるようにする

## 背景 / 課題

`sodactl ask`（20261002-sodactl-ask）は、ほかの sodactl のコマンドと同じ `/ws` の接続（`sodactl login` で保存した session cookie）を通す。
pane の環境には token・cookie を入れない方針なので、**pane の中で一度も `sodactl login` していないと `unauthenticated`（終了コード 1）で失敗する**。

2026-10-03 に、Claude Code のスキル ask-form（`ask.py`）が pane の中で `sodactl ask` を呼ぶようにしたところ、未ログインのため失敗して
単独のウィンドウ（`ask.py` が動いているマシンの画面）に切り替わった。利用者は理由に気づけなかった。利用者の指摘:
「ask-form を通すだけなのにログインが必要なのはなぜか。AskUserQuestion の拡張に過ぎない」。

ask に限れば、ログインは安全の境界になっていない:

- ask が出来ることは「質問を出して回答を受け取る」だけ。pane のプログラムは、もともと利用者と同じ権限で動いている。
- 同じ利用者のプロセスは状態ディレクトリの `local-auth.json` を読める（端末版 `soda` はこれで token なしに繋ぐ。`docs/tui.md`「認証」）。
- なりすましは「どの pane からの質問か」の固定表示、出しすぎは同時数の上限（総数 32・接続あたり 8・1 つの pane に同時に 1 つ。超えると `ask_busy`）で防いでいる（`docs/sodactl.md`「質問のフォーム」）。認証とは別の仕組み。

一方、`/ws` の接続は pane のシェルを操作できる権限なので、sodactl 全体をログイン不要にする（未ログインなら `local-auth.json` で自動ログインする）と、
pane のプログラムが黙ってその権限を取れるようになる。利用者はこの案（B）を採らず、**ログイン不要の専用の受け口**（A）を選んだ。

利用者の追加の指示（2026-10-03・requirements の途中）: 「今後も特別な権限が必要ないものに対しては認証不要にする可能性があるので、汎用的な口にしておいて」。
受け口は ask 専用に作り込まず、**特別な権限の要らない操作を後から足せる汎用の口**にする。この作業で載せる操作は ask だけ。

既存の似た仕組み: 公式フック連携の report は、pane の環境の `SODA_AGENT_REPORT_SOCKET` が指すローカルの socket
（Linux・macOS・WSL2 は状態ディレクトリの `agent-report.sock`〔0600〕、Windows は名前付きパイプ `\\.\pipe\soda-agent-report-<hash>`）で受けている
（`packages/server/src/agent/AgentReportSocket.ts`・`packages/server/src/config.ts:82-87`）。Windows のパイプの権限の限定は「既知の制約」として未対応（`AgentReportSocket.ts:44-49` のコメント）。

## 目的 / ゴール

pane の中のプログラムが、利用者に一度も `sodactl login` をさせずに `sodactl ask` で質問でき、かつその経路から出来ることが
「自分の pane の質問を出して回答を受け取る」ことだけに限られている状態。加えて、特別な権限の要らない操作を後からその受け口に足すとき、
受け口そのもの（接続・やりとりの形・権限の限定・sodactl 側の使い分け）を作り直さずに済む状態。

（`.aidev/charter.md` は無いので、charter ゴールへの紐づけは省く。）

## ユーザーストーリー

- US1: 利用者として、pane の中のエージェント（Claude Code の ask-form 等）の質問を、ログインの手間なしに自分の見ているブラウザの画面で受けたい。
  なぜなら、質問に答えるだけのことに token を探して打つ理由が無く、未ログインだと別のマシンの画面にウィンドウが出て質問に気づけないから。（受け入れ: AC1, AC2, AC6, AC17）
- US2: 利用者として、ログイン不要の経路が増えても、pane のプログラムに出来ることが増えないでほしい。
  なぜなら、pane の中ではエージェントが任意のコマンドを打つので、認証の要らない経路から pane の操作まで出来ると歯止めが無くなるから。（受け入れ: AC3, AC4, AC5, AC15）
- US3: 既存の使い方（ログイン済み・古いサーバ・`SODACTL_URL` で接続先を変えている）の利用者として、今までどおり動いてほしい。
  なぜなら、版を上げただけで ask が動かなくなると困るから。（受け入れ: AC7, AC8）
- US4: 開発者（と AI エージェント）として、次に「ログイン不要でよい操作」を足すとき、操作を 1 つ登録するだけで済ませたい。
  なぜなら、操作ごとに受け口・環境変数・sodactl の分岐を作ると、権限の限定の検査が操作の数だけ散らばり、どれかで漏れるから。（受け入れ: AC13, AC14, AC16）

## スコープ

### 対象

- サーバ: pane の中のプログラムからの、特別な権限の要らない操作を受ける、ログイン不要のローカルの受け口（汎用の口）。**載せる操作は明示的に登録したものだけ**で、この作業で登録するのは ask だけ。
- sodactl: 受け口に載っている操作のコマンド（この作業では `sodactl ask`）が、その受け口を使えるときは使う（使えないときは今までの `/ws` の経路）。使い分けは操作ごとに書かず共通にする。
- pane の環境: 受け口の場所を pane の環境で知らせる（新しい変数を足すか、既存の変数から決めるかは design）。
- docs（`docs/sodactl.md`「質問のフォーム」「pane の中から使う」・`docs/verification.md`・sodactl の skill ファイル）の更新。

### 対象外

- sodactl のほかのコマンドのログイン不要化（案 B。採らない）。ask 以外の操作を受け口に載せること（どれを載せてよいかの判断は、載せる作業ごとに行う）。
- 既存の公式フック連携の report（`SODA_AGENT_REPORT_SOCKET`）を新しい受け口へ移すこと（相乗り・統合するかは design で決めるが、既存の hook スクリプトの動きは変えない）。
- `sodactl ask` の定義・結果の形・終了コード・対応する型・ブラウザ側のダイアログの変更。
- `--machine` 越しの ask（今までどおり `local` 以外では使えない）。
- ask-form 側（別リポジトリ public_docs の `ask.py`）の変更。
- 公式フック連携の report の socket（`SODA_AGENT_REPORT_SOCKET`）の Windows での権限の限定（既知の制約のまま。ただし新しい受け口が同じ弱さを持ち込まないことは AC5）。

## 機能要件

- pane の中で、`sodactl login` をしていなくても `sodactl ask < spec.json` が質問を出し、結果（`answered`・`cancelled`・`timeout`・`unavailable`）を返す。
- 結果の JSON・終了コード・定義の検査・定義の大きさの上限（`docs/sodactl.md`「サーバ側の上限」）・同時数の上限（総数・pane ごと）・どのブラウザに出るか・「どの pane からの質問か」の固定表示・
  待っている間に呼び出し側が終わったら質問を取り消す挙動は、`/ws` の経路と同じ。
- 受け口が受けるのは、登録された操作だけ（この作業では ask だけ）。登録に無い操作——pane の入出力・workspace／tab／pane の操作・session cookie の発行など——は出来ない。
  `/ws` の RPC をそのまま通す口にはしない（載せるものを 1 つずつ選ぶ。既定は「載っていない」）。
- 受け口のやりとりは、操作の名前・引数・結果（成功／エラーの code）・すぐ返る操作と結果を待つ操作（ask）の両方を、操作を足しても形を変えずに扱える。
- 受け口に載せる操作は「呼び出し元の pane」を対象にする形を基本にし、どの pane からの要求かを操作に渡す（ask の「どの pane からの質問か」と同じ扱い）。
- 版の違い: 受け口はあるがその操作を知らないサーバ（新しい sodactl × 古いサーバ）では、sodactl はそれを見分けて今までの `/ws` の経路へ落ちる。
- 質問の対象は呼び出し元の pane（今までどおり）。実在しない pane への質問は断る。
- 受け口を使えないとき（古いサーバ・受け口の場所が pane の環境に無い・接続できない・`SODACTL_URL`／`--url` で接続先を明示している）は、今までの `/ws` の経路で動く。

## 非機能要件 / 制約

- 受け口に繋げるのは、サーバを動かしている利用者と同じ利用者のプロセスだけ（Linux・macOS・WSL2 はファイルの権限）。
- Windows（ネイティブ）: ほかの利用者が繋げる状態でログイン不要の受け口を開かない。同じ利用者に限れないなら、Windows では受け口を出さず今までの経路のままにする（どちらにするかは design）。
- pane の環境に token・cookie を入れない方針は変えない。
- 名前付き session（`--session`）ごとに受け口が分かれ、別の session の pane を対象にした操作（この作業では質問）を出せない。
- 更新時の引き継ぎ（`soda handoff`）・`soda session stop` の後も、受け口が使える／残骸が残らない（既存の socket と同じ扱い）。
- 受け口への入力は信用しない（大きさの上限・壊れた入力で落ちない・同時数の上限は `/ws` の経路と共通に数える）。

## 完了条件 (受け入れ基準)

- [ ] AC1: `sodactl login` をしていない（`~/.sodactl` にキャッシュが無い・`SODACTL_TOKEN` も無い）pane の中で `sodactl ask` を打つと、その pane を見ているブラウザにダイアログが出て、決定すると `{"status":"answered",…}`（終了コード 0）が返る。
- [ ] AC2: 同じ条件で、キャンセル → `cancelled`、`--timeout` の超過 → `timeout`、質問を出せるブラウザが 1 つも無い → `unavailable`、対応していない型 → `unavailable`（どれも終了コード 0）。`/ws` の経路と同じ結果になる。
- [ ] AC3: 受け口に、登録に無い操作（pane への入力・workspace の作成など `/ws` の RPC の名前）を送っても、何も行われない（pane に入力が届かない・workspace が増えない）。返るエラーは AC14。
- [ ] AC4: 受け口経由の質問も、ダイアログの最上部に「どの pane からの質問か」が出る。実在しない pane を名乗ると断られる（`not_found`）。総数 32 と「1 つの pane に同時に 1 つ」の上限は `/ws` の経路の質問と合わせて数える（「接続あたり 8」に当たる数え方は未確定事項。design で決める）。
- [ ] AC5: 受け口はサーバと同じ利用者だけが繋げる（Linux・macOS・WSL2 では、ほかの利用者が受け口に繋げない権限になっている。確かめ方は design で決めた受け口の形に合わせる）。Windows（ネイティブ）では、ほかの利用者が繋げる形のログイン不要の受け口が開かない——同じ利用者に限れているか、受け口を出していないかのどちらか。
- [ ] AC6: 待っている間に `sodactl ask` のプロセスが終わる（Ctrl+C・kill）と、質問は取り消されてブラウザのダイアログが閉じる。
- [ ] AC7: 受け口を使えないとき（古いサーバ・受け口の場所が環境に無い・接続できない）は、ログイン済みなら今までどおり `/ws` の経路で質問が出る。未ログインなら今までどおり `unauthenticated`（終了コード 1）。
- [ ] AC8: `--url`・`SODACTL_URL` で接続先を明示しているときは受け口を使わず、今までどおりの経路・歯止め（別のサーバへ向けると `caller_pane_unknown`）で動く。
- [ ] AC9: 受け口への壊れた入力（JSON でない・上限を超える大きさ・途中で切れる）でサーバが落ちず、ほかの質問・接続に影響しない。
- [ ] AC10: 名前付き session のサーバでは受け口が session ごとに別で、ある session の pane から、受け口経由で別の session の pane を対象にした操作（質問）を出せない。
- [ ] AC11: `soda handoff` の後も、ログインなしの `sodactl ask` が動く。サーバを止めた後に受け口の残骸で次の起動が失敗しない。
- [ ] AC12: `docs/sodactl.md`・sodactl の skill ファイルから「ask にはログインが要る」という記述が無くなり、ログイン不要の条件と、今までの経路に落ちる条件が書かれている。受け口に操作を足すときの決まり（載せてよい操作の条件・登録の仕方）が docs にある。`docs/verification.md` に、ログインなしの ask を実物で確かめる手順がある。
- [ ] AC13: 受け口の操作は登録の一覧で決まり、テスト用の操作を 1 つ登録するだけで、受け口・sodactl の接続の部分を変えずにその操作を呼べる（単体テストで、ask 以外のすぐ返る操作を登録して呼び、結果とエラーの code が返ることを確かめる）。
- [ ] AC14: 登録に無い操作の名前を送ると、決まった code のエラーが返り、sodactl はそれを「受け口がその操作を知らない」として見分けて `/ws` の経路へ落ちる。
- [ ] AC15: 受け口を足した後も、pane の環境に token・cookie・`local-auth.json` の秘密が入っていない（pane の環境の一覧で確かめる）。
- [ ] AC16: 受け口は、要求がどの pane からのものかを操作に渡す（AC13 のテスト用の操作が、呼び出し元の pane の id を受け取れる）。
- [ ] AC17: ログインなしの pane の中で、誤った定義（JSON でない・`questions` が空・上限の超過）を `sodactl ask` に渡すと、`/ws` の経路と同じく使い方の誤り（終了コード 2）になる。

## 未確定事項 / 確認したいこと

- 受け口に載せてよい操作の条件（「特別な権限が要らない」の線引き）を docs にどう書くか。
- 受け口を新しい socket にするか、既存の `agent-report.sock` に相乗りするか（既存は 1 接続 1 メッセージ・返事なし・4096 バイトまで。ask は返事を待ち、定義は 256 KiB まで）。
- Windows の扱い（名前付きパイプを同じ利用者に限れるか。限れないなら受け口を出さない）。
- 回答待ちの持ち主: `/ws` の経路は「接続」に質問を紐づけている（接続あたり 8・接続が切れたら取り消し）。受け口の接続をどう数えるか。
- 受け口が使えずに `/ws` へ落ちたことを、利用者に知らせるか（落ちる条件そのものは機能要件・AC7・AC14 で確定）。
- pane の環境の変数の名前（新しく足すか、既存の変数から場所を決めるか）。
