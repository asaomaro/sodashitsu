# 要件: サーバ側の大きさと入力の上限

## 背景 / 課題

backlog（`.aidev/backlog/product-roadmap.md`「サーバ側の大きさと入力の上限」。出典 20260926-pane-observe-control の decisions D6・D13）より。

- **大きさ**: `pane.attach`・`pane.attach_resize`・`client.view` の `cols/rows` は、protocol のスキーマ（`packages/protocol/src/messages.ts`
  の `PaneAttachParams`・`PaneAttachResizeParams`・`ClientViewParams`）が「正の整数」しか見ていない。`wtmctl` は 1〜1000 に絞る
  （`packages/cli/src/sessionStream.ts` の `MAX_STREAM_DIMENSION`）が、生の `/ws` からは `cols: 100000, rows: 100000` のような値が通り、
  サーバはその大きさで PTY とミラー（headless の xterm。`packages/server/src/terminal/Mirror.ts` の `resize`）を作り直す。
  画面の行はその場で確保されるので、1 通の要求でサーバのメモリを食い潰し、**同じサーバの全 pane**（シェル・エージェント）を巻き込んで落としうる。
  SNAPSHOT のフレームは大きさを u16 で運ぶ（`packages/protocol/src/frames.ts` の `encodeSnapshotFrame`）ので、65535 を超えると値が化ける。
- **入力**: INPUT フレームは 1 通 1 MiB までだが（`packages/server/src/ws/WsGateway.ts` の `MAX_INPUT_FRAME_BYTES`）、pane のプログラムが
  stdin を読まないとき、PTY へ書けなかった分はサーバのプロセスの中の書き込み待ちに積まれ続け、上限が無い。`wtmctl pane control` で
  パイプから流し込む（`yes | wtmctl pane control <paneId>` 等）のが容易になり、読まない pane（raw モードで固まった TUI 等）に向けると
  サーバのメモリが際限なく増える。複数ホストの中継（`/ws?machine=`）の先のサーバも同じ。

## 目的 / ゴール

- `/ws`（直接・`?machine=` の中継の先のどちらも）から届く**端末の大きさ**が、サーバのスキーマで決まった範囲の外なら受け付けられず、
  サーバが PTY・ミラーをその大きさで作り直さない状態。範囲は protocol に 1 か所で定義され、サーバ・ブラウザ・wtmctl が同じ値を参照している状態。
- pane が入力を読まなくても、**サーバの中に積まれる入力の量が pane ごとに上限で止まり**、超えた入力は捨てられ、送った側（ブラウザ・wtmctl）が
  その事実を知れる状態。上限の内側の入力（数 MB の貼り付け・流し込み）は今までどおり届く状態。
- ほかの `/ws` の大きさの入力（独自コマンドの popup・報告のトークン・kitty graphics 等）について、上限の有無を確かめ、無いものは同じ考え方で
  埋めるか、後続として記録されている状態。

## ユーザーストーリー

- US1: サーバの運用者として、壊れた・悪意のあるクライアントが巨大な `cols/rows` を送っても、サーバが落ちず他の pane が影響を受けないようにしたい。
  なぜなら、1 つのサーバに作業中のシェル・エージェントが全部載っており、サーバが落ちると全部失うから。（受け入れ: AC1, AC2, AC3, AC4, AC14, AC15）
- US2: `wtmctl pane control` でパイプから入力を流し込むスクリプトの作者として、読まない pane に向けてしまってもサーバを巻き込まず、
  入力が捨てられたことを stderr で知りたい。なぜなら、黙って捨てられると流し込みの欠けに気づけず、捨てられなければサーバのメモリが尽きるから。
  （受け入れ: AC5, AC6, AC7, AC8）
- US3: ブラウザの利用者として、今までどおり大きなテキストを貼り付けられ、画面の大きさも今までどおり合わせられたい。固まった pane に打ち込んだときは、
  入力が届いていないことを知りたい。なぜなら、上限のために普段の操作が壊れては困り、捨てられた入力に気づかず打ち続けたくないから。
  （受け入れ: AC5, AC7, AC9）
- US5: エージェントを別のプログラムから操る自動化の作者として、`agent.prompt`・`agent.send_keys`・`agent.start` が読まない pane に際限なく積まれず、
  失敗として返ってきてほしい。なぜなら、成功と返って実は積まれているだけだと、自動化が待ち続けるか同じ入力を送り直してさらに積むから。（受け入れ: AC10）
- US4: 開発者・レビュアとして、上限の値と、それを選んだ理由（壊れる具体例）と、見送った課題を文書で知りたい。なぜなら、上限は将来の変更で
  緩め・締めの判断が要り、その根拠が無いと判断できないから。（受け入れ: AC11, AC12, AC13）

## スコープ

### 対象

- protocol: 端末の大きさの上限（1 辺と面積）の定数と、それを使う `cols/rows` のスキーマ（`client.view` の `visible`・`pane.attach`・
  `pane.attach_resize`）。`client.view` の `visible` の件数の上限。入力を捨てたことを伝えるエラーコード。
- server: pane ごとの入力の書き込み待ちの量を測り、上限を超える INPUT フレームを捨て、送った接続へ知らせる（間引いて）。サーバのログにも間引いて残す。
  エージェントへの入力（`agent.prompt`・`agent.send_keys`・`agent.start` の書き込み）も同じ上限で断る。
- web: 大きさを測る所で上限に丸める（上限の外の `client.view` を送って要求ごと断られないように）。新しいエラーコードの日本語の文言。
- cli: `wtmctl pane control` が入力を捨てた知らせを stderr に出す。`wtmctl pane attach` が大きさを上限に丸める。
- ほかの `/ws` の大きさの入力の点検と、その結果の記録（上限済み・今回埋める・後続）。
- 文書（`docs/` の該当箇所・wtmctl の skill ファイルに関係があれば）。

### 対象外

- 入力の**本当の背圧**（pane が読むまで送り手を待たせる。クレジット方式等）——捨てて知らせる方式にとどめる（design で理由を書く）。
- node-pty の書き込みの内部の作り（EAGAIN の再試行の仕方）を変えること——research で見つかれば後続に残す。
- 認証の無い経路の変更（`/ws` は認証の後だけ。上限は認証済みのクライアントの誤り・誤用からサーバを守るもの）。
- E2E テスト・負荷試験（利用者の指示）。

## 機能要件

- `cols`・`rows` は 1 以上・1 辺の上限以下の整数で、`cols × rows` は面積の上限以下。外れた `client.view`・`pane.attach`・`pane.attach_resize` は
  `invalid_params` で断られ、PTY・ミラー・モデルの大きさは変わらない。
- pane ごとの「PTY へまだ書けていない入力の量」がサーバの中で分かる。INPUT フレームを受けたとき、その量＋フレームの長さが上限を超えるなら、
  そのフレームを丸ごと捨てる（途中まで書かない）。
- `client.view` の `visible` の件数は上限以下（外れたら `invalid_params`）。
- 捨てたとき、送った接続へ `client.error`（新しいエラーコード・どの pane か）を送る。同じ接続・同じ pane への知らせは一定の間隔に 1 回まで。
  知らせは「不正なフレーム」の数（10 秒 10 回で接続を閉じる）に数えない。サーバのログにも間引いて 1 行残す（ログの行数も上限の内に留める）。
- エージェントへの入力（RPC。`agent.prompt`・`agent.send_keys`・`agent.start` の書き込み）は、上限を超えるなら書かずに新しいエラーコードで失敗を返す。
- 端末への問い合わせへのミラーの応答（サーバが自分で書くもの）は上限で捨てない。

## 非機能要件 / 制約

- 上限の内側では今までの振る舞いを変えない（普段のキー入力・1 MiB までの貼り付け・数 MB の流し込みは届く）。
- 上限の判定は入力 1 通あたり軽い（書き込み待ちの量を数えるのは待ち行列の長さに比例してよいが、普段は空）。
- Linux・macOS・Windows のどれでも起動と入力を壊さない。書き込み待ちの量が測れない環境では、今までどおり（捨てない）に倒す。
- 負荷試験・busy loop の並走・E2E はしない（共有マシン。利用者の指示）。読まない pane に 1 回だけ書く機能テストはよい。

## 完了条件 (受け入れ基準)

- [ ] AC1: `client.view`・`pane.attach`・`pane.attach_resize` に 1 辺の上限を超える `cols` または `rows`（または 0・負・非整数）を渡すと
  `invalid_params` になり、pane の大きさ（モデル・PTY・ミラー）が変わらない（サーバのテストで確かめる）。
- [ ] AC2: 1 辺は上限内でも `cols × rows` が面積の上限を超えると `invalid_params` になる。上限ちょうどは通る。
- [ ] AC3: `client.view` の `visible` の件数が上限を超えると `invalid_params` になる。
- [ ] AC4: 上限の定数は `@wtm/protocol` に 1 か所で定義され、サーバのスキーマ・web の大きさの計算・wtmctl の attach が同じ定数を参照する。
  web は測った大きさを上限に丸めて送る（丸めのテスト）。
- [ ] AC5: 入力を読まない pane（raw モードで読まない子プロセス）に上限を超える入力を送ると、上限を超えたフレームは PTY に書かれず、
  サーバの中の書き込み待ちは上限以内に留まる（実物の node-pty の PTY に 1 回だけ書く機能テスト、または偽の PTY のテスト）。
- [ ] AC6: 捨てたとき、送った接続に `client.error`（新しいコード・pane の id）が届き、同じ pane への知らせは間隔の内では 1 回だけ。
  接続は閉じられない（不正なフレームの数に数えない）。サーバのログの行は間引かれる（窓ごとの上限を超えて書かない）。
- [ ] AC7: 上限の内側の入力（1 MiB のフレームを含む）は今までどおり届く（既存のテストが通り、上限ちょうどの境界のテストがある）。
- [ ] AC8: `wtmctl pane control` は、制御中の pane について入力を捨てた知らせを受けたら stderr に理由を出す（stdout の記録は変えない）。
- [ ] AC9: ブラウザは新しいエラーコードを日本語の文言で知らせる（`clientError.ts` の表）。
- [ ] AC10: エージェントへの入力（`agent.prompt`・`agent.send_keys`・`agent.start` の書き込み）は、書き込み待ちが上限を超えている pane では
  書かずに新しいコードで失敗する。
- [ ] AC14: 端末への問い合わせへのミラーの応答（サーバが自分で書くもの）は、書き込み待ちが上限を超えていても捨てられない。書き込み待ちの量が
  測れない PTY（量を返さない実装）では、今までどおり捨てない。
- [ ] AC15: 中継（`/ws?machine=`）の先のサーバも同じ判定で断る（中継は中身を解釈せず先へ渡すだけで、先のサーバの `/ws` の処理が同じコードである
  ことを research で確かめ、記録する）。`wtmctl pane attach` は手元の端末の大きさを上限に丸めて送る（丸めのテスト）。
- [ ] AC11: ほかの `/ws` の大きさの入力（popup の大きさ・報告のトークン・kitty graphics・`pane.subscribe` の `scrollbackLines`・中継の上流）を点検し、
  上限の有無と扱いを research/decisions に記録し、今回埋めないものは backlog の `[ ]` 行に残す。
- [ ] AC12: 上限の値・選んだ理由（壊れる具体例）・捨てる方式を選んだ理由が decisions.md にあり、利用者向けの文書（docs）に上限と振る舞いが書かれている。
- [ ] AC13: `pnpm -s build`・`pnpm -s typecheck`・`pnpm -s test` が通り、`aidev smoke` が通る。変更した判定には変異による負の確認がある。
