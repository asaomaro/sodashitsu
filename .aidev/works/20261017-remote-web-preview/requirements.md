# リモートWebプレビューの要件

## 目的と今回の範囲

操作側AのSodashitsuから開発側Bの端末・エージェントを操作してWebアプリを開発し、Bのloopbackで動く実アプリをA側Sodashitsuのアプリ画面で操作・検証する。ブラウザが動く端末CはAと同じとは限らない。

初回依頼は調査・設計まで。続く作業継続依頼により専用worktreeを作成し、エージェントがポート設定・画面起動も行える仕様を追加した。ユーザーはPC側の補助プログラムを許可したため、この方式を採用し、入口PoCからCLI・外向き転送・ブラウザUIまでの初期実装を進めた。実装範囲と未検証部分はdesign.md/test-result.mdに分けて記録する。

- worktree: `/workspaces/sodashitsu-remote-web-preview`
- branch: `feature/remote-web-preview`
- 起点: `94f53f12`（mainの追跡済み内容のみ。元worktreeの未コミット変更は含めない）
- 初回調査: [research.md](research.md)。調査時の元worktreeは未コミット変更を含んでいたため、実装時はこのworktreeの現物を正とする。

## 必須要件

1. BのWebアプリportを外部公開しない。ルーター/Firewallの開放、個別の公開サービス設定を不要にする。B発の外向き操作委譲しか成立しない構成を標準対象にする。
2. HTTP/WSを実ブラウザへ転送する。GUI映像配信とは別機能。SSH/外向き委譲を利用し、公開済みB HTTPS経路は追加adapterとする。
3. 任意URL proxyを提供しない。利用者/許可されたエージェントが明示登録したBのliteral loopback address + portだけへ接続する。
4. 管理画面と検証アプリのorigin・資格情報を分離する。異なるアプリのcookie/storage/SWと検証セッションを混ぜない。別port・path・兄弟subdomainだけで達成したと扱わない。
5. 通常のroot配信を優先する。相対/絶対path、API、module/CSS/assets、redirect/cookie、WS/HMR、SSE/SSR streaming、upload/downloadの成立範囲を記録する。HTMLの一括書換えで完全互換を約束しない。
6. 登録をworkspaceと関連付け、起動paneを記録する。複数PJ/app/machine/clientを識別し、誤った対象の画面を開かない。
7. エージェントからサーバー起動・port登録・画面起動・状態確認・更新・停止まで操作できる。利用者が毎回portを手入力する運用にしない。
8. 登録/転送停止/登録削除/開発プロセス停止を分ける。再起動・再接続で許可が勝手に広がらず、入力/POSTを再送しない。失効で長寿命streamも止める。
9. 遅いプレビューが端末操作を継続的に止めない。上限、channel別credit、timeout、cancel、端末優先を設ける。共有TCPによる影響は測定する。

## エージェントによる利用体験

想定会話: 利用者が「このPJのWebアプリを直して、画面を開いて」と依頼する。エージェントは既存pane/コマンド実行機能で開発サーバーをloopback起動し、実際のportを確認して、そのpaneからプレビュー登録とopenを呼ぶ。利用者はA側Sodashitsuのアプリ画面で操作する。

- `SODA_PANE_ID`等の既存caller情報からB側workspace/tab/paneを解決し、環境変数の自己申告だけで別machineへ登録しない。
- 開発サーバーの起動方法はPJごとに異なる。初期版では任意shellコマンドを保存・自動実行する汎用ランチャーを新設せず、既存のpane/agent機能を使う。
- port自動加算を行う開発サーバーでは、エージェントが実際のportを読み取って登録する。strict-portオプションが使える場合は優先する。port scanによる自動公開はしない。
- 名前を指定した再実行で登録を重複させない。同じpane・workspaceの登録を明示的に更新するupsertを提供する。port変更はgenerationを更新して旧転送を閉じる。
- openはBでOSブラウザを起動する意味ではない。該当paneを操作しているA側の認証済みブラウザへ、Sodashitsu内のプレビューを開く要求を送る。
- ブラウザがない、複数候補、補助機能がない、方式未対応、失効、到達不可を区別してJSONで返す。全利用者の画面を無条件に開いたり、サーバー全体の最後のフォーカスを推測したりしない。
- open要求受付、画面作成、アプリ到達、表示確認、アプリ機能の正しさを区別する。クロスorigin iframeのloadイベントだけで正常表示・動作確認済みにしない。
- pane内のエージェントには可能ならログイン操作なしの導線を用意するが、pane.sockの既存安全境界を変更しない。登録とopenの権限は設計書の二段階方式とする。

## 未確定・確認待ち

1. 解決済み: ユーザーがPC側の補助プログラムを許可。初期対象はPCのブラウザ端末C。スマホ対応は後段とする。
2. iframeへの埋め込みを必須とするか。ブラウザの制約があるアプリは別タブで検証できる範囲を許容するか。
3. 複数利用者は同じSodashitsu権限を信頼して共有するか。相互に機密を隔離するprincipal/ACLが必要か。

ブラウザ側のローカルネットワークアクセス許可が必要な場合は、標準のブラウザ許可を利用者へ案内する。エージェントからのopenのために許可を迂回しない。PC補助プログラムの許可をブラウザの自動許可と同一視しない。

## 対象外

親ペインのTailscale設定、別ペインのVSCode GUI配信、元worktreeの未コミット変更、外部公開・外部port開放・PR/merge。特定トンネル製品への依存を導入しない。worktreeの依存関係は既存lockfileとローカルstoreからofflineで準備し、ブラウザや証明書のシステムへの追加導入は行っていない。

## 完了基準

調査・設計の完了は、方式の比較と未確定事項、CLI/ブラウザ選択/権限/失効/転送の契約、段階的PoCと受入基準がreview可能な文書になっていること。機能実装の完了は別途、実ブラウザで外向き経路の転送とエージェントの登録→openが通り、独立レビュー・関連テストが通った時点とする。
