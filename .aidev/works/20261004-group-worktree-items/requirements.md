# 要件: グループのメンバーを「項目」（workspace か worktree グループ丸ごと）にする

## 背景 / 課題

サイドバーの workspace のまとまりには 2 種類ある（`20260923-workspace-grouping`）。

- **worktree グループ**（自動）: 同じ git の共通ディレクトリを持つ workspace が 2 つ以上あると束ねる。herdr と同じ動き。保存しない。
- **グループ**（手動。今の呼び名は「手動グループ」）: 利用者が名前を付けて任意の workspace を束ねる。Sodashitsu 独自。保存する。

今の決まりは「手動が優先」で、所属を workspace ごとに持つ。このため次の分かりにくさがある（`packages/client-core/src/workspace/workspaceGrouping.ts` の `autoGroupsOf`・`groupedWorkspaceRows`、`packages/server/src/session/SessionModel.ts` の `linkedWorktreeGroupMembers` で確認）。

- worktree の workspace を 1 つだけグループへ入れると、同じリポジトリの workspace がサイドバーの 2 か所に分かれる。つながりを示す印は無い。
- 本体（linked worktree でない方）をグループへ入れると、残った worktree は束ねられず、ばらばらの行になる（worktree グループが黙って消える）。
- グループの中では、同じリポジトリの本体と worktree の関係が見えない（平らに並ぶ）。
- グループか worktree グループかを示す印が無い（先頭の行の作りが違うだけ）。
- 本体を閉じるときの「worktree も一緒に閉じる」は、グループに入れた workspace を対象から外す。
- 端末版（引数なしの `soda`）には、worktree グループを折りたたむ入口と、グループ全体のドラッグが無い（`docs/tui-parity.md` は「対応」と書いているが、実装が見当たらない。research.md「F7 端末版」）。

利用者は、作業の単位をフォルダのような構造で扱いたい。次の作業（連携のグラフの単位を「サイドバーの一番上のまとまり」にする）の前提として、サイドバーのまとまりを「分かれない・黙って消えない」形に固める必要がある。

## 目的 / ゴール

- worktree グループが、git が決める **1 つの項目**として常にまとまって見え、利用者の操作で分かれたり消えたりしない状態。
- 利用者が作るグループに、通常の workspace と worktree グループ（丸ごと）を入れて、作業の単位として束ねられる状態。
- グループと worktree グループが、見た目で区別できる状態。
- 同じリポジトリの worktree を後から開いても（エージェントが作った場合を含む）、利用者が何もしなくても同じ worktree グループ・同じグループに入っている状態。
- ブラウザ版と端末版で、同じ並び・同じ決まり・同じ操作ができる状態。

charter ゴール: `.aidev/charter.md` は無い（紐づける charter はない）。

## ユーザーストーリー

- US1: Sodashitsu の利用者として、同じリポジトリの本体と worktree が、グループに入れても入れなくても必ず 1 つのまとまりとして見えてほしい。なぜなら、どれが同じ作業のフォルダかを探さずに済み、まとまりが黙って消えて混乱しないから。（受け入れ: AC1, AC2, AC3, AC9）
- US2: 同じ利用者として、複数のリポジトリや git 管理外のフォルダを、1 つの仕事のまとまりとしてグループに束ねたい。なぜなら、仕事の単位で折りたたみ・並べ替え・（次の作業で）グラフを 1 枚にできるから。（受け入れ: AC4, AC5, AC6, AC7）
- US3: 同じ利用者として、エージェントや自分が後から開いた worktree が、自動で正しい場所に入ってほしい。なぜなら、毎回グループへ入れ直す手間が無くなるから。（受け入れ: AC8, AC10, AC11）
- US4: 同じ利用者として、グループと worktree グループを一目で見分けたい。なぜなら、どれが自分で作ったまとまりで、どれが git の構造かで、できる操作が違うから。（受け入れ: AC12）
- US5: 端末版の利用者として、ブラウザ版と同じ並びと操作を使いたい。なぜなら、同じサーバを 2 つの画面から見たときに、まとまりが食い違うと混乱するから。（受け入れ: AC15, AC16）
- 互換性・移行・文書・回帰テストの AC（AC13, AC14, AC17, AC18）は、特定のストーリーに紐づかない制約由来の基準。

## スコープ

### 対象

- サーバ: グループの所属の持ち方（項目単位）、所属の保存、既存データの移行、`group.*` と `workspace.move`／`workspace.move_to`／`workspace.close` の意味の変更、リポジトリの判定が決まった・変わったときの所属の決め直し。
- 並びの計算（ブラウザ版・端末版が共有する純関数）と、サーバ側の同じ判定。
- ブラウザ版のサイドバー: 3 段の描画、種類の印、ドラッグ、右クリックのメニュー、キーボードの並べ替え、折りたたみ、畳んだサイドバーでの見え方。
- 端末版のサイドバー: 上と同じ並び・印・メニュー・並べ替えに加え、**worktree グループの折りたたみの入口**と**グループ・worktree グループ全体のドラッグ**。
- 呼び名: 利用者が作るまとまりは「グループ」、git のまとまりは「worktree グループ」（画面の文言・文書）。
- E2E（グループ・並べ替え・worktree グループの基本の一巡）と、文書（`docs/herdr-parity.md`・`docs/tui-parity.md`・`docs/tui.md`・`docs/verification.md`・`docs/machines.md`）。

### 対象外

- 連携のグラフの単位の変更（次の作業。この work は前提を整えるだけ）。
- グループの入れ子（1 段だけ）。タグ・ラベルによる絞り込み。
- worktree グループの判定そのものの変更（herdr 準拠のまま: 先頭の pane が今いる場所の git の共通ディレクトリ。2 つ以上で束ねる。本体が先頭。本体が開かれていなければ最初に開いたものが先頭）。
- 別のマシンの workspace の行のグループの表示（`docs/machines.md` の backlog のまま）。
- モバイルの pane 選択・移動先の一覧（今も平らな一覧。変えない）。
- `sodactl` へのグループのコマンドの追加（今も無い）。
- worktree グループの中の並べ替え（今までどおり開いた順で固定）。

## 機能要件

- F1 **項目**: サイドバーの一番上の並びは「項目」の列とする。項目は (a) グループ、(b) グループに入っていない worktree グループ、(c) グループに入っていない通常の workspace。グループの中身も項目（worktree グループか通常の workspace）。グループの中にグループは入らない。
- F2 **worktree グループは分けられない**: worktree グループの中の workspace を、個別にグループへ入れる・外す・別のグループへ移すことはできない。グループへの出し入れは worktree グループ丸ごとで行う。workspace を**閉じる**のは今までどおり個別にできる。
- F3 **所属はリポジトリ単位**: git 管理下の workspace の所属は、リポジトリ（git の共通ディレクトリ）に対して持つ。workspace が 1 つしか開いていないリポジトリでも同じ。git 管理外の workspace の所属は workspace に対して持つ。
- F4 **自動で入る**: 同じリポジトリの workspace を新しく開く（worktree を作る・開く・エージェントが `sodactl workspace create` で作る）と、リポジトリの判定が決まった時点で、同じ worktree グループ・同じグループに入る。利用者の操作は要らない。
- F5 **覚えている**: あるリポジトリの workspace を全部閉じても、所属は残る。同じリポジトリを開き直すと、同じグループに戻る。グループを削除したときは、そのグループへの所属を消す。サーバの再起動をまたいで残る。開いている workspace が 1 つも無いリポジトリの所属は画面に出ない（見る・外す入口は作らない。グループの削除で消える）。
- F6 **移った先に従う**: 先頭の pane が `cd` して別のリポジトリへ移り、判定が変わったら、その workspace は移った先のリポジトリの worktree グループと、そのリポジトリの所属するグループに入る（今の worktree グループの動きと同じ。herdr 準拠）。
  - 移った先のリポジトリに所属が無ければ、グループの外へ出る（移った先に従う）。
  - git 管理外へ移ったら、移る前に入っていたグループに、通常の workspace として残る（移った先に「どこのもの」という手掛かりが無いので、場所を変えない。この workspace の所属は workspace 単位になる）。
  - workspace 単位の所属を持つ workspace（管理外、または判定がまだ付いていない新しい workspace）に、初めてリポジトリの判定が付いたとき: そのリポジトリに所属があればそれに従う。無ければ、その workspace の所属をリポジトリの所属にする（グループへ入れた直後に判定が届いても、黙ってグループから出ない）。
- F7 **判定できない間は変えない**: リポジトリの判定が取れない間は、直前の判定・並び・所属を保つ。
  - 「git 管理外」と確定するのは、確認が成功して git の作業ツリーでないと分かったときだけ（コミットが 1 つも無いリポジトリは、今までどおり管理外として扱う）。確認の時間切れ・例外は「取れない」として扱い、何も変えない。
  - 起動直後（まだ確認していない間）は、**停止する前と同じ** worktree グループの束ねとグループの所属で並ぶ。そのために、workspace ごとの直前の判定（どのリポジトリか・本体か）を保存する。最初の確認が届いたら、その結果に合わせる。
- F8 **worktree グループ丸ごとの操作**: 画面では、worktree グループの先頭の行から始めた操作も、子の行から始めた操作も（メニュー・ドラッグ・キーボードの並べ替え）、すべて worktree グループ全体に対して働く。子だけが動く操作は画面に無い。
  - 入口（メニュー）: グループに入っていない項目には「グループへ追加…」、入っている項目には「別のグループへ移す…」「グループから外す」。「新しいグループを作る…」は、その項目を新しいグループへ入れる（すでに別のグループに入っていれば、そこから移る）。
  - 「受け付けない」のは、落とし先が正しくない場合（グループの外と中をまたぐ・worktree グループの内側へ落とす・グループの中へグループを落とす）で、何も変えずに、落とせないことが見た目で分かり、理由を知らせる。
- F9 **並べ替え**: 項目の並べ替え（ドラッグ・キーボード）は、グループの外では一番上の項目どうし、グループの中ではその中の項目どうしで行う。グループの外からグループの中へ（またはその逆へ）は、並べ替えでは移らない（出し入れはメニューの操作で行う）。グループそのものも項目として並べ替えられ（ドラッグ・キーボード）、**グループは中身と無関係に自分の位置を持つ**（空でも・中身が全部閉じていても位置が変わらない）。キーボードの並べ替えは端で止まる（巡回しない）。
- F10 **一緒に閉じる**: 本体を閉じるときの「worktree も一緒に閉じる」は、グループに入っている worktree グループでも使える。
- F11 **種類の印**: グループの先頭の行と、worktree グループの先頭の行に、種類が分かる印を付ける（色だけに頼らない）。畳んだサイドバー（ブラウザ版）でも区別でき、読み上げ（支援技術）にも種類が伝わる。画面の文言は、利用者が作るまとまりを「グループ」、git のまとまりを「worktree グループ」と呼ぶ。
- F12 **折りたたみ**: グループと worktree グループは、それぞれ折りたためる。グループを畳むと、中の worktree グループも隠れる。畳んでいる間も、今いる workspace の行は見える（今までどおり。グループを畳んでいて、今いる workspace が中の worktree グループの子なら、その子の行だけが見える）。
- F13 **既存データの移行**: リポジトリごとに行う。そのリポジトリの所属がまだ決まっていない状態で、そのリポジトリの workspace が初めて判定されたとき、開いている同じリポジトリの workspace のうち**本体の所属**をリポジトリの所属にする（本体がグループに入っていなければ、所属なし＝worktree もグループの外）。本体が開かれていなければ、最初に開いた workspace の所属にする。本体の判定がまだ取れていない間は決めず、取れた時点で決める。一度決めたリポジトリの所属は、移行では書き換えない（何度走っても同じ結果）。単独の workspace がグループに入っている場合も、同じ決まりでリポジトリの所属になる。git 管理外の workspace の所属はそのまま。
- F14 **古い画面からの要求**: 読み込み済みの古い画面が、worktree 1 件に対して「グループへ追加」「グループから外す」を送ってきたときは、worktree グループ丸ごとの操作として扱う。worktree グループの一部だけを動かす並べ替えの要求・グループの外と中をまたぐ並べ替えの要求は、何も変えない（エラーにもしない）。古い平らな入れ替え（`workspace.move`）は、項目単位の入れ替えとして扱う。複数の画面からの同時の操作で、古い並びにもとづく要求が届いたときも同じ扱い。
- F15 **端末版**: F1〜F12 と同じ並び・印・決まり・メニューを持つ（F11 の「畳んだサイドバー」は端末版に無いので当てはまらない）。加えて、worktree グループを折りたたむ入口（クリックとキー）と、グループ・worktree グループ全体のドラッグを足す。

## 非機能要件 / 制約

- worktree グループの判定（どの workspace が同じリポジトリか）は、サーバと画面で**同じ 1 つの決まり**を使う（今は同じ判定がサーバと画面に二重にあり、過去に 2 度食い違った。research.md「F5 同じ判定の二重持ち」）。
- 保存の形（`session.json`）は、古い版が読んでも壊れた扱いにならない形で足す（版の番号は上げない。古い版に戻すと、新しい所属は失われるが、起動はする）。
- 並びの変化・所属の変化は、接続しているすべての画面（ブラウザ・端末版）にすぐ届く。
- リポジトリの判定は周期的な確認（5 秒ごと）と、作成直後の即時の確認で決まる（既存の仕組み。変えない）。「自動で入る」は、判定が届いた時点で起きる。
- 字下げは最大 3 段（グループ → worktree グループの先頭 → 子）。幅が狭いときの名前の省略の仕方は design で決める。
- この work の後に行う「グラフの単位」の作業が、「workspace → その workspace の一番上のまとまり」を 1 つの決まりで引けること（その入口を純関数として用意する）。

## 完了条件 (受け入れ基準)

- [ ] AC1: 同じリポジトリの本体と worktree が 2 つ以上開いているとき、グループに入っていても入っていなくても、本体を先頭に 1 つの worktree グループとして並ぶ（F1）。worktree グループの workspace が 1 つに減ると、同じ場所（同じグループの中）に通常の workspace として残り、worktree グループの印が消える（F3）。
- [ ] AC2: worktree グループの子の行で「グループへ追加」「グループから外す」を選ぶと、worktree グループ全体が入る・外れる。「別のグループへ移す…」「新しいグループを作る…」でも全体が移り、リポジトリの所属も移る。子だけが別の場所へ移ることは、メニュー・ドラッグ・キーボードのどの操作でも起きない（F2・F8）。
- [ ] AC3: 本体をグループへ入れても、worktree グループは消えず、全体がそのグループの中に並ぶ（F2・F3）。
- [ ] AC4: グループに、通常の workspace と worktree グループの両方を入れられ、グループの中で項目として並ぶ。グループの中にグループは入れられない。字下げは、グループ → worktree グループの先頭 → 子の 3 段になる（F1・非機能）。
- [ ] AC5: 並び順が「開いた順」のとき、項目の並べ替え（ドラッグ・キーボード）で、一番上の項目どうし・グループの中の項目どうしの順を変えられる。worktree グループは丸ごと動く。グループそのものも並べ替えられ、空のグループ・中身が全部閉じているグループも位置を保つ。キーボードの並べ替えは端で止まる。グループの外と中をまたぐ移動は起きず、落とせないことが見た目で分かる（F8・F9）。
- [ ] AC6: グループを畳むと中の worktree グループも隠れ、worktree グループだけを畳むこともできる。畳んでいても今いる workspace の行は見える（グループを畳んでいて今いる workspace が worktree グループの子なら、その子の行だけ）（F12）。
- [ ] AC7: 本体を閉じるとき、グループに入っている worktree グループでも「worktree も一緒に閉じる」を選べ、選ぶと全部閉じる（F10）。
- [ ] AC8: グループに入っているリポジトリの worktree を新しく開くと、利用者の操作なしに、同じ worktree グループ・同じグループの中に現れる。workspace が 1 つだけのリポジトリに 2 つ目を開いた場合も同じ（F3・F4）。
- [ ] AC9: 確認の時間切れ・例外で判定が取れない間は、直前の表示（worktree グループの束ね・グループの所属・並び）と同じまま変わらない。サーバを再起動した直後（最初の確認が届く前）は、停止する前と同じ束ねと所属で並ぶ。確認が成功して git の作業ツリーでないと分かったときだけ、管理外として扱う（F7）。
- [ ] AC10: グループに入っているリポジトリの workspace を全部閉じ、同じリポジトリを開き直すと、同じグループに戻る。サーバを再起動しても同じ。グループを削除すると、開いている中身（worktree グループはまとまりを保ったまま）が、そのグループのあった位置で一番上の並びへ出る。削除した後に開き直すと、グループの外に出る（F5）。
- [ ] AC11: 先頭の pane が別のリポジトリへ移ると、その workspace は移った先の worktree グループと、そのリポジトリのグループへ移る。移った先のリポジトリに所属が無ければ、グループの外へ出る。git 管理外へ移ると、移る前のグループに通常の workspace として残る。グループへ入れた直後の（判定がまだ付いていない）workspace に判定が届いても、グループから出ない（そのリポジトリに所属が無ければ、その所属がリポジトリの所属になる）（F6）。
- [ ] AC12: グループの先頭の行と worktree グループの先頭の行に、種類の印が付く。印は色だけでなく形・文字でも区別でき、畳んだサイドバーでも区別できる。読み上げ（支援技術）にも種類が伝わる。画面の文言が「グループ」「worktree グループ」になっている（F11）。

## 相互作用の受け入れ基準

- [ ] AC-I1 開く / 閉じる: グループ・worktree グループの折りたたみは、先頭の行の折りたたみの印（クリック・`Enter`／`Space`）で切り替わる。グループの見出しの行は、行のクリックでも切り替わる（今までどおり）。worktree グループの先頭の行のクリックは、その workspace へ移る（今までどおり）。
- [ ] AC-I2 確定 / 取り消し: ドラッグは離した時点で確定し、`Esc`・行の外で離すと取り消す（並びは変わらない）。受け付けない落とし先（グループの外と中をまたぐ・worktree グループの内側・グループの中へグループ）は、何も変えずに、落とせないことが見た目で分かり、理由が知らせで出る。「グループへ追加…」の選択は、選ぶと確定、`Esc` で取り消す。
- [ ] AC-I3 キーボードだけで完結するか: グループを作る・項目を入れる・外す・別のグループへ移す・項目を並べ替える・グループそのものを並べ替える・畳む・worktree グループを畳むが、マウス無しでできる（ブラウザ版・端末版とも）。
- [ ] AC-I4 フォーカスの行き先: メニュー・ダイアログを閉じると、開く前の場所へ戻る。並べ替えの後も、動かした項目にフォーカス（選択）が付いたまま。折りたたみの切り替えの後は、その印にフォーカスが残る（端末版は、選択している行がそのまま残る）。
- [ ] AC-I5 既存の操作を妨げないか: サイドバーの上でのキー・ホイール・ドラッグが端末の pane へ漏れない（今までどおり）。pane を workspace の行へドロップして移す操作・workspace の切り替えのキー・番号での切り替えが、新しい並びの順で今までどおり動く。

## 未確定事項 / 確認したいこと

- 種類の印の具体的な形（アイコン・文字）と、畳んだサイドバーでの出し方。design で決める。
- 所属はリポジトリ → グループの表として保存する（F5 から確定）。未確定なのは、表の形・workspace ごとの直前の判定の保存の形（F7）・画面へ配る形（各 workspace の実効の所属をサーバが計算して載せるか）。design で決める。
- グループが自分の位置を持つ（F9）ための保存の形と、平らな順の中で worktree グループを連続させるか。design で決める。
- キーボードの並べ替え（`workspace.move`）は今、グループを考えない平らな入れ替えで、見た目が変わらないことがある（`20260923-workspace-grouping` の decisions D13 が未解決）。AC5 を満たすために、項目単位の入れ替えに直す。グループそのものをキーボードで動かす入口（見出しの行の選択・メニュー・別のアクション）も含め、やり方は design で決める。
- リポジトリの判定のキーは `path.resolve` だけで決まり、symlink を通った場所・bare・コミットの無いリポジトリ・サブモジュールでの値は確かめていない（research）。所属を保存するキーにするので、design で確かめ方を決める。
- `name` 順のとき、名前順が効く段（一番上／グループの中）と、worktree グループを何の名前で並べるか（先頭の workspace の名前を想定）、そのときの並べ替え操作の扱い（今の動きは追えていない）。design で確かめて決める。AC5 は「開いた順」のときの基準。
- 「管理外と確定」と「取れない」を、今の確認の実装（`rev-parse` の失敗も時間切れも `null`）で区別できるか。design で確かめ、区別できる形に直す。
