> 設計の方針の案（承認の鍵・プロセスの扱い・脅威）は、この work の `decisions.md` に勧める案として残した（確定は、この work の design）。

## 背景 / 課題

表示の面（`sodactl display`）は、pane の中のプログラムが自分で呼ぶ形でしか使えない。「エージェントを問わない拡張」（D1）にするには、pane の中のエージェントとは別に、
**Sodashitsu が起動して動かし続けるプログラム**（拡張）が要る（D3: 別プロセス・NDJSON）。拡張は、リポジトリと一緒に配りたい（D7: プロジェクトの設定も読む）が、
clone しただけで他人のプログラムが自分の権限で動いてはならない（D7: 承認つき）。

## 目的 / ゴール

利用者が設定ファイルに登録した拡張が、サーバの起動・停止・入れ替え（`soda handoff`）に合わせて動き続け、標準入出力の NDJSON で表示の面を出し・操作を受け取れる状態。
リポジトリの中の設定に書かれた拡張は、**利用者がその中身を見て承認するまで 1 度も実行されず**、中身が変わったら承認し直すまで動かない状態。拡張が落ちても・応答しなくても、pane とほかの画面は止まらない状態。

## ユーザーストーリー（案）

- US1: 利用者として、自分の設定ファイルに拡張を 1 行登録すれば、サーバを起動するたびに動いてほしい。なぜなら、毎回手で起動したくないから。
- US2: リポジトリの作者として、リポジトリの中の設定に拡張を書いて、チームに配りたい。なぜなら、各自に設定させずに同じパネルを出せるから。
- US3: 利用者として、clone したリポジトリの拡張が、自分が承認するまで動かないと確かでいたい。承認のときに、何が動くかを見たい。なぜなら、拡張は自分の権限で動き、隔離されないから。
- US4: 利用者として、承認した後に拡張の登録が書き換えられたら（`git pull` など）、動く前に気づきたい。なぜなら、承認したものと違うプログラムを動かしたくないから。
- US5: 拡張の作者として、Sodashitsu と 1 行 1 JSON でやり取りし、表示の面の操作（`20261007-soda-extensions` の `display.*`）を、同じ名前・同じ引数で使いたい。なぜなら、`sodactl` を何度も起動せずに済み、後で観測・割り込みの種類が足されても同じ口で受けられるから。
- US6: 利用者として、拡張が落ちた・暴走したとき、pane は動き続け、何が起きたかを画面で知りたい。

## スコープ（案）

### 対象

- **登録**: 利用者の設定（状態ディレクトリの `extensions.json`。`commands.json` と同じ読み方・検査）と、プロジェクトの設定（リポジトリの根の `.soda/extensions.json`）。
- **承認**: プロジェクトの分は、初回に中身を見せ、利用者が承認したものだけ動かす。中身が変わったら再承認。承認の記録・取り消し・一覧（設定画面の節「拡張」）。
- **プロセスの管理**: 起動（状態ディレクトリのロックを取った後）・停止・落ちたときの再起動（間隔をあける・続けて落ちたら止める）・設定の読み直し・`soda handoff` をまたぐ扱い（止めて、新しい版で起動し直す）。
- **やり取り**: 標準入出力の NDJSON。拡張 → サーバは要求（`{"id","method","params"}`）、サーバ → 拡張は返事と出来事（`{"type":…}`）。最初の版で載せる操作は、表示の面（`display.set`・`close`・`list`・`features`・`send`）と、pane の一覧。
  出来事の `display.closed` の理由には、アプリが面を止めた場合（`navigated`・`focus_steal`）がある。
  出来事は、表示の面の操作と閉じたこと・pane の増減。機能の問い合わせ（使えない機能は「未対応」）。
- **応答しない・落ちた拡張の扱い**（D6）: 表示の面では、素通し（何も待たない）。拡張ごとの設定「応答しないときは止める」の項目は、**形だけ先に決める**（効くのは割り込みの作業）。
- 文書（新しい `docs/extensions.md`）。

### 対象外

- 観測のイベント（ターンの完了・承認待ち・ツール呼び出し）・割り込み・端末版のパネル（後の作業。D1・D4・D8）。
- 拡張のプロセスの隔離（サンドボックス）: しない（D3 で受け入れた弱点。承認で守る）。
- 拡張の配布・更新・マーケットプレイス。
- Windows ネイティブでの、設定ファイルの持ち主・権限の検査（`commands.json` と同じく、しない）。

## 安全の要件（案。確定は requirements と design）

1. **承認していないプロジェクトの拡張は、1 度も実行しない**（起動も、存在の確認のための実行も）。設定を読むことと、ハッシュを計算することだけをする。
2. **承認の画面に出すもの**: リポジトリの根の絶対パス・設定ファイルのパス・拡張の id・**実行されるコマンドの全文**（文字として。HTML として解釈しない。長くても省略しない）・作業ディレクトリ・
   「あなたの OS の利用者の権限で動き、隔離されない」という固定の文言・前に承認した中身があれば、その差分。既定のフォーカスは［承認しない］。「すべて承認」は置かない。
3. **承認の鍵**: リポジトリの根の実体のパス（`realpath`）と、その拡張の登録の中身（正規化した JSON）の SHA-256。どちらかが変われば、承認していない扱いに戻る（動いていれば止める）。
4. **検査と実行の間に差し替えられない**: 設定は開いた fd から読み、読んだバイト列でハッシュを計算し、**そのとき解釈した中身で**起動する（起動のときに読み直さない）。
5. **承認できるのは、ログイン済みの画面（ブラウザ・端末版）だけ**。`pane.sock`（ログイン不要の受け口）には、承認・登録・拡張の起動に関わる操作を載せない。
6. **拡張に渡すもの**: token・cookie は渡さない。環境変数は pane と同じ規則（`buildPaneEnv`）に、拡張の id・種類・プロジェクトの根を足したもの。
7. **拡張が出来ること**（最初の版）: 表示の面の操作と、pane の一覧だけ。pane の入出力・設定・認証には、この口からは触れない（拡張のプロセス自身は利用者の権限で動くので、`sodactl login` 済みなら別の口で触れる。これは隔離しない前提の限界として docs に書く）。
8. **量の上限**: 拡張の数・1 行の大きさ・要求の頻度・サーバが拡張へ溜める出来事の数・stderr のログの量。読まない拡張へ溜め続けない（溜まったら捨てて知らせる。続くなら止める）。
9. **落ちても巻き込まない**: 拡張の終了・例外・壊れた行・読まない・書かないで、サーバ・pane・ほかの拡張が止まらない。
10. **`soda handoff`**: 入れ替えの前に拡張を止めて終了を待ち、新しい版が起動し直す（子プロセスを置き去りにしない）。拡張の状態は引き継がない（拡張が自分で出し直す）。

## 完了条件（受け入れ基準の案。ID は requirements の工程で振る）

- 利用者の設定に登録した拡張が、サーバの起動で動き、`display.set` で pane にパネルを出せ、パネルの操作を標準入力で受け取れる。
- プロジェクトの設定の拡張は、承認の前に実行されない（実行の印のファイルが出来ない）。承認すると動く。登録の中身を 1 文字変えると止まり、再承認を求める。リポジトリを別の場所へ移すと、承認し直しになる。
- 承認の画面に、コマンドの全文・パス・固定の文言が出る。既定のフォーカスは［承認しない］。
- 承認の操作は、受け口（`pane.sock`）と、画面でない接続からは出来ない。
- 拡張が落ちると、間隔をあけて起動し直され、続けて落ちると止まって画面に知らせが出る。pane の入出力は止まらない。
- 拡張が標準入力を読まない・巨大な行を書く・壊れた JSON を書くとき、サーバは動き続け、決まった上限で拡張を止める。
- `soda handoff` の後、拡張は起動し直されていて、子プロセスが置き去りになっていない（ビルドした成果物での起動確認）。サーバの停止で、拡張は終わっている。
- 設定の読み直し（既存の「設定を読み直す」の操作）で、足した拡張が動き、消した拡張が止まる。
- 拡張が使えない操作を呼ぶと、エラーで切れずに「未対応」の返事が返る。
- 負の対照: 承認の検査を外すと「承認の前に実行されない」のテストが落ちる。

## 利用者に確かめる点（着手の前に）

1. **承認の鍵に、コマンドが指すスクリプトの中身を含めるか**。勧める案: 含めない（鍵は登録の中身とリポジトリの場所だけ。Claude Code のプロジェクトのフック・Codex のフックの信頼と同じ考え方）。
   `git pull` でスクリプトの中身だけが変わっても、再承認は求められない、という限界を承認の画面と docs に書く。代わりの案: 登録に「見張るファイル」の一覧を書けるようにし、その中身も鍵に入れる。
2. **プロジェクトの拡張が扱える pane の範囲**。勧める案: そのリポジトリの workspace の pane だけ（ほかのリポジトリの pane に面を出せない）。利用者の設定の拡張は、全部の pane。
3. **承認の記録の置き場所**。勧める案: 状態ディレクトリの根（名前付き session で共有。`machines.json` と同じ）。session ごとに承認し直さなくて済む。
4. **別のマシン（保存した SSH のマシン）のプロジェクトの拡張を、手元のブラウザから承認できるか**。勧める案: できる（中継の接続はログイン済みと同じ扱いで、動くのは先のマシン）。承認の画面に、マシンの名前を出す。
5. **拡張の寿命**。勧める案: 利用者の設定の拡張はサーバと同じ。プロジェクトの拡張は、そのリポジトリの workspace が 1 つでも開いている間だけ動く。
6. **プロジェクトの拡張が、スクリプトが動く面（`script-html`）を出せるか**（2026-10-08 に足した。表示の面の作業で、利用者が「スクリプトが動く形式を足す・初回の許可は入れない」と決めたため。`20261007-soda-extensions/decisions.md` D21）。
   pane の中のプログラムは、形式を自分で選べる（縛る手段が無い）。Sodashitsu が起動する拡張については、縛れる。勧める案: 利用者の設定の拡張は出せる。プロジェクトの拡張は、登録に「スクリプトが動く面を出す」と書いたものだけが出せ、
   **承認の画面に、その旨と、残る限界（操作中のキーが読める・枠の移動で持ち出せる）を出す**（登録の中身なので、承認の鍵にも入る）。書いていない拡張の `script-html` は「未対応」で返す。
