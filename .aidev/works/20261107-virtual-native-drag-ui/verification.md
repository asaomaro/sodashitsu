# U10 owned virtual Explorer drag UI

Scope: RemoteDesktopWindow.vue opts into the negotiated capability only for an explicit, initially unchecked per-window request. Protocol dependency is upstream 24feae786fbcfb821cfdefbce73dfb3a3f5e6f8d (local cherry-pick 707adb6d, exclude this duplicate when integrating UI). No backend/helper or Windows machine is operated by this task.

`virtualNativeDrag` feature hint advertises UI support; the start option is sent only after the explicit virtual request. Only a current ready with public `virtualNativeDrag:true` and protocol-validated `files/resourceFences/virtualDisplay`, without secure/cover/virtualMonitors, opens virtual transfer UI. Ordinary physical transfer stays available. File permission, helper preparation, explicit left-button gesture, ACK/COPY and input ownership use unchanged existing components. A ready capability is not a fresh input witness: control release for deliberate COPY handoff keeps capability while inputEnabled/interrupt still cancel an unfinished gesture. Server validates a fresh private witness for each gesture. Reconnect, topology/source/real geometry termination requires fresh stream ready; old socket handlers are epoch-rejected. Shared viewers must agree on explicit request as part of capture settings.

Related four component suites: 22 tests passed (unit.log), including 9 new tests covering implicit request denial, physical/default compatibility, file permission, current ready proof, missing proof/fence, secure/cover/multi-monitor/nonvirtual rejection, control-release capability persistence, fresh proof after reconnect and old socket/topology invalidation. Web `vue-tsc --noEmit` exit0 (typecheck.log). Only protocol/client-core prerequisite package builds were used; no whole-repo build/test repeated. Node24.15.0 and isolated local workspace dependencies/dist.

Real headless Chromium/Vite serves the production Vue component and subcomponents with generated socket messages. Browser observes unchecked opt-in, start frame, missing-proof hidden UI, proof-enabled UI, disabled helper preparation without separate files permission, control-release persistence and topology/stale-proof hidden UI. Native helper/file transfer commands zero, page errors zero (browser.json, browser.log, browser.png). No actual screen, Explorer or IDD is opened. Screenshot inspected.

Negative control changes only the new template source gate back to the old `!virtualScreen` restriction. New unit tests fail 2/9 (negative-unit.log); the real Vite browser fails waiting for the transfer DOM (negative-browser.log). Each Vite run compiles current source, so the negative is not using stale built output. The file is restored byte-for-byte with recorded SHA256 (restoration.json), then both final unit/browser runs pass. Raw outputs are retained, not replaced by summaries.

Actual signed IDD → Windows Explorer drag/OS COPY is not validated here; it remains dependent on real driver availability and a separately scheduled device check. Existing physical Windows drag end-to-end status is unchanged. No sr-pc operations, OS/global settings, microphone, driver, service, UAC or real agent session were used.
