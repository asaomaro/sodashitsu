# 要件: 更新時の引き継ぎ（live handoff。herdr H32 の残り）

## 背景 / 課題

サーバ（`wtm serve`）を新しい版に入れ替えるには、今は止めて起動し直すしかない。止めると各 pane のプロセス
（シェル・実行中のビルドやテスト・Claude Code 等のエージェント）はすべて終わり、戻るのはレイアウト
（`session.json`。`packages/server/src/persist/SessionFile.ts`・`SessionService.restore`）と、有効なら前回の画面
（`--pane-history`。20260926-screen-history-replay）と、公式連携のある会話の再開（20260923-agent-session-resume）だけになる。
長く走らせているエージェントやサーバ・テストを抱えたまま、wtm 自体を更新できない。

herdr には「Live handoff」がある（`docs/herdr-parity.md` の H32 の「live handoff は対象外のまま」、backlog
`product-roadmap.md`「セッション永続化の拡張: 更新時の引き継ぎ（live handoff）〔D8〕」、一次資料は herdr の
`docs/.../session-state.mdx`「Live handoff」節と `src/server/handoff.rs`）:

- 実験的・明示の指定（`herdr update --handoff`）でだけ行う。
- 古いサーバが新しいサーバへ、生きている pane（PTY とプロセス）を渡し、プロセスを止めずに入れ替える。
- 保つもの: pane の PTY とプロセス・エージェントの識別・永続する状態。保たないもの: 実行中の要求・購読・
  クライアントの接続（クライアントは繋ぎ直す）。
- Windows（ConPTY）では対応しない（`[H]windows-beta.mdx`。research.md（20260918-web-terminal-multiplexer）H49）。

## 目的 / ゴール

- Linux（と macOS）で動かしている `wtm serve` を、pane のプロセスを止めずに**ディスク上の新しい版へ入れ替えられる**状態。
  入れ替えた後も、各 pane は同じプロセスのまま入出力・大きさの変更・終了の検知が今までどおり働き、画面も直前のまま見える。
- 入れ替えに失敗しそうなとき（新しい版を読み込めない・引き継ぎに対応していない・引き継ぎの形式の版が違う）は、**入れ替えを始める前に止まり、
  古いサーバがそのまま動き続ける**状態（入れ替えを試したせいで pane を失う場面が、普通に起動し直す場合より増えない）。
- 引き継ぎの指示と受け渡しが、**同じ利用者の同じマシンの中だけ**で行われ、新しいネットワークの待ち受けを作らない状態。
- 指示しない利用者・Windows の利用者には、今までの動作が何も変わらない状態。

## ユーザーストーリー

- US1: wtm を更新する利用者として、長く動いているエージェント・ビルド・開発サーバを止めずに wtm を新しい版へ入れ替えたい。
  なぜなら、再起動するとそれらがすべて終わり、エージェントの作業の途中の状態や、手で起動し直す手間を失うから。
  （受け入れ: AC1, AC2, AC3, AC7, AC9, AC14）
- US2: 利用者として、入れ替えがうまくいかないときは今のサーバのまま残ってほしい。なぜなら、「試しに引き継ぐ」ことで
  pane を失うなら、怖くて使えないから。（受け入れ: AC4, AC12）
- US3: ブラウザで使っている利用者として、入れ替えの後に同じ URL・同じログインのまま画面に戻りたい。
  なぜなら、入れ替えのたびにログインし直したり URL を探したりするのは面倒だから。（受け入れ: AC5）
- US4: 運用者として、引き継ぎの指示と受け渡しが同じ利用者に限られ、外から叩ける口が増えないでほしい。
  なぜなら、pane のプロセスと画面の内容は端末そのものと同じ機微な情報だから。（受け入れ: AC6, AC8）
- US5: 名前付き session（20260926-named-session）を使う利用者として、session ごとに入れ替えたい。
  なぜなら、session はサーバが別々だから。（受け入れ: AC10）
- US6: herdr から移ってきた利用者・Windows の利用者として、何ができて何ができないか（対応する OS・既知の制約）を docs で知りたい。
  なぜなら、herdr の `update --handoff` と入口が違い、Windows では使えないから。（受け入れ: AC11, AC6）
- US7: 引き継ぎを使わない利用者として、今までと同じに動いてほしい。（受け入れ: AC13）

## スコープ

### 対象

- 動いている `wtm serve` に引き継ぎを指示する入口（CLI）。名前付き session・`WTM_SESSION` の指定に従う。
- 指示を受けたサーバが、ディスク上の wtm（同じ起動の入口）で新しいサーバに入れ替わり、生きている pane を渡す。
- 引き継いだ pane の入出力・大きさの変更・終了の検知・画面（ミラー）の続き。
- サーバがメモリにだけ持っている pane の付随の状態のうち、pane を閉じたときの後始末に要るもの——スクロールバックを $EDITOR で開いた pane
  （20260926-edit-scrollback。元の pane のスクロールバックを書いた一時ファイルをエディタで開く pane で、閉じると一時ファイルを消し、
  開く前の元の pane の焦点・拡大表示に戻す）の対応——を新しいサーバへ引き継ぐ。
- 入れ替えの前の確認（新しい版が起動できるか・引き継ぎの形式が合うか）と、確認に失敗したときに元のまま動き続けること。
- 受け渡しの経路を同じ利用者に限ること（ファイル・socket の権限、新しい TCP の待ち受けを作らない）。
- Linux を対象に実装し実機で確かめる。macOS は同じ仕組みで動く設計にするが、実機では確かめない（未検証として記す）。
- Windows は非対応（指示すると非対応だと答えて終わる。サーバには何も起きない）。
- 利用者向け docs と `docs/herdr-parity.md` の H32 行の更新。

### 対象外

- herdr の `herdr update`（自己更新・更新チャネル）に当たるもの——backlog「配布と運用: 自己更新・更新チャネル」の範囲。
  本 work は「ディスク上の新しい版へ入れ替える」ところまで（更新そのものは利用者が行う）。
- herdr の `--remote <host> --handoff`（別マシンへの接続時の入れ替え）。
- 実行中の要求・購読・WebSocket の接続の引き継ぎ（herdr と同じく繋ぎ直しに任せる）。
- 画面の設定（ブラウザ）から引き継ぎを指示する入口。
- Windows（ConPTY）での引き継ぎ。

## 機能要件

- `wtm handoff [--state-dir DIR] [--session NAME]` で、動いている同じ状態ディレクトリの `wtm serve` に引き継ぎを指示する。
  `--session` が無ければ `WTM_SESSION` に従う（`wtm serve` と同じ）。
- 引き継いだ後、pane の id・レイアウト・フォーカス・pane のプロセス（pid）が変わらない。
- 引き継ぎの途中でない起動（普通の起動・落ちた後の起動）は、残っていた受け渡しのファイルを使わずに消す。
- 受け渡される PTY の端末の番号（ファイル記述子）は、PTY の端末であると確かめてから使う。
- スクロールバックを $EDITOR で開いた pane を引き継いだ後に閉じても、今までどおり一時ファイルを消し、元の pane の焦点・拡大表示に戻す。
- 引き継いだ後、pane への入力はそのプロセスに届き、出力は画面に出て、大きさの変更はプロセスに伝わる。
- 引き継いだ後に pane のプロセスが終わったら、その pane は今までどおり閉じる。
- 引き継ぎの直前の画面とスクロールバックが、引き継いだ後の画面にそのまま見える。
- 待ち受けのポートは引き継ぐ前と同じ。ブラウザはログインし直さずに繋ぎ直せる。
- 引き継いだ pane には、会話の自動再開のコマンドを打ち込まず、保存した画面履歴（`--pane-history`）も流さない（プロセスが続いているため）。
- 新しい版を確かめられないとき（読み込めない・引き継ぎに対応していない・形式の版が違う）、引き継ぎを始めずに失敗を答え、サーバは元のまま動き続ける。
- CLI は結果（成功・失敗の理由・引き継いだ pane の数）を表示し、終了コードで成否を返す。サーバが動いていなければそう答える。

## 非機能要件 / 制約

- 対象 OS: Linux（WSL2 を含む）で実装・確認。macOS は設計上の対象・未検証。Windows は非対応。
- Node.js は `package.json` の `engines`（>=24）の範囲で動くこと。ネイティブのアドオンを新しく足さない（足す必要があるなら、実装に入らず判断を仰ぐ）。
- 受け渡しの経路: 新しい TCP/UDP の待ち受けを作らない。ローカルの経路は状態ディレクトリの中に置き、所有者だけが読み書きできる権限にする。
  画面の内容を含む受け渡しの中身がディスクに残る時間を最小にし、読んだら消す。
- 引き継ぎの指示が無い限り、既存の起動・停止・復元の動作を変えない（性能は、起動時に受け渡しのファイルの有無を 1 度見る以上の処理を足さない）。
- 引き継ぎにかかる時間は目安（数秒。ブラウザからは一度切れて繋ぎ直す）で、受け入れ基準にはしない。

## 完了条件 (受け入れ基準)

- [ ] AC1: Linux で `wtm handoff` を実行すると、動いている `wtm serve` がディスク上の wtm で入れ替わり、各 pane のプロセスの pid・pane の id・レイアウト・フォーカスが入れ替え前と同じまま、CLI が成功（終了コード 0）と引き継いだ pane の数を表示する。
- [ ] AC2: 引き継いだ pane に入力すると同じプロセスに届き、その出力が画面（ミラー）に出る。大きさを変えるとプロセスに伝わる（`stty size` 等で見える）。
- [ ] AC3: 引き継ぐ直前に pane に出ていた画面の内容（通常の画面とスクロールバック）が、引き継いだ後の画面にも見える。
- [ ] AC4: 新しい版を確かめられないとき（読み込めない・引き継ぎに対応していない・形式の版が違う）、CLI は失敗と理由を表示して 0 以外で終わり、サーバは同じプロセスのまま、pane は何も失わずに動き続ける。
- [ ] AC5: 引き継いだ後のサーバは同じポートで待ち受け、既存のログイン（Cookie）で `/ws` に繋がる。
- [ ] AC6: 引き継ぎの指示の経路は状態ディレクトリの中のローカルの socket（所有者だけが読み書きできる権限）で、新しい TCP の待ち受けを作らない。Windows では socket を作らず、`wtm handoff` は非対応と表示して 0 以外で終わる。
- [ ] AC7: 引き継いだ後に pane のプロセスが終わると、その pane は閉じる（今までの終了の扱いと同じ）。
- [ ] AC8: 受け渡しの中身（画面の内容を含む）のファイルは所有者だけが読み書きでき、新しいサーバが読んだら消える。引き継ぎの途中でないサーバの起動（普通の起動・落ちた後の起動）は、残っていたそのファイルを使わずに消す。受け渡しのファイルに書かれた PTY の端末の番号（ファイル記述子）を、PTY の端末であると確かめずに使わない。
- [ ] AC9: 引き継いだ pane には会話の自動再開のコマンドも保存した画面履歴も流さない。
- [ ] AC10: `wtm handoff --session NAME`（または `WTM_SESSION`）は、その名前付き session のサーバだけを入れ替える。`--state-dir DIR` を付けると、その状態ディレクトリ（と、その下の名前付き session）のサーバを対象にする。
- [ ] AC11: 利用者向け docs に `wtm handoff` の使い方・対応 OS・既知の制約が書かれ、`docs/herdr-parity.md` の H32 行が更新されている。
- [ ] AC12: 対象のサーバが動いていないとき、`wtm handoff` はそう表示して 0 以外で終わり、何も作らない。
- [ ] AC13: 引き継ぎを指示しない限り、既存のテスト一式と起動確認（smoke）が今までどおり通る。
- [ ] AC14: スクロールバックを $EDITOR で開いた pane（20260926-edit-scrollback）を引き継いだ後に閉じても、一時ファイルが消え、元の pane の焦点・拡大表示が戻る。

## 未確定事項 / 確認したいこと

- Node.js だけで PTY を別のプロセスへ渡せるか（herdr は Rust で `SCM_RIGHTS` を使う）。ネイティブのアドオン無しで可能な方式があるか → research。
- 引き継ぐ側のプロセスが pane のプロセスの親でなくなる（または親のまま待たなくなる）ことの影響（終了の検知・終了コード・ゾンビ） → research。
- 端末（`wtm serve` を起動した端末）・systemd 等の親から見た振る舞い（pid が変わるか） → research / design。
