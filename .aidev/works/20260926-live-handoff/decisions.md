# 判断の記録（20260926-live-handoff）

## D1: 着手の判断と範囲（autonomous・full）

- **背景**: backlog `product-roadmap.md`「セッション永続化の拡張: 更新時の引き継ぎ（live handoff）〔D8〕」を、ユーザーの明示の依頼で
  autonomous で処理する。依頼は「大きな判断（ネイティブのアドオン・デーモンとフロントの分割）が要るなら設計で止めて推奨を返す。
  安全な最初の一切れ（Linux/macOS だけ・明示の指定）が作れるならそれを作り、残りは backlog へ」。
- **決定**: full で進める。research で「ネイティブのアドオンもデーモンの分割も要らない方式（D2）」が見つかったので、
  **設計で止めずに実装まで進める**。対象は Linux（実機で確認）・macOS（設計上の対象・未検証）。Windows は非対応。
- **理由**: D2 の方式は、引き継ぎを指示しない限り既存の経路に一切入らず（起動時に受け渡しのファイルを 1 度見るだけ）、
  指示しても確認（D5）に通らなければ何も変えない。確認の後の失敗は「普通に起動し直した」のと同じ結果（レイアウトは戻り、プロセスは失う）で、
  今より悪くならない。止める条件（ネイティブのアドオン・構造の分割）に当たらない。
- **影響**: 非対応・未検証の範囲と既知の制約（D6）を docs と backlog に残す。

## D2: 入れ替えの方式——同じプロセスのまま `process.execve` で新しい版に入れ替える（方針。承認者がいないので記録して進む）

- **背景**: herdr は古いサーバが新しい版を子として起動し、PTY の master を `SCM_RIGHTS` で渡す（research F1.1〜F1.3）。Node の標準 API には
  `SCM_RIGHTS` が無い（F2.1）。
- **案と具体的な破綻の場面**:
  - **(A) `process.execve` で自分を新しい版に置き換える（採用）**。close-on-exec の無い PTY の master の fd はそのまま残り（F2.2・F2.3）、pid も同じ
    （F2.4）。**fd がプロセスの外へ出ない**ので受け渡しの口が要らない（F7.1）。
    - 破綻 A-1: Node の文書は「標準入出力以外の資源は保たれない」と書く（F2.2）。将来の Node が execve の前に fd を閉じるようになると、
      入れ替えた瞬間に全 pane を失う。→ **execve の前に、その Node で「fd が残ること」を子プロセスで実際に確かめる**（D5）。
    - 破綻 A-2: execve の後に新しい版が起動の途中で落ちると戻れない（herdr の rollback が無い）。→ execve の前に新しい版を
      同じ Node で読み込み、引き継ぎの形式の版を答えさせる（D5）。それでも落ちたら「普通の再起動」と同じ結果（`session.json` は execve の前に保存済み）。
    - 破綻 A-3: 引き継いだ pane のシェルが終わるとゾンビで残る（F4.1）→ D6。
  - (B) 新しい版を `child_process.spawn` の `stdio` 配列で fd を渡して子として起動し、古いほうが終わる。rollback はできる。
    - 破綻 B-1: `wtm serve` を端末で動かしている利用者（既定の使い方）が入れ替えると、**端末に入力待ちが戻り、サーバは背景に残って Ctrl+C が届かない**。
      端末を閉じても止まらない（F4.3）。
    - 破綻 B-2: systemd の `Type=simple` で動かしていると、主プロセス（古いほう）の終了でサービスごと止められ、**pane のプロセスも新しいサーバも終わる**（F4.3）。
    - 破綻 B-3: 古いほうが全 pane の親のまま待ち続けるか、終わって孤児にするかの二択。待ち続けるなら入れ替えのたびに古いプロセスが鎖のように残る。
  - (C) ネイティブのアドオンで `SCM_RIGHTS`（herdr と同じ）。4 つのプラットフォームの prebuild と配布が要る。B-1・B-2 は同じく起きる（herdr はもともとデーモン）。
    **依頼の「止める条件」に当たる**。
  - (D) PTY を持つ長寿命の別プロセス（デーモン）と Web サーバに分ける。全 pane の入出力が IPC を通り、デーモン自身は入れ替えられない。**構造の大きな変更**で止める条件に当たる。
- **決定**: (A)。
- **影響**: `process.execve` は Experimental（F2.2・R5）。Node >= 22.15 / 23.11 が要る（`engines` は >=24 なので満たす）。

## D3: 引き継ぎの指示の経路——状態ディレクトリの Unix ドメイン socket `handoff.sock`（0600）

- **背景**: `wtm handoff` からサーバへ指示を届け、結果（失敗の理由）を返す必要がある。
- **決定**: 状態ディレクトリに `handoff.sock` を置き（Windows では置かない）、0600 にする。1 接続 1 要求の改行区切り JSON。
- **代替案と破綻**: (a) シグナル（`SIGUSR2`）——`wtm.lock` の pid が別の同じ利用者のプロセスに再利用されていると、そのプロセスを既定の動作で
  終わらせる（F7.2）。失敗の理由も返せない。(b) HTTP の API（`/api/handoff`）——ログインしたどのブラウザからでもサーバの入れ替えを
  起こせることになり、ネットワークに口が増える。(c) 既存の `agent-report.sock` に相乗り——pane の中の hook スクリプト向けの口で、返事を返さない形。
- **影響**: Node からは接続相手の uid（`SO_PEERCRED`）を読めない（F7.2）ので、同じ利用者に限る根拠は socket の権限 0600 だけ（既存の report socket と同じ）。
  パスの長さは `agent-report.sock` より短いので既存の検査（`config.ts`）で足りる。

## D4: 結果の返し方——受け付けの返事を返してから execve し、CLI は繋ぎ直して `status` で完了を確かめる

- **背景**: execve で socket の接続は切れる。
- **決定**: サーバは確認（D5）を通ったら `{"ok":true,"id":…,"panes":n}` を返し、書き終えてから execve する。新しい版は起動時に
  引き継ぎの結果（`id`・引き継いだ数・引き継げなかった数）をメモリに持ち、`{"op":"status"}` に答える。CLI は `id` が一致する返事が来るまで繋ぎ直す（上限 60 秒）。
- **代替案**: `serve.json` に結果を書く——ファイルの形（schema 1）を変え、名前付き session の一覧の読み手にも影響する。

## D5: execve の前の確認（preflight）

- **決定**: 同じ Node（`process.execPath`・`process.execArgv`）で `main.js __handoff-preflight` を子として起動する。その子（1 段目）は node-pty で
  使い捨ての PTY（`sleep` するシェル）を開き、master の fd と `dev:ino` を引数にして、自分自身を `process.execve` で `main.js __handoff-preflight --stage 2` にする。
  2 段目はその fd の `dev:ino` が 1 段目と同じで（Linux では `/dev/ptmx` を指す）ことを確かめ、使い捨てのシェルを終わらせ、引き継ぎの形式の版を JSON で答える。
  親は 20 秒で打ち切る。
- **確かめること**: ① その Node で execve が close-on-exec の無い fd を残す（D2 の破綻 A-1）② ディスク上の新しい版が読み込める・`__handoff-preflight` を知っている
  （古い版への入れ替えや壊れたビルドを弾く）③ 形式の版が一致する。
- **退けた案**: 親が `stdio` の 4 つ目で渡した pipe を使う——子の Node の中では close-on-exec が付いていて、execve で必ず閉じる（research F2.6。実測で誤判定した）。
  fd が開いているかだけを見る——閉じた番号を Node が起動時に開く epoll が使うと開いて見える（同 F2.6）。本番と同じ node-pty の master で、`dev:ino` で同じものかを見る。
- **影響**: 確かめるのは読み込みまで。新しい版が起動の後段（待ち受け等）で落ちるのは防げない（D2 の破綻 A-2 の残り）。

## D6: ゾンビと終了コード

- **決定**: 引き継いだ pane の終了は読み取りの終わり（`end`/`close`/`EIO`）で知る（herdr と同じ。F1.3・F3.4）。終了コードは Linux では
  `/proc/<pid>/stat` の `exit_code` から読み（F4.2）、読めなければ 0 とする。ゾンビは回収できない（F4.1）ので、サーバが終わるまで残ることを docs に書き、
  回収の手段（ネイティブのアドオン・子を回収する補助のプロセス）は backlog に残す。
- **理由**: 数は引き継いだ pane の数を超えない（プロセスの表の 1 行ずつ。メモリは持たない）。回収のためだけにアドオンを足すのは D1 の止める条件に当たる。

## D7: 画面の続き——ミラーの画面を受け渡しの中身に入れ、引き継いだ後に大きさでつつく

- **決定**: execve の前に各 pane の読み取りを止め、ミラーの書き込みを待ってから `historyAnsi()`（通常の画面とスクロールバック）を受け渡しの中身に入れる。
  新しい版はそれを `sanitizeHistoryAnsi` を通してミラーへ先に書き（区切りの行は出さない）、大きさを 1 行減らして戻す（SIGWINCH で TUI に描き直させる。herdr の nudge。F1.4）。
- **理由**: 代替画面（vim・エージェントの TUI）とモードは `historyAnsi` に入らない（F5.5）が、つつきで TUI が描き直す。herdr は会話の識別を持つ pane には
  画面を渡さないが、本製品の新しいミラーは空なので、全 pane に渡す（渡した通常の画面の上に TUI が描き直す）。
- **影響**: 受け渡しの中身に画面の内容（秘密を含みうる）が入る → 0600（`writeFileAtomic`）・新しい版が読んだらすぐ消す・普通の起動は残りを消す（AC8）。

## D8: 受け口は常に置く（`wtm serve` のフラグで有効にしない）

- **決定**: `handoff.sock` は Linux/macOS の `wtm serve` で常に置く。引き継ぎの opt-in は `wtm handoff` を打つこと自体。
- **理由・代替案**: `wtm serve --handoff` を付けた起動だけ受け付ける案は、「今動いている古いサーバを入れ替えたい」ときに、その古いサーバを
  付けて起動していなければ使えない（最初の 1 回が必ず再起動になる）。受け口は既存の report socket と同じ権限で、入れ替え以外のことはできない。

## D9: 引き継いだ pane の会話の再開・画面履歴

- **決定**: 引き継いだ pane には会話の再開のコマンドを打ち込まず、`--pane-history` の保存した画面も流さない（プロセスが続いている。AC9）。

## D10: architecture 工程は挟まない

- **背景**: protocol「4.5」の architecture の条件のうち「アーキテクチャ判断が必要」「インターフェース／データモデルが複雑」に当たりうる。
- **決定**: 挟まない。方式（構造）の選択は D2 で済ませ、新しい部品の責務・interface・状態遷移・受け渡しの形式は design.md に tasks へ分解できる粒度で書いた。
  既存のモジュールの境界は動かさない（`PtyBackend` の差し替え点に実装を足し、`handoff/` を足すだけ）。

## D11: 引き継ぎの境目で割れた多バイト文字は 1 文字化けうる（既知の制約）

- **背景**: T3 の点検。PTY の読み取りは `setEncoding("utf8")`（node-pty も同じ）で、止めた瞬間に多バイト文字の途中まで読んでいると、残りの 1〜3 バイトは
  StringDecoder の中にあり、stream の buffer にも PTY にも無い。execve で失われ、新しい版はその文字の続きのバイトから読み始める。
- **決定**: 直さず制約として残す（docs に書く）。
- **理由**: StringDecoder の残りは Node の内部（ネイティブの decoder の状態）で取り出す口が無い。起きるのは引き継ぎの瞬間に出力の途中だった pane の 1 文字だけで、
  画面は nudge の描き直しか次の出力で戻る。

## D12: 待ち受けのポートは `taken.port` でなく起動の指定のまま（design からの逸脱）

- **背景**: design は「新しい版は `taken.port` で待ち受ける」としていた。Origin の検査（`DefaultOriginPolicy`）は組み立ての時点の `options.port` から作るので、
  `listen()` の中で番号だけ変えると Origin の検査と食い違う（T7 の点検）。
- **決定**: `options.port` のまま待ち受け、`taken.port` と違えば warn を残す。
- **理由**: execve は同じ引数・同じ環境で起動し直し、`--port` は 1〜65535 に限られ（`config.ts` の `parsePort`）、名前付き session のポートの記憶も古い版が
  待ち受けた後に書いた `serve.json` から読むので、両者は一致する。違うのは `serve.json` の書き込みが失敗した等の例外だけで、そのときも warn で分かる。
- **影響**: design の「サーバ（新しい版）の起動」と AC5 の対応を書き換えた。

## D13: `handoff.sock` は復元と poller の開始の後に置く（design からの変更）

- **背景**: design は受け口の起動の位置を定めていなかった。復元の前に置くと、起動の途中の指示で復元の途中の session.json を保存し、まだ始めていない poller を
  「再開」しうる（T7 の点検）。
- **決定**: `listen()` の poller の開始の後・`/ws` の受け付けの前に置く。
