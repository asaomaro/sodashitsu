# 決定の記録: 表示の面の配置と状態（ブラウザ版）

`mode: autonomous`。D1 は利用者の決定（変えない）。D2 は、作業の途中で届いた利用者の範囲の変更への対応。**D5〜D13 は、勧める案で設計を書き進めたもので、利用者に決めてもらう点**（選択肢・得失・勧める案）。

## D1: 利用者の要望（決定済み。2026-10-08）

1. パネルの展開の状態を記憶する。2. 記憶が無いときの既定（展開か、たたむか）を、設定で選べる。3. 帯を、たためる。4. 「ボタンを押すと開く」見せ方として、画面の中の浮いた窓を足す（ブラウザの別ウィンドウではない。端末の幅を奪わず、位置と大きさを動かせる）。
5. パネルは、D&D で配置を変えられる。置ける場所は、pane の上・下・左・右と、浮いた窓。上や下に置くときは、帯を隠さず、帯に隣り合う形で置く。6. 帯は、上か下かを選べる。
7. たたんだパネルや浮いた窓を開くボタンは、帯と同じ行の、アプリが描く部分に置く（帯の中身には入れない。プログラムからは偽れない。帯が無いときは、ボタンだけの細い行になる）。

## D2: 端末版は別の work（`20261008-display-tui`）に切り出す

- **経緯**: 作業の途中で、利用者が「端末版（引数なしの `soda`）にも対応する」と範囲を広げた（2026-10-08）。
- **決定**: 端末版は別の work にし、この work（ブラウザ版）に依存させる（`aidev new display-tui --depends 20261008-display-layout`）。そちらは、要件と、設計の骨子まで書く。
- **理由**: 端末版は、いまは表示の面そのものを描かない（`docs/tui-parity.md` W34）。「帯とパネルをセルで描く・中身を端末向けに描く・操作を返す・フォーカスの状態を作る」から始まり、そのうえに配置・たたみ・浮いた窓・D&D が載る。
  ブラウザ版の 3 つの PR（見込み 80 ファイル前後）に足すと、1 つの work が大きくなりすぎる（AGENTS.md「差分を小さく切る」）。守るものも違う（ブラウザ版は枠の隔離と `load`、端末版はエスケープシーケンスの無害化）。
  以前の決定（`20261007-soda-extensions/decisions.md` D8）も「端末版は作業を分ける」。
- **この work が端末版のために決めておくこと**: プログラムの指定（`dock`・`edge`・`collapsed`）と、共有の設定の 3 項目は、端末版がそのまま読める値にする（px に依らない）。大きさ・位置の記憶は、ブラウザは px・端末版はセルなので、共有しない。
- **順**: ブラウザ版の PR-A → PR-B → PR-C。端末版は、その後ろ（TUI-1「帯とパネルを描く・操作を返す」は、この work の PR-A だけに依存する。TUI-2「配置・たたむ・浮いた窓・D&D」は PR-A〜C の型と設定を使う）。

## D3: 枠（iframe）は DOM の中で動かさない。配置・たたみが変わるたびに作り直す

- **決定**: 置く側の `:key` に、置き場所を入れる（`placedFrameKey(info, slot)`）。置き場所が変わると、`DisplayFrame` の部品が外れて、新しい部品が載る（今の「たたんで戻す」「タブの切り替え」と同じ道。新しい合い札・`load` は 0 から）。
  浮いた窓の移動・大きさの変更・重なりの入れ替えは、**スタイルだけ**を変える（重なりは `z-index`。`v-for` の順は「出た順」のまま替えない）。
- **理由**: PR3 の決まりで、2 回目の `load` は必ず「移った」＝面がサーバごと閉じ、`script-html` なら pane が 5 分の冷却に入る。iframe を文書の中で付け替えると、ブラウザは読み込み直す（`research.md` F6・U1）。
  配置を変えただけで面が閉じて罰が付くのは、最も避けたい壊れ方。
- **代替案**: (a) CSS だけで配置を替え、DOM は動かさない（`grid-area`・`order`）＝スクリプトの状態が残る利点があるが、Vue が兄弟の順を入れ替えた瞬間に壊れる（気づきにくい）。見た目の順と Tab の順もずれる。採らない。
  (b) `Element.moveBefore()`（状態を保って動かす新しい API）＝対応するブラウザが限られ、PR3 の「`load` の回数だけで決める」前提を、ブラウザの実装に預けることになる。採らない。
- **得失**: 置き場所を変える・たたんで開くと、スクリプトの面の状態と、枠の中の入力の途中の値・スクロールの位置が消える（中身は描き直される）。今のたたむと同じ。docs の限界に書く。

## D4: PR を 3 つに分ける

- **決定**: PR-A（状態の記憶と既定・帯をたたむ・帯の上下・帯の行のボタン・表示のメニュー・知らせの位置）／PR-B（パネルの上下左右・各側のつまみ・D&D）／PR-C（浮いた窓）。プロトコルの項目（`dock`・`edge`・`collapsed`）は PR-A で全部入れる（プロトコルの変更を 1 回にする）。
  画面は、出来るようになった機能を、PR ごとに名乗る（`collapse` → `dock` → `float`）。名乗っていない置き場所の指定は、その画面では既定へ落ちる。
- **理由**: 見込みの差分は、PR-A 35・PR-B 25・PR-C 20 ファイル前後（テスト込み）。先の PR だけで使える（PR-A だけでも、要望の 1・2・3・6・7 が満たされる）。

## D5: 置き場所は、パネルごとに決まる（利用者に決めてもらう点）

- **勧める案**: パネル（面）ごとに置き場所を持つ。別々の側に同時に置ける。同じ側のパネルはタブ。浮いた窓は、面ごとに 1 つの窓。
- **代替案**: pane ごとに 1 か所（その pane のパネルは、全部が同じ側のタブ。浮かせるときだけ面ごと）。作りは単純（側が 1 つなので、角・最小の計算が要らない）。
- **得失**: 勧める案は、「進捗は下・差分の一覧は右」のような使い分けが出来る。代わりに、4 つの側が同時にありうるので、最小の大きさを保つ計算と、自動でたたむ順（D13）が要る。計算は純粋な関数 1 つに閉じる。

## D6: 状態は、その画面が覚える。鍵は「pane と面の名前の組」。置き場所だけは、名前でも引き継ぐ（利用者に決めてもらう点）

- **勧める案**: `localStorage`（`soda.prefs.v1` の `displayLayout`。共有の設定へ送らない）。
  - 面ごと（鍵: pane の id・種類・名前）: たたみ・置き場所（帯は上下）・浮いた窓の位置と大きさ。**利用者がその面を 1 回でも操作したら、その時点の置き場所とたたみを、まとめて書く**（項目ごとに「記憶がある・無い」を分けない。移しただけの面を、プログラムが後から `--collapsed` でたためる、を防ぐ）。
  - 名前ごと（鍵: 種類・名前）: **置き場所だけ**（最後に利用者が決めたもの）。別の pane で、同じ名前の面が初めて出たときの初めの値になる。
  - pane の側ごと（鍵: pane の id・側）: 大きさ（幅・高さ）。
  - 上限 256・64・128。古い順に捨てる。もう無い pane の分は、接続のたびに捨てる（今のパネルの幅と同じ）。
- **代替案**: (a) pane と名前の組だけ（名前ごとを持たない）＝いちばん予測しやすいが、pane は作り直すたびに id が変わる（UUID・再利用なし）ので、新しい pane では毎回、既定の場所から。D&D で決めたことが、その pane かぎりになる。
  (b) 名前だけ＝どの pane でも同じ。「あの pane の進捗だけ開いておく」が出来ない。(c) プログラムの種類ごと（エージェントの種類）＝面を出すのはエージェントとは限らない（スクリプト）。種類が取れない面が出る。(d) 共有の設定に持つ＝ブラウザごとに画面の大きさが違い、px の位置が合わない。pane の id を共有の設定に溜めることにもなる。
- **得失**: 勧める案は、「この名前の面は下」という好みが新しい pane にも効く。代わりに、**別のプログラムが同じ名前（たとえば `status`）を使うと、前のプログラムのために決めた置き場所が効く**（たたみ・位置は引き継がないので、害は「思った場所と違う」まで。D&D か「プログラムの指定に戻す」で直せる）。

## D7: プログラムの指定は「初めの値」。たたみは、プログラムからは「たたむ」だけ（利用者に決めてもらう点）

- **勧める案**: `--dock`・`--edge`・`--collapsed`。優先は、利用者の記憶 ＞ プログラムの指定 ＞ 設定の既定。たたみだけは「設定が『たたむ』**または** `--collapsed`」でたたむ（プログラムに、開かせる指定は無い）。
  `--dock float` も許す。**利用者がまだ触っていない浮いた窓は、いつも閉じて始まる**（`--collapsed` を付けなくても。設定の既定が浮いた窓のときも）＝「ボタンを押すと窓が開く」（要望の 4）。浮いた窓の位置・高さは、プログラムは指定できない（幅の初めの値だけ `--size`）。
  理由（2 回目の独立点検）: 記憶の無い面が、プログラムの指定だけで端末の上に重なると、端末を押すつもりの押下が窓に落ち、静的な形式の枠なら、そのままフォーカスが入る（以後のキーが枠へ行く）。利用者が 1 度も開いていない窓は出ない、とすれば、この道は、利用者が開いたことのある名前の面に限られる。
  **残る道（利用者に決めてもらう点）**: 利用者が開いたままにした窓の記憶（開いている・位置）は、面を閉じても残る。その pane のプログラムは、同じ名前で出し直せば、利用者が決めた位置に、好きな時機に窓を出せる。
  - 勧める案: 受け入れる（docs の限界に書く）。開いたままにした窓が、再読み込み・出し直しの後も開いて出るのは、要望の 1「展開の状態を記憶する」そのもの。位置は、利用者が決めた場所に限られる。
  - 代替案: 面が新しく出たとき（面の id が替わったとき）は、浮いた窓は、記憶が「開いている」でも閉じて始め、位置と大きさだけ引き継ぐ（再読み込みでは閉じない）＝突然の窓は無くなるが、出し直すたびに、利用者がボタンを押すことになる。
- **代替案**: (a) プログラムの指定を持たない（利用者と設定だけ）＝安全で単純だが、横長の表を出すプログラムが「下に」と言えない。(b) `--dock float` を許さない＝要望の 4 を、プログラムの側から選べなくなる。
  (c) 浮いた窓も、設定が「開く」なら開いて始める＝プログラムの指定だけで、端末の上に窓が出る（上の理由で、採らない）。
- **古いサーバ**: 受け口の schema は知らない項目を断る（`research.md` F13）ので、sodactl は先に機能を見て、古ければ指定を落として出す（結果に `ignored`）。指定は「初めの値」なので、落ちても面は出るほうがよい（`script-html` のように「未対応」で止めない）。

## D8: 設定は 3 項目（共有の設定）。帯の初めの状態の設定は足さない（利用者に決めてもらう点）

- **勧める案**: 「表示のパネルの初めの状態」（開く／たたむ）・「表示のパネルの既定の置き場所」（右／左／上／下／浮いた窓）・「表示の帯の既定の場所」（上／下）。節「端末」の、`displayScriptEnabled` の近く。共有の設定（好みなので、ブラウザをまたいで同じでよい）。
- **足さないもの**: 帯の初めの状態（帯は 1 行で、たたんで始める必要が薄い。プログラムが `--collapsed` で言える）・浮いた窓の既定の大きさ・各側の既定の大きさ（どの側でも、プログラムの `--size`〔省くと、サーバが 320px を入れる〕を、範囲に丸めて使う。画面は、`--size` が省かれたかどうかを見分けられないので、上下だけ別の既定は持てない）。
- **代替案**: 設定を「初めの状態」だけにする（要望の 2 の最小）。置き場所と帯の上下は、D&D とメニューで足りる、という考え。勧める案は、「いつも下がよい」人が、面ごとに動かさなくて済む。

## D9: 浮いた窓は、その pane の端末の領域の中だけ（利用者に決めてもらう点）

- **勧める案**: 窓の全体が、いつも「端末の領域」（帯・帯の行・ドックのパネルを除いた、端末の箱）の中にある。pane をまたがない。モーダルではない（開いていても、端末を打てる）。複数の窓は、押したものが前。
- **理由**: 「ほかの pane・端末・アプリの部品の上に重なって、押下やキー入力を横取りできないか」への答えを、作り（領域の箱で切る）で保証できる。帯の行のボタン・ほかの面の見出し（固定のラベルと印）を、窓が覆えない。
- **代替案**: (a) pane の全体（帯・ドックのパネルの上も）＝広く使えるが、ほかの面の印・［操作する］を覆える。(b) アプリの画面全体（pane をまたぐ）＝いちばん自由だが、別の pane の端末・tab バーの上に、信頼しない中身の窓が載る。
  「どの pane のものか」が分かりにくくなり、覆い・フォーカスの番の「その pane の端末へ戻す」とも合わなくなる。どちらも採らない。
- **得失**: 小さい pane では、窓も小さい（最小 240×120px。入らなければ出せず、ボタンのまま）。広く見たいときは、pane を拡大（zoom）する。

## D10: たたんだパネルの幅 24px の見出しをやめる。帯の行のボタンは、行の左（印の隣）

- **決定**: たたんだパネルは、帯の行のボタンだけになる（要望の 7）。今の、端末の右の幅 24px の「表示 (N)」は出さない。
- **ボタンの置き場所**: 行の左端の印「▍表示」のすぐ右。アプリが描く部分を左にまとめ（印・ボタン）、その右が帯の枠、右端に、その帯のもの（印「スクリプト」・［操作する］・［⋮］・［×］）。
  帯が上にも下にもあるときは、**最初に出ている帯の行**に置く。出ている帯が無いときは、設定の「帯の既定の場所」の側に、細い行を出す。
- **偽れるか**: ボタンは枠の外で、帯の枠の箱はボタンの箱と重ならない。帯の中身は、自分の箱の中に、似た絵を描くことはできる（今も、見出しに似た絵は描ける）。その絵を押しても、面は開かない（自分のプログラムへ操作が届くだけ）。限界として docs に書く。

## D11: 新しいキーの操作 `display_menu`（既定 `prefix+shift+i`）

- **決定**: pane の面の一覧のメニューを開く操作を 1 つ足す。D&D・帯の行のボタン・つまみで出来ることを、キーボードだけで出来るようにする入口（端末は `Tab` を自分で受けるので、端末から帯の行のボタンへ `Tab` では届かない）。
- **代替案**: pane のメニュー（右クリック。枠の `Enter`）に項目を足すだけ＝キーを増やさないが、端末から枠へ `Tab` で届くのは tab バー経由で、遠い。メニューは入れ子を持てない（`research.md` F17）ので、項目が多くなる。
  勧める案は、メニューを 2 段に開く（一覧 → 面のメニュー）。pane のメニューにも「表示のメニュー…」を 1 行足す。

## D12: モバイルは変えない（利用者に決めてもらう点）

- **勧める案**: 幅 767px 以下の画面は、今までどおり（パネルは重ね表示・帯は上）。置き場所・たたみ・帯の上下・浮いた窓は効かない。記憶も読まない・書かない。
- **理由**: モバイルの重ね表示は、もともと「ボタンを押すと開く」出し方で、端末の幅を奪わない。pane は 1 つだけで、上下左右に置く広さが無い。
- **代替案**: 帯のたたみ・上下だけは、モバイルでも効かせる。モバイルの帯は `MobileShell` が自分で描いており（`research.md` F8）、帯の行のボタンの置き場所を別に作ることになる。必要になってから、別の作業で。

## D13: 端末の最小は 40 列・10 行。収まらないときは、上 → 下、左 → 右の順で自動でたたむ

- **決定**: 列は今の決まり（40 列）。行は 10 行を足す（上下にパネルを置けるようになるため）。向かい合う 2 つの側が収まらないときは、まず大きいほうを縮め、それでも収まらなければ、縦は上、横は左を先に、自動でたたむ（既定の置き場所である右と、プロンプトに近い下を残す）。
  自動のたたみは、記憶に書かない（pane が広がれば戻る）。

## D14: 知らせ（トースト）は、面の固定の部品を測って、重ならない場所に出す

- **経緯**: PR3 は、面が 1 つでも出ていれば知らせを右下へ寄せた（右上の見出しを覆わないため）。この作業で、見出し・帯の行が下にも来るので、右下でも重なる。
- **決定**: 知らせは、画面の右の縁に沿った帯（知らせの幅）の中で、面の固定の部品（`data-display-chrome` を付けた要素）の矩形と重ならない、縦の空きを選んで出す（下から探す。空きの高さを超える分は出さない）。
  端末は最低 10 行あるので、空きは必ずある。計算は純粋な関数。面が無いときは、今までどおり。

## D15: 独立点検で分かった、PR3 のフォーカスの番との噛み合い（押してもフォーカスを取らない部品）

- **分かったこと**（上流の文書の独立点検。2026-10-08。コードを読んで突き合わせた。動かして確かめてはいない）: `DisplayFrame.vue` は、スクリプトの面の操作中に、枠の外で `pointerdown` が起きると操作を終え、1 拍後に、まだ枠にフォーカスがあれば「取られた」と数える。
  押してもフォーカスを取らない部品（`preventDefault` する部品）を押すと、フォーカスが枠に残るので、**利用者の押下が `focus_steal` に数えられる**（3 回で、その pane のスクリプトの面が閉じて、5 分の冷却）。
- **決定**: この作業の部品（見出しのボタン・つかむ場所・帯の行のボタン・つまみ・窓の縁と角）は、押した瞬間に、枠にフォーカスがあれば端末へ移す（`installKeepFocusRelease`。`DisplayFrame.vue` は変えない）。AC24 と負の対照に入れた。
- **追記（2 回目の独立点検）**: スクリプトの面の**覆い**（`.display-frame-cover`。`@mousedown.prevent`）も、同じ形。面 A の操作中に、別のスクリプトの面 B の覆いを押すと、数えられる（PR3 の木でも、パネルと帯の 2 枚で起きうる。確かめていない）。浮いた窓は、中身のほとんどが覆いで、「押して前へ出す」を足すので、`installKeepFocusRelease` の対象に `[data-display-cover]` を入れた。

1. **開いた面を、その側の「選んでいるタブ」にする**（`setFaceCollapsed(info, false)`）。トレイで開いたのに、別のタブが出たままになるため（E2E で見つけた）。前に出ていた面の枠は作り直される（docs に記載）。
2. **面のメニューを、画面の下・右にはみ出さない位置へずらす**。下の帯の［⋮］から開くと、項目が画面の外に出たため。
3. **ブラウザ版の設定の画面は 2 項目**（初めの状態・帯の既定の場所）。「パネルの既定の置き場所」は、左・上・下・浮いた窓が効かない PR-A では出さない。端末版の設定の画面も、レビューの後に同じ 2 項目に揃えた（N3）。値（`displayPanelDock`）は共有の設定に持つ。
4. **「設定で無効」の E2E は、ストアの値だけを変えて確かめる**。共有の設定（`displayScriptEnabled`）を変えると、サーバが面を閉じてしまうため。

## D23: PR-A のレビュー（2026-10-08）の指摘の直し方と、実測（U1）

- **U1 の実測（Chromium）**: iframe を DOM の中で動かすと（並べ替えでも、親をまたぐ移動でも）、**同じ要素のまま `load` が 1 増える**。レビューの実測値は `before [1,1] → afterReorder [1,2] → afterMove [2,2]`、`isConnected` は常に真。設計の前提 U1（動かすと再読み込みされる）が確かめられた。
  - 帰結: 「枠を動かしていない」ことは、`isConnected` では見つからない。E2E (6)(6b) は、`data-display-loads` の比較と、`MutationObserver` による `iframe[data-display-frame]` の出入りの記録で見る。
  - スクリプトの枠を動かすと、`load` の増加が「移動した（navigated）」と数えられて、面が閉じる（負の対照で確認）。
- **S1（知らせが固定の部品に重なる）**: 割り付けのスナップショットに `placement`（帯の上下・たたみ・トレイの行・「ほか N 件」の署名）を含めた。署名が変わると `layoutRev` が増え、知らせが測り直す。
- **S2（細い pane で帯の固定の部品が押せない）**: 「帯の行を折り返す」ではなく、**帯を自動でたたむ**ほうにした。理由: 帯の高さは割り付け（端末の領域の計算・3 分の 1 の上限）が使う値で、折り返すと、実際の高さが計算とずれる。自動でたたむなら、既存の作り（パネルの自動のたたみ・押せないトレイのボタンと `title` の理由）に載る。
  - 下限（`paneDisplayLayout.ts`）: スクリプトの帯 320px・それ以外 140px。実測の固定の部品の合計は、スクリプトの帯 約 265px（操作中 約 285px）・それ以外 約 105px。記憶は変えない（広げれば戻る）。
  - 帯の行の［⋮］［×］は、行の高さに収める（N6。高さ 24px の帯で 26px あった）。
- **S3**: D21-2 の備えを、プログラムの `close` と、pane を狭めた自動のたたみで E2E に足した（(14a)（スクリプトの帯が載る）・(14b)（静的な面だけ）。**備えだけが頼りになるのは (14b)**。スクリプトの帯が載っていると、`focusDrop` の見回りも端末へ戻す）。フォーカスのある要素が DOM から消える瞬間は、ブラウザが一瞬 `body` にする（同じ周期のうちに端末へ移すので見えない）ので、消える操作の検査は標本（25ms）だけで数える。
- **S4**: (7)(c2) に、`keyboard.down` を続ける本物の押しっぱなしを足した（パネルの出入りの回数で見る）。
- **S5**: 上の U1 のとおり。帯の最大数は 2 本（`display_limit`）なので、レビューの「帯 3 本」は「帯 2 本とパネル 1 枚」にした。
- **N1**: `installKeepFocusRelease` に `isTrusted` の確認。**N3**: 上の D22-3。**N4**: docs に 1 行。**N7**: 文言の文字の箱の下端・右端も確かめる（箱そのものは、帯の最小の高さで 1.6px はみ出す〔内側の余白だけ。入れ物は `overflow: auto`〕ので、文字の箱で見る）。

## D24: PR-B の実装で、設計から外れた点・足した点

1. **端末版の設定にも「表示のパネルの既定の置き場所」（右・左・上・下）を足した**（D22-3 の「PR-B から両方に出す」。浮いた窓は PR-C）。
2. **ドラッグの途中の「落とせる場所」は、上下が全幅・左右がその間の高さの 5 つの箱**で描く（設計の図の 22% の帯）。強調は `dockZoneAt` の結果（いちばん近い縁の比）で決めるので、角は箱の見た目より斜めに分かれる。
3. **同じ側のタブの 2 枚目以降は、見出しを持たない**（枠は選んでいる 1 枚だけ）ので、面のメニューは、その側の選んでいるタブからしか開けない。2 枚目以降は、面の一覧のメニュー（`prefix+shift+i`・トレイの「ほか N」）から移す。
4. **端末の最小を保つ縮め方の「先」は、縦が上・横が左**（設計どおり）。両側の最小どうしでも入らなければ、先の側を自動でたたむ。専用のトレイの行（24px）が自動のたたみで出るときのやり直しは、PR-A の仕組みのまま縦にも効く（空きが 24px 減る）。

## D25: PR-C の実装で、設計から外れた点・足した点

1. **D&D の中央（ドック → 浮いた窓）の矩形は、いまの領域へ丸めない**。離した位置を左上にして、大きさは初めの矩形と同じ。設計は「（丸める）」だったが、ドックが場所を取っているいまの領域で丸めると、ドックが外れて広がった後の領域の右寄りに置けない（実測: 右のパネルから中央へ落とすと、離した位置から 68px ずれた）。記憶の矩形はそのままにし、移した後の割り付けが `clampFloatRect` で広がった領域の中へ丸めて描く（`DisplayPanelHead.vue`）。
2. **面に依らない部品を切り出した**: `display/floatGeometry.ts`（矩形の丸め・移動・大きさの変更・キーの量・重なりの順・窓の動ける領域。表示の面の型を持たない）、`composables/useResizeDrag.ts`（`axis` に `move`・`nwse`・`nesw`、始めるときに決まる `axis` を足した）、`display/dockDrag.ts` の `floatEdgeZoneAt`。後でグラフの画面の「端末の窓」が使い回せる（窓の枠〔`DisplayFloat.vue`〕は、まだ面〔`DisplayInfo`・`DisplayFrame`〕に結びついている）。
3. **窓の縁・角のつかむ場所は、窓の外へ 3px はみ出す**（縁は 6px、角は 12px）。窓の見出しのボタンは、つかむ場所より上（`z-index`）。窓の縁が領域の縁の 4px 内側にあるので、はみ出しても隣の部品のつまみは覆わない。
4. **窓の `placement` の署名に窓の矩形を入れた**（知らせの測り直し）。窓の開閉・領域の変化で `layoutRev` が増える。
5. **キーのモードの終わり**: Enter・Esc・Tab（確定してフォーカスは Tab の行き先に任せる）・フォーカスが窓の外へ出た（確定）。窓が消えるときにモードの途中なら、先に端末へフォーカスを移す。窓の根のキーは、Tab 以外すべて端末へ流さない。
6. **浮いた窓の見出しのつかむ場所は、D&D ではなく窓をその場で動かす**（`FloatGripKey` を `DisplayFloat` が `provide`）。縁から 16px 以内で離すと、その側のドックへ置く（`withDisplayChange` を通す）。
7. **E2E の更新**: `display-layout-dock.spec.ts` (5) の中央は、PR-B では「ここには置けません」だったが、PR-C では落とせる場所になる（窓の動ける領域が分かっている間）。その箇所を窓になる確かめに替え、窓から右へ戻して続ける形にした（弱めていない）。
