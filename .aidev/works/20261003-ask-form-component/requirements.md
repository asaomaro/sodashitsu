# 要件: ask-form の画面の部品（`<ask-form>`）を取り込み、sodactl ask の画面をそれで描く（ページングを含む）

## 背景 / 課題

`sodactl ask` の画面（`packages/web/src/components/AskDialog.vue`）は、Claude Code のスキル ask-form（public_docs の `form.html`）を手で写して作った。
定義の検査・回答の集め方・画面が 2 か所にあり、ask-form に足した機能が Sodashitsu に届かない。2026-10-03 に ask-form へ**ページング**
（質問が多いとページに分かれる）が入ったが、pane の中では `sodactl ask` が使われるので、利用者がふだん見る画面には効かない。

ask-form を改修しているセッション（pane p2）から依頼があり、次の方法で合意した（利用者の了承済み。やりとりは `decisions.md` D1）:

- ask-form が画面をフレームワークに依存しないカスタム要素 **`<ask-form>`**（`ask-form.js`。JS 1 ファイル・Shadow DOM）に切り出す。Sodashitsu はそれを取り込み、
  `AskDialog.vue` はダイアログの枠と「どの pane からの質問か」の行だけを持つ。
- 検査と回答の集め方は言語が違い、サーバは定義を信用できない入力として自分で検査するので、部品にしない。**共通の試験データ**（`fixtures/normalize.json`・`collect.json`）を両方のテストが読む。
- 部品は public_docs の `main` にある（コミット 94a5ef6。`docs/ClaudeCode/skills/other/ask-form/`）。`static version` は 1.0.0。

部品を取り込んでも、**定義の新しい項目は自動では届かない**: サーバの `normalizeAskSpec` は知っている項目だけを通す。ページングの項目（全体の `paging`・質問の `page`）は、この作業で通す。
型（`edit`・`rank`・`table`）と、ほかの項目（`code`・`group`・`filter`・画像・音 等）は、別の作業（作業 B）で扱う。

試験データをいまの Sodashitsu に通すと、49 例中 47 例が一致し、2 例が食い違う（試験データが正）: 空の `showIf` を `{}` のまま残す／`collectAsk` が複数選択の値を定義の順に揃えない。

## 目的 / ゴール

- `sodactl ask` の画面が ask-form と**同じ部品**で描かれ、ask-form の側で画面を直せば、部品を写し直すだけで Sodashitsu の画面も同じになる状態。
- 質問の多いフォームが、Sodashitsu の画面でもページに分かれて答えられる状態。
- 検査と回答の集め方が ask-form と食い違ったら、テストが落ちて気づける状態。

（`.aidev/charter.md` は無いので、charter ゴールへの紐づけは省く。）

## ユーザーストーリー

- US1: 利用者として、質問の多いフォームを、Sodashitsu の画面でもページを移りながら答えたい。なぜなら、1 枚に並ぶと長く、どこまで答えたかを見失うから。（受け入れ: AC4, AC5, AC-I1〜AC-I5）
- US2: 利用者として、いままでのフォーム（1 つ選ぶ・複数選ぶ・自由記述・その他・表示条件・補足・選択肢の色の帯・おすすめの印・既定の値）が、今までどおり使えてほしい。なぜなら、部品に替わっただけで答え方が変わると困るから。（受け入れ: AC2, AC3, AC7, AC8, AC9, AC13）
- US3: 開発者（と AI エージェント）として、ask-form の画面の改修を、部品を写し直すだけで取り込みたい。なぜなら、同じ画面を 2 か所で直すと、片方だけ直って食い違うから。（受け入れ: AC1, AC6, AC12, AC14）
- US4: 利用者として、部品に替わっても、pane のプログラムが画面を装ったり壊したりできないままであってほしい。なぜなら、定義は pane のプログラムが自由に書けるから。（受け入れ: AC3, AC10, AC11, AC15, AC16）

## スコープ

### 対象

- 部品（`ask-form.js`）と共通の試験データを Sodashitsu に写す仕組み（同期スクリプト・写した先・出どころの記録・手で直していないことの検査）。
- `AskDialog.vue` を枠（ダイアログ・「どの pane からの質問か」の行・開閉・フォーカス・取り消し）だけにし、中身を部品に任せる。Sodashitsu のテーマの色を部品へ渡す。
- protocol: 定義の `paging`・`page` を検査して通す。空の `showIf` を落とす。`collectAsk` が複数選択の値を定義の順に揃える。共通の試験データを読むテスト。
- 既存のテスト（`AskDialog.test.ts`・E2E `ask-form.spec.ts`・`ask-form-mobile.spec.ts`）の書き直しと、ページングの E2E。
- docs（`docs/sodactl.md`「質問のフォーム」・`docs/verification.md`・sodactl の skill ファイル・`NOTICE`）。

### 対象外

- 型 `edit`・`rank`・`table` と、項目 `code`・`group`・`filter`・`preview`・`thumb`・`image`・`audio`・「前回の回答」の印（作業 B。部品は描けるが、Sodashitsu の検査が通さないので画面には出ない）。
- 画面が出せる型を名乗る仕組み（`ask.subscribe` に足す。作業 B）。
- 画像・音のプレビューを Sodashitsu 経由で配ること（別の作業）。
- 部品そのものの改修（public_docs の側。直したい点は ask-form の側へ伝える）。
- ask-form の側（`ask.py`・`form.html`）の変更。
- CI を足すこと。

## 機能要件

- 部品と試験データは、public_docs の**固定したコミット**から写す。写した先のファイルは手で直さない。出どころ（コミット・各ファイルのハッシュ）を記録する。
  - 写すコミットは、試験データの `sodashitsu` の欄がこの作業の後の Sodashitsu に合っている版にする。94a5ef6 の `normalize.json` は、`page`・`paging` の 3 例を「通すまでは落ちる」としているので、
    その 3 例の欄を外した版を ask-form の側に依頼した（2026-10-03）。**AC6 は、その版（記録したコミット）の試験データで判定する**。
  - 着地までにその版が届かないときは、94a5ef6 のまま写し、その 3 例だけを Sodashitsu のテストの側の一覧（写したファイルの外）で読み替えて、後で差し替える課題として残す。
- `sodactl ask` の定義・結果の JSON・終了コード・どのブラウザに出るか・上限は変えない。足すのは定義の 2 項目だけ:
  - 全体の `paging`: `"auto"`（既定。高さに収まらないときだけ分ける）・`false`（分けない）・1 以上の整数（1 ページの質問の数）。
  - 質問の `page`: ページの題（文字列）。書いた質問から新しいページが始まる。1 つでも書いたら、高さでの自動の分割はしない。
- 回答の形（`answers`・`custom`・`note`）は変えない。サーバは今までどおり、回答を定義と突き合わせて検査する。
- 最上部の「どの pane からの質問か」の行は、今までどおりアプリが描く固定の行（部品の外・定義で消せない・書き換えられない）。
- 部品が「この定義は出せない」と知らせたとき（知らない型・壊れた定義）は、質問を欠けたまま決定させない（扱いは design）。
- 知らない項目・対応していない型の扱いは今までどおり（知らない項目は落とす・対応していない型は `unavailable`）。

## 非機能要件 / 制約

- **安全**: 定義は敵対的な入力。定義の文字は全て文字として表示する（HTML として解釈しない）。CSP（`default-src 'self'` ほか）は緩めない。部品は通信しない・ページ全体に触らない（部品の決まり。取り込むときに確かめる）。
- **配色**: 部品の色は Sodashitsu のテーマの変数に従う（テーマを切り替えると部品の色も替わる）。
- **互換**: 古い sodactl（`page`・`paging` を知らない）× 新しいサーバ、新しい sodactl × 古いサーバ、読み込み直す前の古い画面、のどれでも質問が出て答えられる（ページに分かれないだけ）。
- **配布**: `scripts/package.mjs` で作る配布物と `pnpm build` に、部品が含まれる（Web の `dist` にまとめられる）。実行時に public_docs や外部を読みに行かない。
- **ライセンス**: 写したファイルの出どころを `NOTICE` に書く（`third_party/herdr/` の先例に合わせる）。
- E2E の合否は、ブラウザの DOM と sodactl の stdout・終了コードで見る（条項 `e2e-observe-browser`）。

## 相互作用の受け入れ基準

- [ ] AC-I1 開く / 閉じる: 質問が届くとダイアログが開く。決定・キャンセル・`Esc`・pane が閉じられた・sodactl が終わった、で閉じる。背景のクリックでは閉じない（選びかけの回答を守る）。
- [ ] AC-I2 確定 / 取り消し: ［決定］・`Ctrl/Cmd+Enter`・1 行の入力欄の `Enter`（途中のページでは次のページへ、最後のページでは決定。IME の変換中は除く）で確定。［キャンセル］・`Esc` で取り消し（sodactl には `cancelled`）。ページを移っても、答えた内容は残る。
- [ ] AC-I3 キーボードだけで完結するか: 開く → `Tab` で質問へ → 矢印・`Space` で選ぶ → `Alt+PageDown`／`Alt+PageUp` か［次へ］［戻る］でページを移る → `Ctrl+Enter` で決定、をマウス無しで通せる。
- [ ] AC-I4 フォーカスの行き先: 開いたら最上部の「どの pane からの質問か」の行（操作部品ではない——打っている途中の `Space`・`Enter` が回答にならない）。ページを移ったら、そのページの番号（題）——［次へ］［戻る］・キー・番号・1 行の入力欄の `Enter` のどれで移っても同じ。決定を押して未回答のページへ移されたときの行き先（ページの番号か、未回答の質問か）は、部品の動きを research で確かめて design に書く。閉じたら、質問の pane が表示中ならその端末、そうでなければ開く前の場所。
- [ ] AC-I5 既存の操作を妨げないか: ダイアログが開いている間、キーは端末へ流れない。`Alt+PageDown`／`Alt+PageUp` がブラウザの既定の動き（タブの切り替え等）を起こさない。ほかのダイアログ（設定・確認）が開いていても潰さない。
