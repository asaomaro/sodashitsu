# 決定記録

2026-10-07 に、利用者が ask-form のフォーム（「soda 拡張の方針」）と、その後のやり取りで決めたもの。
根拠の調査は `research.md`。

## D1: 拡張を 3 つの層（表示・観測・割り込み）に分け、下の層から順に出す

- **背景**: Claude Code の Mods は Claude Code だけの機能で、Codex や GitHub Copilot CLI では使えない。
  利用者から「Sodashitsu 側で、Mods でできるような機能を提供できるか」と問われた。あわせて「すべての
  エージェントに対応する必要はなく、ある機能が特定のエージェントでは使えないという状態は許容できる」
  との方針が示された。
- **決定**: 拡張（仮称「soda 拡張」）を、表示（pane の横のパネル・上の帯・通知など）／観測（ターンの完了・
  承認待ち・ツール呼び出しなど）／割り込み（止める・聞く・書き換える・足す・続ける）の 3 層に分ける。
  上の層ほど、使えるエージェントが減る。使えない機能は、エラーではなく「未対応」として拡張に伝える。
- **理由・代替案**: 全部に共通するのは「止める」だけで、それ以上は段階にしかならない（research.md F4）。
  代替案（全エージェントで同じ機能を保証する）は、いちばん弱いエージェントに合わせることになり、
  Claude Code と Codex でできることを捨てる。

## D2: 最初に着手するのは、表示の面

- **決定**: 4 つの作業（表示の面・観測・割り込み・対象の拡大）のうち、表示の面から始める。
- **理由・代替案**: 表示はエージェントに依存せず、検知の対象外のものも含めて、すべてで動く。エージェントの
  側への導入も要らないので、最初に価値が出る。代替案（割り込みを先にして、表示は既存の ask ダイアログで
  代用する）は、実機の確認が要るエージェントごとの作業から始めることになる。

## D3: 拡張は別プロセスで動かし、NDJSON でやり取りする

- **決定**: 拡張は、設定に登録した独立のプログラムとする。Sodashitsu が起動と停止をし、標準入出力で
  1 行 1 JSON をやり取りする。サーバの中で動く JS/TS（Mods と同じ形）にはしない。
- **理由・代替案**: Sodashitsu は、pane を生かし続けることが要である。サーバの中で動かすと、拡張の例外や
  無限ループが、すべての pane と、つないでいる全員を巻き込み、`soda handoff` での入れ替えも複雑になる。
  別プロセスなら、言語を問わず、拡張が落ちてもサーバは無事。欠点（往復の遅さ・見える情報は用意した口
  だけ）は受け入れる。利用者は仕組みの違いの説明を求めたうえで、別プロセスを選んだ。

## D4: 割り込みの最初の対象は、Claude Code と Codex

- **決定**: 止める・利用者に聞く・引数の書き換え・文脈の追加・継続を、まず Claude Code と Codex で動かす。
- **理由・代替案**: この 2 つは、ほぼ全機能を持ち（research.md F2）、Sodashitsu の連携として動作を
  確かめ済み（`agents.ts` の `verified`）。対象を足すほど、実機の確認の手間が増える。ほかのエージェントは、
  対象の拡大の作業で、1 つずつ実機で確かめながら足す。

## D5: プラグイン型のエージェントは、需要が出てから

- **決定**: OpenCode・Kilo Code・Pi・Amp・Maki の割り込みは、当面は作らない。この 5 つでは、表示と状態の
  観測だけが使える。
- **理由・代替案**: 5 つは外部コマンドのフックを持たず、プラグインのファイルを置く形になるので、仲立ちの
  作りが別になる（research.md F4）。OpenCode は v1 と v2 で形が違う移行期でもある（F5）。足すときは、
  API が同じ系統の OpenCode と Kilo からが効率がよい。

## D6: 拡張が応答しないときは、素通しが既定。拡張ごとに変えられる

- **決定**: 割り込みの最中に、拡張が落ちた・時間切れになったときは、既定で素通しにする（エージェントを
  止めない）。拡張ごとの設定で「止める」に変えられる。
- **理由・代替案**: 拡張の不具合で、エージェントが動かなくなることを避ける。安全のための拡張
  （危ないコマンドを止めるもの）は、止める側に倒す設定を選べる。代替案（止めるのが既定・拡張ごとに必ず
  書かせる）は採らなかった。

## D7: 登録は、利用者の設定に加えて、プロジェクトの設定も読む（承認つき）

- **決定**: 拡張は、利用者の設定ファイルと、リポジトリの中の設定ファイルの両方に書ける。プロジェクトの
  分は、初回に内容を見せて、利用者が承認したものだけ動かす。
- **理由・代替案**: 利用者は「プロジェクトの設定に持つ」ことの意味の説明を求めたうえで、こちらを選んだ
  （フォームでの回答は「利用者の設定だけ」で、説明の後に変えた）。リポジトリと一緒に拡張を配れる。
  危険は、他人のリポジトリを clone して開いただけで、その中のプログラムが自分の権限で動くことなので、
  承認の確認を必ず付ける。Claude Code のプロジェクトのフックや、Codex・Grok のフックの信頼の確認と
  同じ考え方。
- **影響**: 承認の単位と、内容が変わったときの扱いを、design で決める（research.md「design への申し送り」）。

## D8: 端末版にもパネルを出す。ブラウザ版と端末版で、作業を分ける

- **決定**: 端末版（引数なしの `soda`）にも、文字だけのパネルを出す。表示の面を、ブラウザ版の作業と
  端末版の作業に分け、ブラウザ版から進める。
- **理由・代替案**: 勧めた案（端末版は帯の 1 行と通知まで）より、広い範囲を利用者が選んだ。端末版の
  パネルは作業が大きく、1 つにまとめると差分が大きくなりすぎる（AGENTS.md「差分を小さく切る」）ので、
  分ける。

## D9: 対象にしないもの

- **決定**: 次の 4 つは、拡張の機能として提供しない。
  - エージェント自身の画面（スピナー・ツールの行など）の描き替え
  - ツールの結果の書き換え
  - プロンプトの本文そのものの書き換え
  - ACP でのエージェントの駆動
- **理由**: 自分の画面に描けるのは 6 種類だけで、API がどれも別物。結果の書き換えを無条件にできるのは
  10 種類、プロンプト本文の書き換えは 5 種類だけ。ACP は、エージェントを端末の画面ではなくその口で
  起動する前提で、pane の中で TUI を直接使ういまの形と両立しない（research.md F2・F4）。描画は、
  Sodashitsu の側に置くのが、唯一の共通の解である。

## D10: 既存の連携の食い違いの修正と、Bob Shell の追加は、別の work で先に行う

- **決定**: 調査で見つかった食い違い（Grok のフックの形・Qoder CLI の SessionStart・Devin CLI の設定の
  場所）の確認と修正、および Bob Shell を検知の対象に足すことを、拡張より先に、別の work で行う。
  この work（soda-extensions）には入れない。
- **理由・代替案**: 拡張とは関係のない、既存の連携の正しさの問題で、小さい。先に片づけたほうが、
  拡張の割り込みの仲立ち（同じ `AgentIntegrationInstaller` を広げる）の土台が確かになる。代替案
  （並行で進める・拡張の後にまとめて直す）は採らなかった。

## D11: 調査は、作業の記録に残す

- **決定**: 23 種類の一覧と出典を、この work の `research.md` に残す。利用者向けの `docs/` には、まだ
  置かない。
- **理由**: 文書とソースの記載だけの調査で、実機では確かめていない。利用者向けの対応の一覧は、実際に
  対応して確かめたものから書く。

## D12: 作業を 2 つの work に分ける（表示の面／拡張の登録と起動）。この work は表示の面にする

- **背景**: 依頼の範囲は「表示の面」「拡張の登録と起動」「機能の問い合わせ」。1 つにすると、表示の面で 30〜40 ファイル（protocol・server・cli・web・静的ページ・E2E・文書）、
  登録・承認・プロセスの管理・設定画面でさらに 20〜25 ファイルになる見込み（research.md の追補 R1〜R9 の「触る場所」から数えた）。
- **決定**: 要件の時点で分ける。この work（`20261007-soda-extensions`）は **A: 表示の面（ブラウザ版）**。**B: 拡張の登録と起動**は別の work `20261007-ext-host`（`dependsOn` に A）で、
  要件の骨子だけを書く。subtask（1 つの PR のまま内部で分ける）にはしない。work の `mode` は、依頼に従って `autonomous` に書き換えた（`state.yml` を手で。切り替える CLI が無い）。
- **理由・代替案**: A は単独で検証でき、単独で使える（pane の中のプログラムが `sodactl display` を呼ぶ。`sodactl ask` と同じ形）。B は A の操作を、Sodashitsu が起動したプロセスの標準入出力に載せるだけなので、
  A の後に足せる。aidev の分け方の決まり（単独で検証・着地できるなら別の work）と、AGENTS.md「差分を小さく切る」（PR を小さく）の両方に合う。subtask は PR が 1 つのままで、最後の差分全体のレビューが
  50 ファイルを超える。代替案（B を先に）は、表示する先が無いので採らない。
- **影響**: A の design で、B がそのまま使えるメッセージの型（操作の名前・引数・出来事の行）を決める。B の承認・プロセスの設計の方針は、`20261007-ext-host/decisions.md` に勧める案として残す（確定は B の design）。

## D13: 作者のスクリプトは動かさない。操作は属性で宣言する【利用者に確かめる点】〔2026-10-08 に利用者が覆した → D21。静的な形式の作りとしては残る〕

- **背景**: 依頼は「中身は ask の `view` と同じ隔離した枠に描く。拡張の HTML がアプリ本体・ほかの pane・認証の情報に触れないこと。操作を拡張へ返す道も要る」。ask の `view` の HTML の枠は
  作者のスクリプトを動かす（`sandbox allow-scripts`・`script-src 'self' 'unsafe-inline' 'unsafe-eval'`）。その限界は docs に書かれている: スクリプトは `window.focus(); input.focus()` で
  利用者のキー入力のフォーカスを奪って読め、`location=` で枠を外のページへ移して URL に載せて持ち出せる。`inert`・`visibility`・`display:none`・フォーカスの検知では防げないと実測済み
  （`20261004-ask-media-popup/decisions.md` D9・D10、`docs/sodactl.md`「成果物（view）」）。
- **決定**: 表示の面の `html` は、**作者のスクリプトを動かさない**（枠の CSP は `script-src 'self'`。動くのは枠の静的ページ自身のスクリプトだけ）。ボタン・フォームの操作は、
  属性 `data-soda-action` で宣言し、枠の静的ページのスクリプトが拾って親へ渡す。中身の更新は、プログラムが `set` で送り直す（枠は差し替えるだけ）。
- **理由・代替案**: ask の `view` は、答えるまでの間だけ出る・自分のスキルが作ったものを見せる、という前提で限界を受け入れた。パネルは**出しっぱなし**で、その横の端末に利用者はパスワードも打つ。
  pane のプログラム（エージェントが取ってきた HTML を含む）がキー入力を読んで外へ出せる道を、最初の版から開けない。スクリプトなしなら、枠の遷移の手段（`meta refresh`・フォーム・リンク）を
  取り除けば「外へ出る道が無い」と言える。失うもの: グラフの描画などクライアント側で動く表示（SVG・CSS で描くか、プログラムの側で作って送り直す）。
  代替案 a（ask と同じくスクリプトを許す）は、上の限界を出しっぱなしの枠で受け入れることになる。代替案 b（`--allow-scripts` を付けたときだけ許す）は、付けるのは pane のプログラム自身なので守りにならない
  （許すなら、利用者の設定で pane・拡張ごとに許す形になり、B の承認の仕組みと一緒に設計するのがよい）。
- **影響**: 利用者がスクリプトを要ると判断したら、枠の静的ページをもう 1 つ（`sandbox allow-scripts` だけ・popup なし）足し、別の `format` として足せる（いまの型を変えない）。

## D14: コマンドと識別子の名前は `display`【利用者に確かめる点】

- **決定**: コマンドは `sodactl display`、操作は `display.*`、サーバの置き場は `packages/server/src/display/`。種類の値は `panel`・`band`。
- **理由・代替案**: 「表示の面」の直訳 `surface` は、サーバに既にある（`packages/server/src/surface/`＝`/ws` の RPC の面 `ControlSurface`）。`panel` を語幹にすると `pane` と 1 文字違いで、
  `paneId`／`panelId` の取り違えを招く。`view` は ask の成果物と重なる。`display` は RPC・イベントの名前に使われていない（`packages/protocol/src` を検索して確認）。
  代替案: `sodactl panel`＋`sodactl band`（2 つに分ける。帯とパネルで引数がほぼ同じなので重複する）／`sodactl ext`（B の `soda` 側のコマンドと紛れる）。

## D15: 面は `soda handoff` で引き継がない（消える）【利用者に確かめる点】

- **決定**: 面はサーバのメモリだけに持ち、サーバの再起動・`soda handoff` で消える。待っていた `sodactl display events` は繋ぎ直して `display.reset` の行を出す（プログラムは出し直せる）。
- **理由・代替案**: 既存のメモリだけの状態（質問の待ち・独自トークン・サブエージェントの一覧）は、どれも引き継がない（research.md の追補 R6）。引き継ぐなら `handoff.json` に最大 8 MiB の中身を足すか、
  別のファイルに書いて新しい版が読む作りになり、入れ替えの手順（失敗したら巻き戻す）に手を入れる。B の拡張のプロセスは、入れ替えで起動し直されて自分で出し直すので、引き継ぎが無くても元に戻る。
  困るのは、1 回 `set` して終わるスクリプトの面が、soda の更新で消えること。利用者が要ると判断したら、後から足せる（型は変わらない）。

## D16: 面を出せる画面は、名乗りで見分ける（クライアントの種類では見分けない）

- **背景**: 依頼は「拡張が、いま何が使えるか（パネル・帯・クライアントの種類）を聞ける」。ところが、接続の種類（`client.hello.kind`）は `desktop`・`mobile`・`external` の 3 つで、
  **端末版も `desktop` と名乗る**（research.md の追補 R4）。種類ではブラウザと端末版を見分けられない。
- **決定**: 画面は、接続のたびに `display.subscribe` で「出せる種類」（`panel`・`band`・`actions`）を添えて名乗る。機能の問い合わせは、種類ごとの「出せる画面の数」を返す。
  接続の種類の内訳は返さない（端末版とブラウザを分けられない数は、誤解を招く）。
- **理由・代替案**: ask と同じ見分け方（`ask.subscribe` を送った画面だけが質問を出せる）。端末版のパネルの作業（D8）は、端末版が同じ名乗りを送るだけで足せ、出せる種類が違っても（たとえば文字だけ）表せる。
  代替案（`client.hello.kind` に `tui` を足す）は、既存の接続の検査と端末版の版の組み合わせに手を入れることになり、この作業の範囲を超える。

## D17: 独立点検は壊れやすいタスクだけに掛ける。負の対照のタスク（T19）は test 工程で消化する

- **決定**: `aidev taskcheck` は T1・T2・T3・T4・T6・T7・T8・T10（protocol・サーバの状態・受け口・sodactl の待ちの繰り返し・枠の静的ページとヘッダ・枠からの知らせの検査）に掛け、
  見た目・配線・E2E・文書のタスクには掛けない。全タスクの後に `cross` を 1 回。最後の独立レビュー（差分全体）は省かない。T19（AC28 の負の対照）は、coding では未チェックのまま残し、test 工程で消化する。
- **理由**: AGENTS.md「点検とテストの掛け方」と依頼の指示。autonomous の既定は「全タスク」だが、プロジェクトの規約が上位（`protocol.md`「12.」）。負の対照は、出来上がったテストに対して対策を外して回す作業で、
  生の出力を `test-result.md` に残す先が test 工程（`20261004-ask-media-popup` の T15 と同じ扱い）。

## D18: design で選んだ作り（勧める案で進めたもの）

1. **出来事は「長く待つ要求」（`display.wait`）の繰り返しで受ける**。受け口の「1 接続 1 要求・返事 1 行」を変えない。pane ごとの通し番号（`seq`）と、サーバの起動ごとの印（`epoch`）で、取りこぼしと入れ替えを見分ける。
   代替案（受け口の返事を複数行にして流す）は、受け口の約束と sodactl の繋ぎ直しの型を変えるので採らない。
2. **面の状態は、ask と同じ「名乗って一覧を取り、中身は別に取る」型**。代替案（`Pane` に載せてスナップショットで配る＝独自トークンの型）は、中身が大きい（最大 256 KiB × 64）ので採らない。
3. **サーバはファイルを読まない・外へ通信しない**（中身は sodactl が読んで要求に載せる）。ask の `image`・`view.file` で受け口に足された権限を、この操作では足さない。画像は中身の中の `data:` だけ。
4. **枠の sandbox に `allow-forms` を付ける**。無いと、ブラウザは `form` の `submit` のイベントを起こす前に送信を止める（仕様の理解。実測は E2E で）ので、フォームの値を操作として拾えない。
   実際の送信は、`frame.js` の `preventDefault()`・CSP の `form-action 'none'`・取り除きで `action` を消す、の三重で起きない。代替案（`allow-forms` なしで、送信ボタンの `click` と欄の `Enter` を自前で拾う）は、
   ブラウザの既定のフォームの動き（必須の欄の検査など）を作り直すことになる。E2E で `submit` が起きない・送信が漏れると分かったら、代替案に切り替えてここに追記する。
5. **枠からの操作は、`MessagePort` だけで受ける**（最初の 1 回の `display-ready` だけ、送り主の窓で確かめる）。枠が別のページへ移ったら（`load` の 2 回目）、枠を捨てて作り直す。
   ask の枠は送り主の窓だけで見分けているが、移った先のページも同じ窓になる（research R2）。ask は受ける知らせを絞って害を抑えているのに対し、ここは操作を拡張へ運ぶので、通り道を分ける。
6. **古いサーバの判定で、受け口の `unknown_op` は `/ws` へ落とさない**（ask は落とす）。受け口はその pane のサーバのものなので、そこが知らなければ古いと決まる。ログインしていない pane の中でも「未対応」（終了コード 0）を返せる（D1 の「エラーではなく未対応」）。
7. **利用者が閉じた（dismiss）は、全部の画面から消し、プログラムへ知らせる**。たたむは、その画面だけ。代替案（閉じるも画面ごと）は、プログラムが「見られていない」と知る手段が無くなる。
8. **上限の値**（design「定数と型」）は、ask の定義の上限（256 KiB）・独自トークンの名前の規則（`[A-Za-z0-9_-]` の 1〜32 文字）・受け口の同時接続（64）に合わせて決めた。根拠の実測は無い。

## D24: スクリプトが動く形式の作り（D21 を受けた、書き手の判断）

1. **`format` の値は `script-html`**。sodactl は `--script-html-file <パス>` か、標準入力と `--format script-html`。出せる画面は、名乗りに `script-html` を足す（古い画面・端末版は名乗らないので、出さずに「この画面では出せません」の固定の文言）。
2. **土台は ask の `view` の HTML の枠と同じ**: `allow-same-origin` なしの sandbox（属性と応答ヘッダの二重）・`default-src 'none'`・スクリプトはインラインと `eval` を許す・画像と音は `data:`/`blob:` だけ・ポップアップなし・フォームの送信なし。中身は `postMessage` で渡して `document.write`。
   **強めるところ**: (i) 操作は専用の通り道（`MessagePort`）だけで受ける（ask は送り主の窓だけ）(ii) 枠が移ったら捨てて、面を閉じて知らせる（ask は固定のラベルを残すだけ）(iii) フォーカスの番（下の 4）(iv) 枠の外の固定の印「スクリプト」(v) CSP に `webrtc 'block'` を足す（対応しないブラウザは無視する）。
3. **スクリプトから拡張への道は、小さな API `window.soda`**: `soda.action(名前, 値?)`（静的な形式の操作と同じ出来事・同じ上限）・`soda.onMessage(関数)`（拡張からの知らせを受ける）・`soda.theme`（配色）。
   拡張 → スクリプトは、新しい操作 `display.send`（`sodactl display send <名前>`。中身を出し直さずに、小さなデータを渡す。64 KiB まで・保存しない・いま出している画面にだけ届く）。
   足した理由: スクリプトが動く面で中身を `set` し直すと、枠を作り直すことになる（2 MiB のライブラリを読み直す・スクリプトの状態が消える）。グラフの更新のような使い方には、データだけを渡す道が要る。
4. **フォーカスの番は「覆い」で作る**。スクリプトが動く枠の上に、利用者が操作を始めるまで、透明の覆い（アプリの要素）を置く。覆いを押す・`Enter`・キーの操作（`prefix+i`）で「操作中」になり、覆いが外れて枠へフォーカスが移る。
   操作中でないのに枠がフォーカスを持ったら（＝スクリプトが取った）、アプリがすぐ端末へ戻す。10 秒に 3 回で、面を閉じて（理由 `focus_steal`）、利用者と拡張に知らせる。
   代替案（覆いを置かず、ポインタが枠の上にあるかで見分ける）は採らない: 親は、枠の中のクリックを見られない。ポインタを枠の上に置いたまま端末に打っている利用者から、スクリプトが取った場合と見分けられない。
   代償: 操作中でない間、枠の中のホバー（ツールチップ）は効かない。ホイールは、覆いが受けて枠へ伝える（文書全体のスクロールだけ）。最初の 1 回は、押して操作を始める。
   **戻すまでの短い間に打ったキーは、枠に入りうる**（ask の D10 が「守れていないのに守っているように見える」として検知の案を退けた、その窓）。ここでは、利用者が (b) を決めたので入れ、**限界として docs に書く**（3 回で閉じるので、漏れは短い窓 3 回ぶんまで）。
5. **枠の移動は、止められる前提にしない**。アプリ本体の CSP（`default-src 'self'`。`frame-src` の指定が無いので、これが効く）が、枠が自分で外のページへ移ることを止めるかどうかは、**実測していない**（ask の docs は「止める手段が無い」と書いている）。
   スクリプトが動く形式の最初の E2E で実測し、docs にはその結果を書く（止まるなら「Chromium では止まる。ほかは未確認」、止まらないなら「止められない」）。どちらでも、(c) の検知（`load` の 2 回目）は入れる。
   枠を二重にして外側の CSP の `frame-src` で止める案は、効くかどうかが同じ実測に依り、内側のページに `frame-ancestors` を付けられなくなる（親が不透明 origin になるため）ので、採らない。
6. **静的な形式でも、枠が移ったら「作り直す」のをやめ、面を閉じて知らせる**（理由 `navigated`）。前の設計（1 分に 3 回まで作り直す）より単純で、(c) と同じ扱いになる。

## D25: 上限の取り直し（D22 を受けた、書き手の判断）

- 1 つの面の中身: **2 MiB**（`DISPLAY_CONTENT_MAX_BYTES`）。
- サーバ全体の中身の合計: 8 MiB → **32 MiB**（2 MiB の面が 16。面の数 64 は案のまま）。
- 受け口の要求の 1 行: 1 MiB → **4 MiB**（`PANE_SOCKET_MAX_LINE_BYTES`。受け口の全部の操作に効く。`/ws` の 1 通の上限 4 MiB〔`MAX_WS_PAYLOAD_BYTES`〕と同じ値にそろえる）。
  中身は JSON の文字列として 1 行に載るので、sodactl は送る前に、組み立てた 1 行が 4 MiB を超えないか確かめる。代替案（中身を小分けにして送る操作を足す）は、操作が 2 つ増え、途中で切れたときの後始末が要るので採らない。
  受け口の同時接続は 64 のままなので、最悪で 256 MiB を読みかけで持ちうる（同じ OS の利用者だけが繋げる受け口。安全の境界ではなく、誤りで巻き込まないための上限）。
- 画面が中身を取る `display.get` は、**小分け**（ask の `ask.media` と同じ 768 KiB の片。`IMAGE_CHUNK_BYTES`）にする。`/ws` の 1 通と、別のマシンの中継を通る大きさを、既存の質問のフォームと同じに保つ。
- 新しい上限: pane ごとの `set` の**量**（続けて 8 MiB まで・毎秒 2 MiB 戻る）。回数（続けて 10 回）だけだと、2 MiB の中身を毎秒 10 回出せてしまう。`display.send` のデータは 64 KiB。
- 古いサーバ（受け口の 1 行が 1 MiB）に 1 MiB を超える要求を送ると `bad_request` になり、`/ws` へ落ちてしまう。sodactl は、1 行が 1 MiB を超えるときは、先に `display.features` を呼ぶ（古いサーバは、ここで「未対応」と分かる）。

## D27: 書き直した design と tasks の独立点検（1 巡。19 件）と、直したこと

- 別のコンテキストに、design と tasks を 1 回見せた（CLI の記録は design の 2 巡目。件数 19 は、design 11・tasks 8 の合計）。must は 3 件で、どれも**スクリプトが動く形式の守りの穴**:

  外の origin への移動は、アプリの CSP が止めるかもしれないので、**合否を見る筋は、必ず移れる同じ origin の宛先**にし、外の宛先は「記録するだけ」にした／「移った先から送っても届かない」の確かめを、枠が外れる前の 1 秒のうちに見る形にした／
