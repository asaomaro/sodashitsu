# 決定記録

2026-10-07 に、利用者が ask-form のフォーム（「soda 拡張の方針」）と、その後のやり取りで決めたもの。
根拠の調査は `research.md`。

## D1: 拡張を 3 つの層（表示・観測・割り込み）に分け、下の層から順に出す

- **背景**: Claude Code の Mods は Claude Code だけの機能で、Codex や GitHub Copilot CLI では使えない。
  利用者から「Sodashitsu 側で、Mods でできるような機能を提供できるか」と問われた。あわせて「すべての
  エージェントに対応する必要はなく、ある機能が特定のエージェントでは使えないという状態は許容できる」
  との方針が示された。
- **決定**: 拡張（仮称「soda 拡張」）を、表示（pane の横のパネル・上の帯・通知など）／観測（ターンの完了・
  承認待ち・ツール呼び出しなど）／割り込み（止める・聞く・書き換える・足す・続ける）の 3 層に分ける。
  上の層ほど、使えるエージェントが減る。使えない機能は、エラーではなく「未対応」として拡張に伝える。
- **理由・代替案**: 全部に共通するのは「止める」だけで、それ以上は段階にしかならない（research.md F4）。
  代替案（全エージェントで同じ機能を保証する）は、いちばん弱いエージェントに合わせることになり、
  Claude Code と Codex でできることを捨てる。

## D2: 最初に着手するのは、表示の面

- **決定**: 4 つの作業（表示の面・観測・割り込み・対象の拡大）のうち、表示の面から始める。
- **理由・代替案**: 表示はエージェントに依存せず、検知の対象外のものも含めて、すべてで動く。エージェントの
  側への導入も要らないので、最初に価値が出る。代替案（割り込みを先にして、表示は既存の ask ダイアログで
  代用する）は、実機の確認が要るエージェントごとの作業から始めることになる。

## D3: 拡張は別プロセスで動かし、NDJSON でやり取りする

- **決定**: 拡張は、設定に登録した独立のプログラムとする。Sodashitsu が起動と停止をし、標準入出力で
  1 行 1 JSON をやり取りする。サーバの中で動く JS/TS（Mods と同じ形）にはしない。
- **理由・代替案**: Sodashitsu は、pane を生かし続けることが要である。サーバの中で動かすと、拡張の例外や
  無限ループが、すべての pane と、つないでいる全員を巻き込み、`soda handoff` での入れ替えも複雑になる。
  別プロセスなら、言語を問わず、拡張が落ちてもサーバは無事。欠点（往復の遅さ・見える情報は用意した口
  だけ）は受け入れる。利用者は仕組みの違いの説明を求めたうえで、別プロセスを選んだ。

## D4: 割り込みの最初の対象は、Claude Code と Codex

- **決定**: 止める・利用者に聞く・引数の書き換え・文脈の追加・継続を、まず Claude Code と Codex で動かす。
- **理由・代替案**: この 2 つは、ほぼ全機能を持ち（research.md F2）、Sodashitsu の連携として動作を
  確かめ済み（`agents.ts` の `verified`）。対象を足すほど、実機の確認の手間が増える。ほかのエージェントは、
  対象の拡大の作業で、1 つずつ実機で確かめながら足す。

## D5: プラグイン型のエージェントは、需要が出てから

- **決定**: OpenCode・Kilo Code・Pi・Amp・Maki の割り込みは、当面は作らない。この 5 つでは、表示と状態の
  観測だけが使える。
- **理由・代替案**: 5 つは外部コマンドのフックを持たず、プラグインのファイルを置く形になるので、仲立ちの
  作りが別になる（research.md F4）。OpenCode は v1 と v2 で形が違う移行期でもある（F5）。足すときは、
  API が同じ系統の OpenCode と Kilo からが効率がよい。

## D6: 拡張が応答しないときは、素通しが既定。拡張ごとに変えられる

- **決定**: 割り込みの最中に、拡張が落ちた・時間切れになったときは、既定で素通しにする（エージェントを
  止めない）。拡張ごとの設定で「止める」に変えられる。
- **理由・代替案**: 拡張の不具合で、エージェントが動かなくなることを避ける。安全のための拡張
  （危ないコマンドを止めるもの）は、止める側に倒す設定を選べる。代替案（止めるのが既定・拡張ごとに必ず
  書かせる）は採らなかった。

## D7: 登録は、利用者の設定に加えて、プロジェクトの設定も読む（承認つき）

- **決定**: 拡張は、利用者の設定ファイルと、リポジトリの中の設定ファイルの両方に書ける。プロジェクトの
  分は、初回に内容を見せて、利用者が承認したものだけ動かす。
- **理由・代替案**: 利用者は「プロジェクトの設定に持つ」ことの意味の説明を求めたうえで、こちらを選んだ
  （フォームでの回答は「利用者の設定だけ」で、説明の後に変えた）。リポジトリと一緒に拡張を配れる。
  危険は、他人のリポジトリを clone して開いただけで、その中のプログラムが自分の権限で動くことなので、
  承認の確認を必ず付ける。Claude Code のプロジェクトのフックや、Codex・Grok のフックの信頼の確認と
  同じ考え方。
- **影響**: 承認の単位と、内容が変わったときの扱いを、design で決める（research.md「design への申し送り」）。

## D8: 端末版にもパネルを出す。ブラウザ版と端末版で、作業を分ける

- **決定**: 端末版（引数なしの `soda`）にも、文字だけのパネルを出す。表示の面を、ブラウザ版の作業と
  端末版の作業に分け、ブラウザ版から進める。
- **理由・代替案**: 勧めた案（端末版は帯の 1 行と通知まで）より、広い範囲を利用者が選んだ。端末版の
  パネルは作業が大きく、1 つにまとめると差分が大きくなりすぎる（AGENTS.md「差分を小さく切る」）ので、
  分ける。

## D9: 対象にしないもの

- **決定**: 次の 4 つは、拡張の機能として提供しない。
  - エージェント自身の画面（スピナー・ツールの行など）の描き替え
  - ツールの結果の書き換え
  - プロンプトの本文そのものの書き換え
  - ACP でのエージェントの駆動
- **理由**: 自分の画面に描けるのは 6 種類だけで、API がどれも別物。結果の書き換えを無条件にできるのは
  10 種類、プロンプト本文の書き換えは 5 種類だけ。ACP は、エージェントを端末の画面ではなくその口で
  起動する前提で、pane の中で TUI を直接使ういまの形と両立しない（research.md F2・F4）。描画は、
  Sodashitsu の側に置くのが、唯一の共通の解である。

## D10: 既存の連携の食い違いの修正と、Bob Shell の追加は、別の work で先に行う

- **決定**: 調査で見つかった食い違い（Grok のフックの形・Qoder CLI の SessionStart・Devin CLI の設定の
  場所）の確認と修正、および Bob Shell を検知の対象に足すことを、拡張より先に、別の work で行う。
  この work（soda-extensions）には入れない。
- **理由・代替案**: 拡張とは関係のない、既存の連携の正しさの問題で、小さい。先に片づけたほうが、
  拡張の割り込みの仲立ち（同じ `AgentIntegrationInstaller` を広げる）の土台が確かになる。代替案
  （並行で進める・拡張の後にまとめて直す）は採らなかった。

## D11: 調査は、作業の記録に残す

- **決定**: 23 種類の一覧と出典を、この work の `research.md` に残す。利用者向けの `docs/` には、まだ
  置かない。
- **理由**: 文書とソースの記載だけの調査で、実機では確かめていない。利用者向けの対応の一覧は、実際に
  対応して確かめたものから書く。
