# リモート機能の標準タブ

Webプレビュー、デスクトップ、VSCodeを新規タブの種類として提供する。右下常駐ボタンとマシン見出しのボタンは廃止する。所有するサーバーのタブとして保存・復元し、表示先は選択中machine。Web/モバイルで共通の内容を使う（端末クライアントでのGUI配信は今回の対象外）。

Webプレビューでは同じワークスペース内の表示元paneを選び、画面の名前・ポート入力から登録して開く。エージェント用CLIも維持する。ブラウザPCのlocalhost originを提供するhelperの初回起動は引き続き必要で、接続状態と登録操作を画面で区別する。対象PCのポートを外部公開しない既存の安全境界は変更しない。

タブ切替でhelperを失効させない。Appに存続するhostで各プレビューを管理し、表示先のDOMは同じタブのために保持する。ブラウザ接続＋tab UUIDでviewerを分け、poll/unwatchも対象を指定する。非表示時は10秒ごとに許可を維持し、表示中は250ms間隔、一覧と表示pollは並列化する。非表示タブの新規要求には表示ACKしない。閉じる・許可取消・ブラウザ切断で失効。表示元の削除時は有効なpaneへ戻す。

速度調査: 既存のpreviewは32KiBごとにHTTP読取RPCを往復し、待機pollもある。端末出力のOutputFanout帯域設定とは別経路。現在のsr-pcはreverse接続。同一LANであることは実際の中継経路がLAN直結である保証にはならない。CLI一覧操作はlocal 252〜332ms、sr-pc 345〜1424msだったが、プロセス起動・認証を含むため純粋なRTTや転送速度とは扱わない。

HTTPダウンロードは能力交渉後に最大256KiBのバッチを要求する。すでに溜まったデータだけをまとめ、SSEをバッチ待ちで止めない。旧helper・旧serverとの読取は32KiBのまま。アップロードやWSの上限、認証、失効、全体バイト上限は維持する。実機の速度向上率は未計測。

## 作業の分割と点検

1. タブ種別と保存・復元、入口の整理、共有GUIのタブ内表示。
2. プレビューのpane選択・画面登録・タブごとの許可と接続維持。
3. HTTP読取バッチと旧版の能力交渉。
4. 既存E2Eの入口をタブ作成に置換し、状態保持・画面登録を実ブラウザで検証。

状態・保存・プロトコルが中心なので独立レビュー対象。テスト導線の置換で差分ファイル数が増えるが、機能追加は上記3群に分けて点検する。タブには現行モデルのpane所有構造を残す。デスクトップ/VSCodeのnative tabは裏側にシェルを1つ保持するが、Webの端末部品は描画しない。
