# Durable desktop file checkpoints

First bounded phase: single-file upload/download checkpoints survive process restart and controlled handoff. Folder transfer persistence is a following phase using the same verified stream snapshots. No legacy compatibility work. A checkpoint is only continuation data, never a grant; every restored attach/read/write/finish needs the new share's explicit file permission and current approved root.

Persist only checkpoints the browser explicitly chose to save. Keep existing8 jobs/100MiB per job/15min last-operation TTL. Save absolute wall-clock expiry plus monotonic in-process TTL; expiry never refreshes on restart, future/invalid stamps fail. Server-process restart/handoff only; this phase does not promise recovery after OS/kernel crash or power loss. Private stateDir/desktop-transfers uses owner-only checked paths (Unix owner/mode/ancestors, Windows existing ACL inspection + a DPAPI-user protected metadata-encryption key). Strict bounded versioned metadata; no owner/permission/agent grant persisted. Existing StateDirLock excludes server generations. Do not log checkpoint tokens or data.

Upload snapshots bind exact canonical approved root identity, parent identity, relative destination, generated .soda-transfer-UUID temporary name, temporary file identity and accepted offset/prefix SHA. Sync data before metadata and ACK. Restore no-follow regular file with nlink1, identity/root/parent/prefix checks; verify any unacknowledged tail then truncate only this held exact temporary file back to the durable offset. Restore reconstructs incremental SHA from verified prefix. Never adopt arbitrary temp paths or overwrite an existing destination. Downloads reopen through existing source validation and verify full SHA before seeking to browser offset; unchanged identity/root required. Completed upload receipts must be persisted before reply and revalidate destination identity/content on attach, without republishing.

Cancellation/revoke/settings change invalidate in-memory authority synchronously, then durably remove/tombstone before reporting cancellation. Queued writers cannot resurrect a canceled generation. Settings changes invalidate retained continuation scope; handoff/shutdown preserve only an explicitly frozen registry, drain queued IO and close held descriptors without deleting own temporary file. Handoff rollback can reload frozen records with fresh grants; no implicit permission transfer. Malformed/unsafe storage fails saved-transfer operations explicitly, without falling back to volatile success. No unbounded cleanup or deletion of unknown files; expired known records may only clean their exact verified generated temporary identity.

Verification/taskcheck: durable store permissions/parse/expiry/atomic save, upload exact-byte resume after closed/reopened registry and real child-process exit, download source change, unacknowledged tail, receipt lost after publication, corrupt/symlink/hardlink/renamed root/parent/temp/destination rejection, cancellation-vs-save/finish, owner concurrent attach, settings scope, graceful freeze and rollback. Browser actual DOM/received frames prove reload/new grant/resume. Actual product source negative controls, byte restore and positives. Independent source/correction/final reviews required. Full checks after frozen product, related E2E, clean external smoke, guarded root reflection and PR/main. No real desktop/input/audio or service/ACL/trust changes.

## Early review corrections

Before finish publication, persist a committing intent containing the exact final upload snapshot/inode/relative destination/full SHA and policy generation. Recovery first checks the exact published inode and full content SHA, including either the known temporary hardlink still present or already removed. A same-content replacement inode is rejected. If no destination exists, restore the original private temporary prefix and finish only after a fresh grant. Crash tests cover pre-link, post-link, post-temp-unlink and receipt commit boundaries.

Persistent policy is a separate durable UUID generation bound to the effective locally approved settings and settings-file identity/timestamps. Every retained record includes that generation. Settings update must durably advance generation BEFORE settings write/success ACK, then bind the committed new settings fingerprint without restoring old records; OFF→ON never adopts old UUIDs. Every queued save checks the live generation before/after await and at commit. Startup reads settings binding; offline edits cause a generation advance before restoration. Endpoint policy changes similarly await durable invalidation. Initial endpoint/settings activation occurs before persistence enable, so normal startup does not accidentally clear valid records. Handoff freezes records before changing the provider source epoch, drains queues, then preserves only verified metadata; rollback reloads under the current generation with a new explicit file grant.

## Durability scope clarification

The requested restart implementation in this phase means restart/replacement of the Sodashitsu server process, including abrupt process termination at the publication boundaries, and controlled handoff. Metadata/data are synced and metadata is atomically renamed; POSIX removals also sync the parent directory. There is no Windows write-through/power-loss contract and no claim that temporary creation/publication directory entries survive an OS/kernel crash or power failure. UI/docs explicitly say server restart. A full power-failure durability protocol (including source/destination directories) is separate work, not a hidden promise. Windows DPAPI protects the32-byte AES-GCM metadata key once per store load; chunk checkpoints use Node crypto/atomic metadata IO rather than spawning PowerShell per chunk.
