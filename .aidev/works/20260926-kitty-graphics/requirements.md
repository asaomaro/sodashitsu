# 要件: 端末内の画像表示（Kitty graphics。herdr H13）

## 背景 / 課題

herdr は pane の中のプログラムが Kitty graphics protocol で出した画像を、外側の端末へ描き直して表示する
（herdr 0.9.1 `configuration.mdx`「Kitty graphics」。既定で有効）。本製品（ブラウザの xterm.js で pane を描く）では、
pane の中で `kitten icat`・`chafa -f kitty`・`timg -pk`・`img2sixel` などを動かしても画像は出ない。

- ブラウザの xterm.js（`@xterm/xterm` 6.0.0）は画像を描かない（画像の addon を読み込んでいない）。
- 6.0.0 の parser は APC（`ESC _ … ESC \`）を黙って捨てる（APC のハンドラを登録する口が無い）。Kitty graphics は
  APC `G` なので、そのままでは addon を足しても届かない。
- サーバは pane の出力を headless のミラー（`packages/server/src/terminal/Mirror.ts`）にも流し、端末からの問い合わせには
  **ミラーだけが答える**（ブラウザ側は `QueryFilter.ts` で握りつぶす。D17）。画像の問い合わせ（Kitty の `a=q`・画素の大きさ）
  に誰も答えないと、画像を出すツールは「非対応の端末」と判断するか、応答を待って止まる。
- pane の出力は信頼できない（`cat` した任意のファイル・リモートのプログラム）。画像の経路を足すと、サーバのファイルを
  読ませる転送方法（Kitty の `t=f`/`t=t`/`t=s`）や、巨大な画像でのメモリの食い潰しの入口になりうる。

出典: backlog `.aidev/backlog/product-roadmap.md`「端末機能の拡張: 端末内の画像表示（Kitty graphics。herdr H13）」、
`docs/herdr-parity.md` H13、`.aidev/works/20260918-web-terminal-multiplexer/research.md`（H13 の行・R2）。

## 目的 / ゴール

- pane の中のプログラムが Kitty graphics protocol（直接転送 `t=d`）で出した画像が、その pane を見ているブラウザに表示される状態。
- Sixel と iTerm2 のインライン画像（OSC 1337 `File=`）で出した画像も、ブラウザに表示される状態。
- Kitty graphics で画像を出すツールが、端末の対応状況（`a=q`）と画素の大きさを問い合わせて正しく判断できる状態（応答は
  1 つの pane につき 1 回だけ届き、ブラウザの台数で重複しない）。Sixel・iTerm2 形式のツールは、利用者が形式を指定すれば表示できる状態
  （端末の識別の応答で Sixel の対応を告げることは対象外）。
- pane の出力に何が含まれていても、サーバのファイル・共有メモリを読まず、ネットワークへ取りに行かず、
  サーバとブラウザのメモリが画像で際限なく増えない状態。
- 画像を出さない利用者には何も変わらない状態（文字の表示・入力・再接続・画面履歴・流量制御）。

## ユーザーストーリー

- US1: pane でエージェントや CLI を使う開発者として、`kitten icat` などで出した画像（グラフ・スクリーンショット・図）を
  ブラウザの pane の中でそのまま見たい。なぜなら、画像を確かめるたびに別のビューアやファイル転送に切り替えずに済むから。
  （受け入れ: AC1, AC2, AC3, AC4, AC5）
- US2: Sixel・iTerm2 形式しか出せないツール（`img2sixel`・`imgcat` 等）を使う開発者として、それらの画像も見たい。
  なぜなら、ツールごとに見える・見えないが分かれると結局別のビューアが要るから。（受け入れ: AC6）
- US3: 同じ pane を複数のブラウザで開いている利用者として、画像のツールの問い合わせへの応答が重複しないでほしく、
  Kitty graphics の画像の後の文字の位置がブラウザ同士・サーバの画面と食い違わないでほしい。なぜなら、応答の重複はシェルに
  ゴミの入力として届き、位置の食い違いは再接続や別のブラウザで画面が崩れて見えるから。（受け入れ: AC3, AC7, AC8）
- US4: サーバの運用者として、pane の出力に悪意ある画像のシーケンスが含まれても、サーバのファイルが読まれたり、
  メモリが食い潰されたりしないでほしい。なぜなら、pane には信頼できない出力（`cat` した任意のファイル・リモートの出力）が
  流れるから。（受け入れ: AC9, AC10, AC11）
- US5: 画像を使わない利用者として、今までどおりに動いてほしい。なぜなら、画像の対応のために文字の表示や再接続が
  壊れては困るから。（受け入れ: AC12, AC13）
- US6: herdr から移ってきた利用者として、画像の表示の対応範囲と herdr との違いを docs で知りたい。なぜなら、
  同じツールが同じように動くかを事前に知りたいから。（受け入れ: AC14）

## スコープ

### 対象

- ブラウザの xterm.js で画像を描くこと（Kitty graphics で届いた画像・Sixel・iTerm2 のインライン画像）。
- Kitty graphics protocol の、直接転送（`t=d`）の画像の送信と表示（分割送信 `m=1` を含む）・保存した画像の後からの配置・
  対応状況の問い合わせ（`a=q`）への応答。形式は PNG（`f=100`）と生の画素（`f=24`/`f=32`、zlib 圧縮 `o=z` を含む）。
  表示の大きさの指定（`c`/`r`）とカーソルを動かさない指定（`C=1`）。
- 画素の大きさの問い合わせ（`CSI 14 t`・`CSI 16 t`）への応答と、PTY の画素の大きさ（`TIOCGWINSZ` の `ws_xpixel`/`ws_ypixel`）。
- 画像の大きさ・数・メモリの上限と、ファイル・共有メモリの転送の拒否。
- `docs/herdr-parity.md` H13 の更新。

### 対象外

- 再接続・ページの読み込み直し・後から開いたブラウザでの画像の復元（SNAPSHOT は文字だけ。画像は消える）。
- 画面履歴（20260926-screen-history-replay）への画像の保存。
- Kitty graphics の削除（`a=d`）・アニメーション（`a=f`/`a=a`/`a=c`）・Unicode placeholder（`U=1`）・
  元画像の切り出し（`x`/`y`/`w`/`h`）・セル内の画素のずらし（`X`/`Y`）・重なり順（`z`）・相対配置（`P`/`Q`）。
- ファイル・一時ファイル・共有メモリでの転送（`t=f`/`t=t`/`t=s`）。安全のため対応しない（エラーで答える）。
- Sixel・iTerm2 形式の画像での、サーバの画面（ミラー）のカーソル位置の追従（既知の制約として docs と backlog に残す）。
- 端末の識別（DA1）の応答で Sixel の対応を告げること・`XTSMGRAPHICS` にサーバが答えること。
- 外部操作 API での画像の配置（herdr の `pane.graphics.*`）。
- 画像の表示の有効・無効の設定（herdr の `[terminal].kitty_graphics`）。
- E2E テストの追加・実行（利用者の指示で、この work では E2E を走らせない）。

## 機能要件

- FR1: pane の出力に含まれる Kitty graphics の APC `G` のうち、対応する指定の画像を、その pane を表示している各ブラウザで
  pane の中の該当位置（カーソル位置）に表示する。
- FR2: Kitty graphics の問い合わせ・送信への応答（`OK`・エラー）は、Kitty の規約（`i` の指定の有無・`q` の抑止）どおりに、
  PTY へ 1 回だけ返す。応答の順は、同じ出力の中の他の問い合わせへの応答との前後を保つ。
- FR3: 画像の表示の後のカーソル位置は、ブラウザ同士・サーバのミラーで一致する（Kitty graphics の画像について）。
- FR4: Sixel・iTerm2 形式の画像を、ブラウザで表示する。ブラウザからの問い合わせの応答（画素の大きさ・Sixel の設定）は
  出さない（D17 と同じく応答はサーバだけ）。
- FR5: 画素の大きさの問い合わせにサーバが答え、PTY の画素の大きさを設定する（画像のツールが大きさを決められる）。
- FR6: ファイル・一時ファイル・共有メモリの転送は、ファイル等を一切開かずにエラーで答える。ブラウザへ送る画像は画像のデータ
  そのもので、URL・パスを含めない（ブラウザもサーバもネットワークへ取りに行かない）。
- FR7: サーバでは、1 枚の画像の大きさ・画素数、pane ごとに保存する画像の総量と枚数、途中の分割送信、APC 1 つの長さに
  上限を置く。ブラウザでは、端末 1 つが保持する画像の総量と、Sixel・iTerm2 の 1 枚の大きさ・画素数に上限を置く。
  上限を超えたものは表示せず（ブラウザの保持の総量は古い画像から捨て）、メモリに残さない。

## 非機能要件 / 制約

- 新しい依存を足すなら、npm registry の安定版だけ（beta を xterm.js 本体に入れない）。追加は decisions に記録する。
- 画像を含まない出力の経路（文字だけの出力）の振る舞いと流量制御の閾値は変えない。
- 端末からの問い合わせに答えるのはサーバだけ（D17）。ブラウザの台数で応答が増えない。
- 共有マシンなので負荷試験・E2E は行わない（利用者の指示）。検証は vitest の単体・結合テストと smoke。

## 完了条件 (受け入れ基準)

- [ ] AC1: Kitty graphics の直接転送の PNG（`a=T,f=100,t=d`。1 回での送信と `m=1` の分割送信の両方）が、ブラウザへ届く出力で
      xterm.js が描ける画像の指示（design で決める形式）になり、サーバのミラーには画像の大きさぶんのカーソル移動として届く。
- [ ] AC2: 生の画素（`f=24`/`f=32`。`o=z` の圧縮を含む）も AC1 と同じく画像として届く。
- [ ] AC3: `a=q` に、`i` があり `q` が抑止していなければ `ESC _ G i=<id>;OK ESC \` を PTY へ 1 回返す。非対応の指定
      （形式・転送方法・動作）にはエラーを返す（`q=2` なら返さない）。`i` が無ければ返さない。同じ出力の中で先に来た
      問い合わせ（例 DA1）への応答より先に PTY へ届かない。
- [ ] AC4: 送信だけ（`a=t`）した画像を、後から `a=p` で配置できる。存在しない id の配置にはエラーで答える。
- [ ] AC5: `c`/`r` の指定どおりのセル数で表示され、指定が無ければ画像の画素の大きさとサーバの基準のセルの大きさから
      セル数が決まる。`C=1` ならカーソルは元の位置に戻る。
- [ ] AC6: ブラウザの端末が Sixel と iTerm2 のインライン画像を描く addon を読み込み、その addon の問い合わせへの応答
      （画素の大きさ・`XTSMGRAPHICS`・DA1）はブラウザから PTY へ送られない。
- [ ] AC7: 同じ出力を受けたとき、画像の後のカーソル位置がサーバのミラーとブラウザで一致する（Kitty graphics について）。
- [ ] AC8: `CSI 14 t`・`CSI 16 t` にサーバのミラーが 1 回だけ答え、PTY の大きさを変えるときに画素の大きさも設定する。
- [ ] AC9: `t=f`/`t=t`/`t=s` はファイル・共有メモリを開かず（パスとして解釈しない）、`i` があればエラーで答える。
- [ ] AC10: サーバの上限（1 枚の大きさ・画素数・保存の総量と枚数・分割送信の途中の量・APC 1 つの長さ）を超えた画像は表示されず、
      保持もされない。圧縮の展開は上限の大きさで打ち切る。ブラウザの addon には FR7 の上限（保持の総量・1 枚の大きさ・画素数）が設定される。
- [ ] AC11: サーバが Kitty graphics から作り直してブラウザへ送る画像の指示（AC1 の「画像の指示」）の中身は、サーバが作り直した
      base64 と数値の指定だけで、pane の出力の生の文字列・URL・パスを埋め込まない（制御文字の差し込みができない）。
- [ ] AC12: 画像を含まない出力は、ブラウザ・ミラーへ今までと同じ文字列で届く（APC `G` 以外の APC を含め、分割の境目の扱いを含む）。
- [ ] AC13: 全体のテスト（`pnpm -s test`）・build・typecheck・smoke が通る。
- [ ] AC14: `docs/herdr-parity.md` H13 に対応範囲・herdr との違い・対象外が書かれている。
