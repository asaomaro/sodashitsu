# 判断の記録（20260926-kitty-graphics）

## D1: Kitty graphics をサーバで解釈し、ブラウザには iTerm2 形式で送る（2026-09-27・design の方針）

- 背景: research F1〜F3。ブラウザで Kitty graphics を描く xterm.js の addon（`@xterm/addon-image`）の Kitty 対応は 0.10.0-beta にだけあり、
  `@xterm/xterm` 6.1.0-beta（APC ハンドラの口）を要する。安定版 6.0.0 は APC を読み捨てる。安定版の組 0.9.0 は Sixel と iTerm2 形式（OSC 1337）だけ。
- 案:
  - A. xterm.js 一式（xterm・headless・serialize・webgl・search・unicode11・web-links）を 6.1.0-beta にそろえ、addon 0.10.0-beta で Kitty を描く。
  - B. 6.0.0 のまま、ブラウザで `term.write` の手前に Kitty の解釈と配置を自前で実装する。
  - C. サーバで Kitty の APC を解釈し、ブラウザへは 0.9.0 が描ける iTerm2 形式（大きさはセル数で指定）に作り直して送る。ミラーには同じだけのカーソル移動を送る。
- 決定: **C**。
- 理由:
  - A は端末の中核を beta にする判断で、全 pane の表示・入力・再接続に影響する。利用者の承認無しに自律で入れない（requirements「非機能要件」）。
    さらに応答（`a=q` 等）がブラウザから出るので、応答はサーバだけという D17 と衝突し、ブラウザの台数だけ重複する。
  - B は 1,100 行超の自前実装（配置・スクロール・消去）になり、応答の問題は A と同じ。
  - C は安定版だけで済み、応答はサーバから 1 回だけ出せ、ファイル転送の拒否・上限・展開をサーバ（`node:zlib`）で一か所に置ける。
    画像の大きさをセル数でサーバが決めるので、ブラウザのフォントが違っても画像の後のカーソル位置がブラウザ同士・ミラーで一致する（research F11・F12）。
- 失うもの（C の制約）: 削除（`a=d`）・アニメーション・Unicode placeholder・切り出し・画素のずらし・重なり順は iTerm2 形式で表せない（対象外。backlog）。
  xterm.js 6.1 の安定版が出たら A を見直す（backlog）。

## D2: 新しい依存 `@xterm/addon-image` 0.9.0（web）（2026-09-27・design）

- npm registry の安定版（dist-tag `latest`）。`@xterm/xterm` 6.0.0 と同じコミット `f447274` から同時に公開された組（research F1）。MIT。
- web のパッケージだけに足す（サーバは使わない）。版は他の xterm の addon と同じく固定（`^` を付けない。`packages/web/package.json` の慣習）。

## D3: 基準のセルの大きさは 9×17 px の固定（2026-09-27・design）

- 背景: サーバはブラウザのセルの画素の大きさを知らない（research F14）。Kitty の画像で `c`/`r` の指定が無いとき、画素からセル数を決める基準が要る。
  画素の問い合わせ（`CSI 14/16 t`）・PTY の `ws_xpixel`/`ws_ypixel` にも同じ値を使う。
- 案: (a) 固定値 (b) 大きさを決める権利を持つブラウザが自分のセルの画素を送り、サーバがそれを使う。
- 決定: (a)。値は xterm.js の既定（`fontSize` 15・`fontFamily` 未指定）のセルの目安の 9×17（**実物のブラウザでは未計測**。等幅の既定のフォントの
  字幅はおよそ 0.6em、行の高さはおよそ 1.13em からの目安）。
- 理由: (b) は通信の型（`pane.attach_resize`）・権利の移譲時の扱い・値の検証が増える。画像は iTerm2 形式のセル数の指定で各ブラウザのセルに拡縮されるので、
  基準がずれても画像のセル数は変わらず、見た目の縦横比が少し変わるだけ。(b) は backlog に残す。

## D4: DA1（端末の識別）は変えず、`XTSMGRAPHICS` にも答えない（2026-09-27・design）

- 背景: 0.9.0 はブラウザで DA1 を `?62;4;9;22c`（Sixel の対応を告げる）に変える（research F5）。ミラーは headless の既定の DA1 を返している。
- 決定: ミラーの DA1 は変えない。`XTSMGRAPHICS` にもミラーは答えない。ブラウザ側の addon の DA1・`XTSMGRAPHICS` の応答は握りつぶす（D17）。
- 副作用（coding の T6・T7 の点検で記録）: ブラウザで `XTSMGRAPHICS` を握りつぶすので、設定の操作（`CSI ? 1 ; 3 ; N S` の Sixel のパレット数の変更・`;2` の既定に戻す）も addon に
  届かず、ブラウザのパレットの上限は既定の 256 のまま（256 色を超えるパレットの Sixel は減色して描かれる）。ミラーも答えないので交渉の相手がおらず、
  後から接続したブラウザとも状態がそろう。既知の制約として受け入れる。
- 理由: DA1 は全てのアプリが見る端末の識別で、変えると画像を使わない利用者にも影響しうる（requirements「目的」の最後の項）。Sixel のツールは
  形式の指定（例 `chafa -f sixel`）で使える。Kitty のツールは `a=q` で判定するので影響しない。DA1 で Sixel を告げるかは backlog に残す。

## D5: 上限の値（2026-09-27・design）

- サーバ（pane ごと）: APC 1 つ 16 MiB（herdr の `APC_MAX_BYTES_KITTY` と同じ。research F15）／1 回の送信の復号後の中身 16 MiB（分割送信の合計）／
  画素 4,194,304（2048×2048 相当）・1 辺 8192／展開後の生の画素 16 MiB（4 MP×4 byte）／表示の箱（セル数×基準のセルの画素）4,194,304 画素・
  1 辺 1000 セル／保存（`i` 付きの画像）合計 32 MiB・64 枚（古いものから捨てる）。
- ブラウザ（端末 1 つ）: `storageLimit` 16（MB。既定 128 から下げる。端末はデスクトップで最大 24 個を保つ〔`packages/web/src/main.ts` の LRU の容量〕ので最悪の合計は 384MB。
  design では 32 としたが、T6 の点検で合計 768MB の見積もりが記録に無いと指摘され、下げた。review ラウンド 1 で、addon は新しい 1 枚を
  `storageLimit` を超えても保持すると指摘された。端末 1 つの最悪は 16MB＋1 枚〔`pixelLimit` まで約 67MB。サーバが送る画像は約 16MB まで〕）・`pixelLimit` 16,777,216（既定のまま。サーバの箱の上限の 4 倍の余裕＝
  セルが基準の 2 倍の大きさのブラウザでも捨てない）・`sixelSizeLimit` 12,000,000（既定 25,000,000 から下げる）・`iipSizeLimit` 20,000,000（既定のまま。
  サーバが送る PNG は 16 MiB を超えない）。
- ブラウザへ送る PNG は 1,310,720 バイト（1.25 MiB）まで（coding の cross 点検で追加。`maxPngBytes`）: base64 にして 4/3 倍でも、配信が購読者を stale にする閾値
  （2MB。`packages/server/src/terminal/OutputFanout.ts` の `STALE_THRESHOLD_BYTES`）を 1 枚で超えない。超えると接続直後の購読者は画像ごと捨てられ、
  直後の出力で SNAPSHOT からやり直して画像が消えるため。大きな画像は `EFBIG` で答える（流量制御を画像向けに変える案は backlog）。
- 理由: 生の画素を PNG に作り直す（`deflateSync`）のはサーバの主スレッドで同期に走るので、1 枚を数十 ms に収める大きさにする。表示の箱の上限は、
  ブラウザの `pixelLimit` で捨てられて「ミラーだけカーソルが動く」ずれを作らないため。

## D6: Kitty の応答の順序はミラーの書き込みの完了を待って保つ（2026-09-27・design）

- 背景: 応答はミラーが出力を処理した時点で出る（research F7）。Kitty の応答を出力を受けた瞬間に PTY へ書くと、同じ出力で先に来た問い合わせ（例 DA1）の
  応答を追い越す。`a=q` の後に DA1 を送って「DA1 の応答が先に来たら非対応」と判定するツールでは、追い越しは起きないが、逆順（DA1 の後に `a=q`）では壊れる。
- 決定: Kitty の応答は `mirror.write("", cb)` の `cb` で PTY へ書く（それより前の出力をミラーが処理し終えた後）。
- 代替案: 応答を私用の OSC に包んでミラーに流し、ミラーのハンドラが出す——pane の出力が同じ OSC を出せば自分の PTY へ任意の入力を差し込めるので採らない。

## D7: 出力の境目で割れた `ESC` / `ESC _` は溜めずに流し、続きが Kitty なら CAN で打ち消す（2026-09-27・design）

- 背景: 1 つの APC が node-pty の読み取りの境目で割れうる（research F18）。末尾の `ESC` を次の出力まで溜める案は、`ESC` だけ書いて止まるプログラムで
  表示が遅れるので、時間切れの仕組みが要る。
- 決定: 末尾の `ESC`・`ESC _` はそのまま流し、次の出力の先頭が続き（`_G`・`G`）なら、ブラウザとミラーの両方へ CAN（`0x18`）を 1 つ流してから Kitty として扱う。
  CAN は xterm.js で「制御の列の途中なら取り消して通常の状態に戻る」。通常の状態では何もしない。
- 理由: 時間切れが要らず、割れなかったときと同じ結果になる。

## D8: ブラウザの addon は握りつぶしより先に読み込む（2026-09-27・design）

- xterm.js のハンドラは後から登録したものが先に呼ばれる（research F5）。`installQueryFilter` を画像の addon の読み込みの後に呼び、`XTSMGRAPHICS`
  （`CSI ? … S`）の握りつぶしを足す。`enableSizeReports` は偽にする（真だと xterm.js 本体が `CSI 14/16/18 t` に答える。research F4）。

## D9: PTY の画素の大きさは大きさの変更のときだけ設定する（2026-09-27・design）

- node-pty の `spawn` は画素の大きさを受けない（research F13）。起動の直後に `resize` を足すと全ての pane の起動で SIGWINCH が 1 回増えるので足さない。
  最初の大きさの変更（ブラウザの接続）までは `ws_xpixel` は 0 で、その間はミラーが `CSI 14/16 t` に答える。Windows（ConPTY）は node-pty が無視する。

## D10: architecture 工程は挟まない（2026-09-27・design の終了時）

- protocol「4.5」の 4 条件を見た: モジュールの境界は動かさない（`terminal/` に翻訳器を足し、`TerminalHost` の出力の分岐点の中で使うだけ。依存の向きは既存どおり
  `TerminalHost` → 部品）、新しい構造のパターンの選択は D1 で済んでいる、データの形は翻訳器の中に閉じる（通信の型・永続化は変えない）、tasks に直接分解できる粒度。
  いずれにも当たらない。design の点検（1 ラウンド・11 件）は全て直してから承認した。

## D11: 翻訳器と PNG の部品は tasks の承認の前に下書きした（2026-09-27・tasks）

- design・tasks の点検を別のコンテキストに任せて待つ間に、T1（`png.ts`・`cellPixels.ts`）と T2（`KittyGraphics.ts`）の下書きとテストを書いた。
  design の点検の指摘（分割送信の途中の APC の扱い・`c`/`r` の 0・`a=d` の範囲・`I` の対応表）は、直した design と下書きが一致することを
  coding の中で確かめた（下書きは直した design のとおりに動く。T2 のテストがその規則を検査する）。工程の記録（coding の start）は tasks の承認の後に打つ。

## D12: ミラーの行送りは LF ではなく IND（2026-09-27・coding の T2 の点検）

- 背景: design「振る舞いの詳細 3」はミラーへ LF（`\n`）を `r-1` 個送るとし、「ドメイン固有の考慮」で LNM（`CSI 20 h`）の pane でのずれを既知の制約にしていた。
  点検で、LF の代わりに IND（`ESC D`）を使えば、同じようにスクロールし x を変えないので、このずれ自体を無くせると指摘された。
- 決定: ミラーへは IND を `r-1` 個送る。LNM の既知の制約は無くなる（design の記述より良い側への逸脱）。

## D13: ミラーとブラウザのカーソルが食い違う残りの経路は既知の制約にする（2026-09-27・coding の cross 点検）

- 経路: (1) ブラウザで addon を作れない・読み込めない、(2) 画像の復号（`createImageBitmap`）の失敗、(3) サーバの PNG の検査（署名・チャンク・CRC）をすり抜けた壊れた画像、
  (4) プログラムが `CSI ? 80 h`（DECSDM）を出すとブラウザの addon だけが「左上に置きカーソルを戻す」方式に替わる。いずれもサーバの画面だけ画像の行数ぶん下がる。
- 決定: この work では直さず、docs（H13）と backlog に残す。(4) はブラウザで `?80` を握りつぶすと束ねたモードも殺すので（`Mirror.ts` の `CSI ? h/l` のコメントと同じ問題）、
  addon の内部の状態を戻す形が要り、安定した口が無い。(1)〜(3) はブラウザからサーバへ「置けなかった」を伝える経路が無い（応答はサーバだけの原則）。

## D14: 生の画素の PNG 化は行のフィルタ Paeth・deflate level 6、続けて出る画像の流量は既知の制約（2026-09-27・review ラウンド 1）

- 背景: review ラウンド 1 の 2 件。(1) 生の画素から作る PNG がフィルタ 0・level 1 でほとんど縮まず、pane に収まる写真でも `maxPngBytes` を超えうる。
  (2) 1 MiB 前後の画像を続けて出すと、ブラウザへ送るバイト数が流量制御に入らず `bufferedAmount`（2MB）を超えて stale になり、SNAPSHOT で画像がまとめて消える。
- 決定 (1): 各行を Paeth（先頭の行は Sub）で差分にし、level 6 で圧縮する。行ごとに 5 種を試して選ぶ方式は、1 回の実測で 2048×2048 が約 0.7〜1.4 秒
  主スレッドを止めたので採らない。いまの方式の 1 回の実測（共有マシン・ばらつき大）: 1080×680 で約 0.1 秒・1920×1080 で約 0.2 秒・2048×2048 で約 0.4 秒。
  画素の上限（4 MP）の画像はサーバを 0.4 秒前後止めうる（既知のリスク。backlog の「画像を流量制御の外で送る」と合わせて、別スレッドでの圧縮を後続に残す）。
- 決定 (2): 既知の制約として docs（H13）・backlog に書く。画像のバイト数を流量制御に入れる・画像を別の経路で送るのは、流量制御の設計（design「流量制御」）を
  変えるので、この work では行わない。
