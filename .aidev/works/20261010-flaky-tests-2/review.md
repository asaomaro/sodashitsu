# 記録: 全体テストでだけ落ちる、時間に頼る試験の直し（flaky-tests-2）

## 背景
2026-10-10、着地のたびに `pnpm test` の全体を流すと、毎回 1〜4 件が落ち、そのファイルだけ流し直すと通った（ほかのエージェントの試験と重なり、負荷の平均が 5〜20 の中）。製品のコードは変えない（試験と、試験の道具だけ）。

## 原因と直し
| 試験 | 原因 | 直し |
| :- | :- | :- |
| `paneSocket.integration`「/ws の方式は通さない」 | 状態の前後を丸ごと比べていた。シェルが決める pane の `title` が、後から入る（負荷で再現） | 比較から `title`・`busy`・`cwd` を除く。作業フォルダに頼らない確かめ（拒否される `pane.write` で `touch` させて、ファイルが出来ていない）を足した |
| `display.integration`「量の頻度の上限」 | 量の桶が毎秒 2 MiB 戻るので、要求が遅いと、決め打ちの 5 つ目が通る（負荷で再現） | 通る間は続け、いつか `display_busy`。**通った数が 4 以上 8 以下**（件数の桶〔10〕より、はっきり小さい＝量の桶で断られた） |
| `composeServer.integration`「同じ state-dir の 2 つ目…」ほか | 1 つ目のサーバの git の情報が、5 秒の周期で後から入り、基準の写しと食い違う（負荷で再現） | 基準を取る前に、状態を確定させる（`settleFirstServer`） |
| `ExtensionHost.project`（承認の記録） | 試験の道具が、固定の 2 ms しか待たない（負荷では再現せず。待ちを縮める形で、13 件が落ちることを確認） | fs の要求が無くなるまで待つ（`settleIo`。上限 10 秒で**落とす**。FS の要求の名前が見えることの自己点検つき） |

## 軽いレビュー（実装とは別のエージェント。否定の対照つき）
- 判断: マージしてよい。製品のコードに差分なし。
- **見つかった弱まり**: `display.integration` の最初の直しは、量の桶だけを外しても通った（件数の桶が先に効く）＝量の上限を確かめていなかった → 通った数の範囲を足して直した（量の桶を外すと、`expected 15 to be less than or equal to 8` で落ちることを確認）。
- `settleIo` が、上限で黙って進む → 落とす形に。`GraphView.test` の上限の明示。
- この最後の直しには、再レビューを掛けていない（指摘どおり。否定の対照つき）。
